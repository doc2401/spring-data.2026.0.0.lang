    基于元数据的映射

    为了充分利用 SDN 内部的对象映射功能，您应该使用 @Node 注解来标记已映射的对象。 虽然映射框架并不需要此注解（即使没有任何注解，您的 POJO 也能被正确映射），但该注解可让类路径扫描器发现并预处理您的领域对象，从而提取必要的元数据。 如果您不使用此注解，在首次存储领域对象时，应用程序的性能会略有下降，因为映射框架需要构建其内部元数据模型，以便了解您领域对象的属性以及如何持久化它们。

    映射注解概述

    来自 SDN

    • @Node：在类级别应用，表示该类是数据库映射的候选者。

    • @Id：应用于字段级别，用于标记用于标识目的的字段。

    • @GeneratedValue：与 @Id 一起应用于字段级别，用于指定如何生成唯一标识符。

    • @Property：应用于字段级别，用于修改从属性到属性的映射。

    • @CompositeProperty：在类型为 Map 的属性字段级别应用，这些属性将以复合形式读回。参见复合属性。

    • @Relationship：应用于字段级别，用于指定关系的详细信息。

    • @DynamicLabels：应用于字段级别，用于指定动态标签的来源。

    • @RelationshipProperties：在类级别应用，用于指示该类为关系属性的目标。

    • @TargetNode：应用于带有 @RelationshipProperties 注解的类的字段上，用于从另一端的角度标记该关系的目标。

    以下注解用于指定转换并确保与 OGM 的向后兼容性。

    • @DateLong

    • @DateString

    • @ConvertWith

    有关该主题的更多信息，请参阅转换。

    来自 Spring Data 公共模块

    • @org.springframework.data.annotation.Id 与 SDN 中的 @Id 相同，实际上，@Id 是标注了 Spring Data Commons 的 Id 注解。

    • @CreatedBy：应用于字段级别，用于指示节点的创建者。

    • @CreatedDate：应用于字段级别，用于指示节点的创建日期。

    • @LastModifiedBy：应用于字段级别，用于指示对节点进行最后一次修改的作者。

    • @LastModifiedDate：应用于字段级别，用于指示节点的最后修改日期。

    • @PersistenceCreator：应用于一个构造函数，以在读取实体时将其标记为首选构造函数。

    • @Persistent：在类级别应用，表示该类是数据库映射的候选者。

    • @Version：在字段级别应用时，用于乐观锁，并在保存操作时检查修改。初始值为零，每次更新时会自动递增。

    • @ReadOnlyProperty：在字段级别应用，用于将属性标记为只读。该属性会在数据库读取时进行水合（hydration），但不会接受写入操作。当将其用于关系时，请注意，如果该集合中的相关实体未通过其他方式建立关联，则这些实体不会被持久化。

    有关审计支持的所有注释，请查看审计。

    基本构建块：@Node

    `@Node` 注解用于将类标记为受管理的领域类，使其接受映射上下文的类路径扫描。

    要将对象映射到图中的节点，反之亦然，我们需要一个标签来标识用于映射的类。

    `@Node` 注解拥有一个 `labels` 属性，允许您配置一个或多个标签，用于读取和写入该标注类的实例。 `value` 属性是 `labels` 的别名。 如果您未指定标签，则会将简单类名用作主标签。 如果您需要提供多个标签，您可以选择以下任一方式：

    1. 向 `labels` 属性提供一个数组。 数组中的第一个元素将被视为主标签。

    2. 为primaryLabel提供一个值，并将其他标签放入labels中。

    主要标签应始终是最具体的、能够反映您领域类的标签。

    对于通过仓储或 Neo4j 模板写入的每个已标注类的实例，将在图中写入一个具有至少主标签的节点。反之，所有具有主标签的节点都将被映射到该已标注类的实例。

    关于类层次结构的一个说明

    `@Node` 注解不会从父类型或接口中继承。不过，您可以在每个继承级别单独为领域类添加该注解。这支持多态查询：您可以传入基类或中间类，并检索到节点对应的正确具体实例。此功能仅支持带有 `@Node` 注解的抽象基类。在此类上定义的标签将与具体实现的标签一起作为附加标签使用。

    我们也在某些场景下支持领域类层次结构中的接口：

    在独立模块中定义领域模型，其主标签与接口名称保持一致。
    import java.util.HashSet;
import java.util.List;
import java.util.Objects;
import java.util.Set;

import org.springframework.data.neo4j.core.schema.GeneratedValue;
import org.springframework.data.neo4j.core.schema.Id;
import org.springframework.data.neo4j.core.schema.Node;
import org.springframework.data.neo4j.core.schema.Relationship;
import org.springframework.data.neo4j.core.schema.RelationshipId;
import org.springframework.data.neo4j.core.schema.RelationshipProperties;
import org.springframework.data.neo4j.core.schema.TargetNode;

public interface SomeInterface { (1)

    String getName();

    SomeInterface getRelated();
}

@Node("SomeInterface") (2)
public static class SomeInterfaceEntity implements SomeInterface {

    @Id
    @GeneratedValue
    private Long id;

    private final String name;

    private SomeInterface related;

    public SomeInterfaceEntity(String name) {
        this.name = name;
    }

    @Override
    public String getName() {
        return name;
    }

    @Override
    public SomeInterface getRelated() {
        return related;
    }

    public Long getId() {
        return id;
    }

    public void setRelated(SomeInterface related) {
        this.related = related;
    }
}
    1 仅使用普通的接口名称，就像您为域命名一样
    2 由于需要同步主标签，我们在实现类上添加 @Node 注解（该类可能位于另一个模块中）。请注意，该值必须与实现的接口名称完全一致，无法进行重命名。

    所需的数据结构如下测试所示：

    用于使用多个不同接口实现的所需数据结构。
    void mixedImplementationsRead(@Autowired Neo4jTemplate template) {

    Long id;
    try (Session session = this.driver.session(this.bookmarkCapture.createSessionConfig());
            Transaction transaction = session.beginTransaction()) {
        id = transaction
            .run("""
                CREATE (s:ParentModel{name:'s'})
                CREATE (s)-[:RELATED_1]-> (:SomeInterface3:SomeInterface3b {name:'3b'})
                CREATE (s)-[:RELATED_2]-> (:SomeInterface3:SomeInterface3a {name:'3a'})
                RETURN id(s)""")
            .single()
            .get(0)
            .asLong();
        transaction.commit();
    }

    Optional<Inheritance.ParentModel> optionalParentModel = this.transactionTemplate
        .execute(tx -> template.findById(id, Inheritance.ParentModel.class));

    assertThat(optionalParentModel).hasValueSatisfying(v -> {
        assertThat(v.getName()).isEqualTo("s");
        assertThat(v).extracting(Inheritance.ParentModel::getRelated1)
            .isInstanceOf(Inheritance.SomeInterfaceImpl3b.class)
            .extracting(Inheritance.SomeInterface3::getName)
            .isEqualTo("3b");
        assertThat(v).extracting(Inheritance.ParentModel::getRelated2)
            .isInstanceOf(Inheritance.SomeInterfaceImpl3a.class)
            .extracting(Inheritance.SomeInterface3::getName)
            .isEqualTo("3a");
    });
}
    接口不能定义标识符字段。 因此，它们不能作为存储库的有效实体类型。

    动态或“运行时”管理的标签

    所有通过简单类名隐式定义或通过 `@Node` 注解显式定义的标签都是静态的，无法在运行时更改。如果您需要可以在运行时操作的额外标签，可以使用 `@DynamicLabels`。@DynamicLabels 是一个字段级别的注解，它将类型为 java.util.Collection<String>（例如 List 或 Set）的属性标记为动态标签的来源。

    如果存在此注解，则在加载过程中，节点上所有未通过 `@Node` 和类名进行静态映射的标签将被收集到该集合中。 在写入时，节点的所有标签将被替换为静态定义的标签加上该集合的内容。

    如果您有其他应用程序，请在节点上添加额外的标签，不要使用 @DynamicLabels。 如果托管实体上存在 @DynamicLabels，则生成的标签集合将被写入数据库，成为“唯一真相”。

    识别实例：@Id

    虽然 `@Node` 在类与具有特定标签的节点之间建立了映射，但我们还需要建立该类（对象）的单个实例与节点实例之间的连接。

    这就是 `@Id` 发挥作用的地方。 `@Id` 用于标记类的属性，使其成为对象的唯一标识符。 在理想情况下，这个唯一标识符应是一个唯一的业务键，换句话说，即自然键。 `@Id` 可用于所有具有支持简单类型的属性。

    然而，自然键很难找到。例如，人名通常不唯一，会随时间变化，或者更糟的是，并非每个人都有名和姓。

    因此，我们支持两种不同类型的代理键。

    对于类型为 `String`、`long` 或 `Long` 的属性，可以结合使用 `@Id` 和 `@GeneratedValue`。 `Long` 和 `long` 映射到 Neo4j 的内部 ID。 `String` 则映射到自 Neo4j 5 版本起可用的 `elementId`。 两者均不是节点或关系上的属性，通常对用户不可见；该属性允许 SDN 检索类的单个实例。

    @GeneratedValue 提供了 generatorClass 属性。 generatorClass 可用于指定一个实现 IdGenerator 的类。 IdGenerator 是一个函数式接口，其 generateId 方法接收主键标签和实例，用于生成 ID。 我们开箱即用地支持 UUIDStringGenerator 作为其中一种实现。

    此外，您可以通过在 `@GeneratedValue` 中使用 `generatorRef` 指定应用程序上下文中的 Spring Bean。该 Bean 同样需要实现 `IdGenerator` 接口，但可以利用上下文中的所有资源，包括用于与数据库交互的 Neo4j 客户端或模板。

    请勿跳过关于 唯一 ID 的处理与配置 中的重要说明

    乐观锁：@Version

    Spring Data Neo4j 通过在 `@Version` 注解的 `Long` 类型字段上使用该注解来支持乐观锁。此属性在更新时会自动递增，且不得手动修改。

    例如，如果两个不同线程中的事务都试图修改版本为 x 的同一对象，第一个操作将成功持久化到数据库中。此时，版本号字段会被递增，变为 x+1。第二个操作则会因尝试修改一个在数据库中已不存在的、版本号为 x 的对象而失败，抛出 OptimisticLockingFailureException 异常。在这种情况下，需要重新执行该操作，首先从数据库中获取当前版本的最新对象数据。

    如果使用了业务标识符，则@Version属性也是强制要求的。Spring Data Neo4j 将检查该字段以确定实体是新创建的还是之前已经持久化过。

    映射属性：@Property

    `@Node` 注解类的所有属性都将持久化为 Neo4j 节点和关系的属性。 在没有进一步配置的情况下，Java 或 Kotlin 类中属性的名称将用作 Neo4j 属性名。

    如果您正在使用现有的 Neo4j 模式，或者希望将映射自定义以适应您的需求，则需要使用@Property。 name用于指定数据库中属性的名称。

    连接节点：@Relationship

    @Relationship 注解可用于所有非简单类型的属性。 它适用于其他带有 @Node 注解的类型属性，以及这些类型的集合和映射。

    `type` 或 `value` 属性可用于配置关系的类型，而 `direction` 则用于指定方向。 SDN 中的默认方向为 `Relationship.Direction#OUTGOING`。

    我们支持动态关系。 动态关系表示为 `Map<String, AnnotatedDomainClass>` 或 `Map<Enum, AnnotatedDomainClass>`。 在这种情况下，与其他领域类的关系类型由 Map 的键给出，且不能通过 `@Relationship` 进行配置。

    映射关系属性

    Neo4j 支持不仅为节点定义属性，也为关系定义属性。 为了在模型中表达这些属性，SDN 提供了 `@RelationshipProperties`注解，可应用于一个简单的 Java 类。 在该属性类中，必须恰好有一个字段标记为 `@TargetNode`，用于定义关系所指向的实体；或者，在 `INCOMING` 关系的上下文中，表示该关系源自何处。

    关系属性类及其用法可能如下所示：

    关系属性Roles
    @RelationshipProperties
public class Roles {

	@RelationshipId
	private Long id;

	private final List<String> roles;

	@TargetNode
	private final PersonEntity person;

	public Roles(PersonEntity person, List<String> roles) {
		this.person = person;
		this.roles = roles;
	}


	public List<String> getRoles() {
		return roles;
	}

	@Override
	public String toString() {
		return "Roles{" +
				"id=" + id +
				'}' + this.hashCode();
	}
}

    您需要为生成的内部 ID（@RelationshipId）定义一个属性，以便 SDN 在保存时能够确定哪些关系可以安全地覆盖而不会丢失属性。如果 SDN 找不到用于存储内部节点 ID 的字段，则在启动时将失败。

    为实体定义关系属性
    @Relationship(type = "ACTED_IN", direction = Direction.INCOMING)
private List<Roles> actorsAndRoles = new ArrayList<>();

    关系查询备注

    通常情况下，创建查询时没有对关系/跳数的限制。 SDN 会解析您建模节点所能到达的整个图。

    话虽如此，当您将关系定义为双向映射（即在实体的两端都定义该关系）时，您可能会得到超出预期的结果。

    考虑一个示例，其中一部电影拥有演员，而您希望获取某部特定电影及其所有演员。如果从电影到演员的关系仅仅是单向的，这便不会成为问题。但在双向关系场景中，SDN 在获取特定电影及其演员的同时，还会根据关系的定义获取该演员所关联的其他所有电影。在最坏的情况下，这将导致级联查询，最终为单个实体获取整个图数据。

    完整示例

    将所有这些组合在一起，我们可以创建一个简单的领域。 我们使用电影和具有不同角色的角色：

    示例 1。MovieEntity
    import java.util.ArrayList;
import java.util.List;

import org.springframework.data.neo4j.core.schema.Id;
import org.springframework.data.neo4j.core.schema.Node;
import org.springframework.data.neo4j.core.schema.Property;
import org.springframework.data.neo4j.core.schema.Relationship;
import org.springframework.data.neo4j.core.schema.Relationship.Direction;

@Node("Movie") (1)
public class MovieEntity {

	@Id (2)
	private final String title;

	@Property("tagline") (3)
	private final String description;

	@Relationship(type = "ACTED_IN", direction = Direction.INCOMING) (4)
	private List<Roles> actorsAndRoles = new ArrayList<>();


	@Relationship(type = "DIRECTED", direction = Direction.INCOMING)
	private List<PersonEntity> directors = new ArrayList<>();

	public MovieEntity(String title, String description) { (5)
		this.title = title;
		this.description = description;
	}

	// Getters omitted for brevity

}
    1 @Node 用于将此类标记为托管实体。它还可用于配置 Neo4j 标签。如果您仅使用普通的 @Node，则标签默认为类的名称。
    2 每个实体都必须具有一个 id。我们使用电影的名称作为唯一标识符。
    3 这展示了 @Property 的用法，即可以使用与图属性不同的名称来命名字段。
    4 此配置用于指向某人的入向关系。
    5 这是您的应用程序代码以及 SDN 将使用的构造函数。

    此处人员被映射为两个角色：actors 和 directors。 领域类是相同的：

    示例 2。PersonEntity
    import org.springframework.data.neo4j.core.schema.Id;
import org.springframework.data.neo4j.core.schema.Node;

@Node("Person")
public class PersonEntity {

	@Id
	private final String name;

	private final Integer born;

	public PersonEntity(Integer born, String name) {
		this.born = born;
		this.name = name;
	}

	public Integer getBorn() {
		return this.born;
	}

	public String getName() {
		return this.name;
	}

}
    我们尚未对电影与人物之间的双向关系进行建模。这是为什么呢？ 我们将 MovieEntity 视为聚合根，由其拥有这些关系。 另一方面，我们希望能够从数据库中检索所有人物，而无需同时加载与他们关联的所有电影。 在尝试将数据库中的每个关系以每个方向进行映射之前，请充分考虑您应用程序的使用场景。 虽然您可以这样做，但这可能会导致在对象图中重建一个图数据库，而这并非映射框架的初衷。 如果您必须对循环或双向领域进行建模，但不想获取整个图， 您可以通过使用 投影 来定义所需数据的细粒度描述。
