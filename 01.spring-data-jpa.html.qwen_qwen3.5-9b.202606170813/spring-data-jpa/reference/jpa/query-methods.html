    JPA 查询方法

    本节介绍了使用 Spring Data JPA 创建查询的各种方法。

    查询查找策略

    JPA 模块支持将查询手动定义为字符串，或从方法名派生。

    使用谓词 IsStartingWith、StartingWith、StartsWith、IsEndingWith、EndingWith、EndsWith、IsNotContaining、NotContaining、NotContains、IsContaining、Containing 和 Contains 的派生查询，其相应参数将经过清理。这意味着如果参数中实际包含被 LIKE 识别为通配符的字符，这些字符将被转义，从而仅作为字面量进行匹配。 所使用的转义字符可以通过设置 @EnableJpaRepositories 注解的 escapeCharacter 属性来配置。 请参见 使用值表达式。

    声明查询

    虽然通过方法名获取查询非常方便，但有时可能会遇到方法名解析器不支持您想要使用的关键字，或者导致方法名变得过于冗长丑陋的情况。因此，您可以选择使用遵循命名约定的 JPA 命名查询（有关详细信息，请参阅使用 JPA 命名查询），或者更直接地通过 @Query 注解来标注您的查询方法（有关详情，请参阅使用 @Query）。

    查询创建

    通常，JPA 的查询创建机制如查询方法中所描述的那样工作。以下示例展示了 JPA 查询方法的转换结果：

    示例 1：从方法名创建查询
    public interface UserRepository extends Repository<User, Long> {

  List<User> findByEmailAddressAndLastname(String emailAddress, String lastname);
}

    我们使用 JPQL 创建查询，将其转换为以下查询：select u from User u where u.emailAddress = ?1 and u.lastname = ?2。Spring Data JPA 会执行属性检查并遍历嵌套属性，具体描述请参阅属性表达式。

    下表描述了 JPA 支持的关键词以及包含该关键词的方法所对应的含义：

    表 1。方法名中支持的关键词
    关键字 示例 JPQL 片段

    Distinct

    findDistinctByLastnameAndFirstname

    select distinct …​ where x.lastname = ?1 and x.firstname = ?2

    And

    findByLastnameAndFirstname

    … where x.lastname = ?1 and x.firstname = ?2

    Between

    … where x.startDate between ?1 and ?2

    LessThan

    … where x.age < ?1

    LessThanEqual

    … where x.age <= ?1

    GreaterThan

    In 和 NotIn 同样接受任何 Collection 的子类作为参数，同时也支持数组或可变参数。对于同一逻辑运算符的其他语法形式，请查阅仓储查询关键字。

    `DISTINCT` 有时颇具陷阱，并不总能产生你预期的结果。例如，`select distinct u from User u` 会产生与 `select distinct u.lastname from User u` 完全不同的结果。在第一种情况下，由于包含了 `User.id`，因此不会有重复项，你会得到整个表的数据，且结果为 `User` 对象。

    然而，后一种查询会将焦点缩小到仅 `User.lastname`，并找出该表中所有唯一的姓氏。 这也会返回一个 `List<String>` 结果集，而不是 `List<User>` 结果集。

    `countDistinctByLastname(String lastname)` 也可能产生意外结果。 Spring Data JPA 会推导出 `select count(distinct u.id) from User u where u.lastname = ?1`。 同样，由于 `u.id` 不会产生重复项，该查询将统计所有具有绑定姓名的用户数量。 这与 `countByLastname(String lastname)` 的结果相同！

    这个查询的目的是什么呢？是为了找出具有某个特定姓氏的人数吗？还是为了找出拥有该绑定姓氏的不同人数？亦或是为了找出不同的姓氏的数量？（最后一种情况完全是另一个查询！）使用distinct有时需要手动编写查询语句，并利用@Query来最准确地捕捉所需信息，因为你可能还需要一个投影来捕获结果集。

    基于注解的配置

    基于注解的配置具有无需编辑其他配置文件从而降低维护工作量的优势。为此付出的代价是，每声明一个新的查询都需要重新编译您的领域类。

    示例 2：基于注解的命名查询配置
    @Entity
@NamedQuery(name = "User.findByEmailAddress",
  query = "select u from User u where u.emailAddress = ?1")
public class User {

}

    使用 JPA 命名查询

    示例使用了 <named-query /> 元素和 @NamedQuery 注解。这些配置元素的查询必须在 JPA 查询语言中定义。当然，您也可以使用 <named-native-query /> 或 @NamedNativeQuery。这些元素允许您通过牺牲数据库平台独立性来以原生 SQL 形式定义查询。

    XML 命名查询定义

    若要使用 XML 配置，请将必要的 `` 元素添加到位于类路径中 `META-INF` 文件夹下的 JPA 配置文件 `orm.xml` 中。通过使用某些定义的命名约定，可以启用命名查询的自动调用。有关更多详细信息，请参见下文。

    示例 3。XML 命名查询配置
    <named-query name="User.findByLastname">
  <query>select u from User u where u.lastname = ?1</query>
</named-query>

    该查询具有一个特殊名称，用于在运行时解析它。

    声明接口

    若要启用这些命名查询，请按如下方式指定 `UserRepository`：

    示例 4。UserRepository 中的查询方法声明
    public interface UserRepository extends JpaRepository<User, Long> {

  List<User> findByLastname(String lastname);

  User findByEmailAddress(String emailAddress);
}

    Spring Data 尝试将这些方法的调用解析为命名查询，其格式以配置的实体类的简单名称开头，后跟由点号分隔的方法名。因此，上述示例将使用之前定义的命名查询，而不是尝试根据方法名创建查询。

    Using @Query

    使用命名查询来声明实体查询是一种有效的方法，适用于少量查询的场景。由于这些查询本身与执行它们的 Java 方法绑定，您可以直接使用 Spring Data JPA 的 `@Query` 注解将它们直接绑定到方法上，而不是将其注解到领域类中。这样做可以将领域类从持久化特定的信息中解耦，并将查询逻辑与仓库接口放在一起。

    注解到查询方法的查询优先于使用 `@NamedQuery` 定义或在 `orm.xml` 中声明的命名查询。

    以下示例展示了使用 `@Query` 注解创建的查询：

    示例 5：在查询方法中使用 `@Query` 声明查询。
    public interface UserRepository extends JpaRepository<User, Long> {

  @Query("select u from User u where u.emailAddress = ?1")
  User findByEmailAddress(String emailAddress);
}

    使用高级 LIKE 表达式

    手动定义的查询（使用 `@Query` 创建）的运行机制允许在查询定义中指定高级的 `LIKE` 表达式，如下例所示：

    示例 6。@Query 中的高级 like 表达式
    public interface UserRepository extends JpaRepository<User, Long> {

  @Query("select u from User u where u.firstname like %?1")
  List<User> findByFirstnameEndsWith(String firstname);
}

    在上面的示例中，识别了 `LIKE` 分隔符字符（%），并将查询转换为有效的 JPQL 查询（移除了 %）。执行该查询时，传递给方法调用的参数会附加之前识别的 LIKE 模式。

    原生查询

    使用 `@NativeQuery` 注解可以执行原生查询，如下例所示：

    示例 7：在查询方法中使用 `@NativeQuery` 声明原生查询。
    public interface UserRepository extends JpaRepository<User, Long> {

  @NativeQuery(value = "SELECT * FROM USERS WHERE EMAIL_ADDRESS = ?1")
  User findByEmailAddress(String emailAddress);
}
    @NativeQuery 注解主要是一个组合注解，用于 @Query(nativeQuery=true)，但它还提供了其他属性，例如 sqlResultSetMapping，以便利用 JPA 的 @SqlResultSetMapping(…)。
    Spring Data 可以重写简单的分页和排序查询。 更复杂的查询需要 JSqlParser 位于类路径中，或者在代码中声明一个 countQuery。 有关更多详细信息，请参见下面的示例。
    示例 8：在查询方法中使用 `@NativeQuery` 声明用于分页的原生计数查询。
    public interface UserRepository extends JpaRepository<User, Long> {

  @NativeQuery(value = "SELECT * FROM USERS WHERE LASTNAME = ?1",
    countQuery = "SELECT count(*) FROM USERS WHERE LASTNAME = ?1")
  Page<User> findByLastname(String lastname, Pageable pageable);
}

    对于命名原生查询，也可以采用类似的方法，只需在查询副本后添加.count后缀即可。不过，您可能需要为计数查询注册一个结果集映射。

    除了获取映射结果外，原生查询允许您通过选择Map容器作为方法的返回类型来读取数据库中的原始Tuple。 生成的 Map 包含键值对，分别代表实际的数据库列名和对应的值。

    示例 9：返回原始列名/值对的本地查询
    interface UserRepository extends JpaRepository<User, Long> {

  @NativeQuery("SELECT * FROM USERS WHERE EMAIL_ADDRESS = ?1")
  Map<String, Object> findRawMapByEmail(String emailAddress);      (1)

  @NativeQuery("SELECT * FROM USERS WHERE LASTNAME = ?1")
  List<Map<String, Object>> findRawMapByLastname(String lastname); (2)
}
    1 由 Tuple 支持的单个 Map 结果。
    2 由多个 Tuple 支持的多个 Map 结果。
    基于字符串的元组查询仅由 Hibernate 支持。 Eclipselink 仅支持基于条件的元组查询。

    查询内省与重写

    Spring Data JPA 提供了广泛的功能，可用于执行各种类型的查询。 具体来说，给定一个声明的查询，Spring Data JPA 可以：

    • introspect 查询以获取其投影，并针对接口投影运行元组查询。

    • 如果查询使用构造函数表达式，请使用 DTO 投影；如果查询声明了实体别名或仅包含多字段表达式选择，请重写该投影。

    • 应用动态排序

    • 推导一个 `COUNT` 查询。

    为此目的，我们针对定义明确的 HQL（Hibernate）和 EQL（EclipseLink）方言提供了专用的查询解析器。另一方面，SQL 在不同方言间存在相当大的差异。因此，Spring Data 永远无法支持所有级别的查询复杂度。我们并非通用的 SQL 解析库，而是旨在通过简化查询执行来提高开发人员生产力的工具。我们内置的 SQL 查询增强功能仅支持用于元数据探查的简单查询（如 COUNT 查询推导）。对于更复杂的查询，您需要使用 JSqlParser，或者通过 @Query(countQuery=…) 提供 COUNT 查询。如果 JSqlParser 位于类路径中，Spring Data JPA 将对其原生查询使用该解析器。

    若要实现对选择的细粒度控制，您可以使用 @EnableJpaRepositories 配置 QueryEnhancerSelector：

    示例 10：使用 JavaConfig 配置 Spring Data JPA 仓库
    @Configuration
@EnableJpaRepositories(queryEnhancerSelector = MyQueryEnhancerSelector.class)
class ApplicationConfig {
  // …
}

    QueryEnhancerSelector 是一个策略接口，旨在根据特定查询选择一个 QueryEnhancer。如果您需要，也可以提供自己的 QueryEnhancer 实现。

    应用 QueryRewriter

    有时，无论你尝试应用多少特性，似乎都无法在查询被发送到 `EntityManager` 之前让 Spring Data JPA 应用你希望它应用的所有内容。

    您可以在查询发送至 `EntityManager` 之前获取该查询，并对其进行“重写”。也就是说，您可以在最后一刻对查询进行任何修改。 查询重写适用于实际查询，以及在适用情况下适用于计数查询。 计数查询经过优化，因此要么不需要执行，要么通过其他方式获取计数（例如，如果存在外部事务，则从 Hibernate `SelectionQuery` 派生）。

    示例 11：使用 `@Query` 和 `@NativeQuery` 声明查询重写器。
    public interface MyRepository extends JpaRepository<User, Long> {

		@NativeQuery(value = "select original_user_alias.* from SD_USER original_user_alias",
				queryRewriter = MyQueryRewriter.class)
		List<User> findByNativeQuery(String param);

		@Query(value = "select original_user_alias from User original_user_alias",
                queryRewriter = MyQueryRewriter.class)
		List<User> findByNonNativeQuery(String param);
}

    本示例展示了原生（纯 SQL）重写器和 JPQL 查询，两者均利用相同的 `QueryRewriter`。在此场景中，Spring Data JPA 将在对应类型的应用程序上下文中查找已注册的 Bean。

    您可以这样编写查询重写器：

    示例 12。示例QueryRewriter
    public class MyQueryRewriter implements QueryRewriter {

     @Override
     public String rewrite(String query, Sort sort) {
         return query.replaceAll("original_user_alias", "rewritten_user_alias");
     }
}

    您必须确保您的 `QueryRewriter` 已注册到应用程序上下文中，无论是通过应用 Spring Framework 的某个基于 `@Component` 的注解，还是将其作为 `@Configuration` 类中的 `@Bean` 方法的一部分来实现。

    另一种选择是让仓库本身实现该接口。

    示例 13。提供QueryRewriter的存储库
    public interface MyRepository extends JpaRepository<User, Long>, QueryRewriter {

		@Query(value = "select original_user_alias.* from SD_USER original_user_alias",
                nativeQuery = true,
				queryRewriter = MyRepository.class)
		List<User> findByNativeQuery(String param);

		@Query(value = "select original_user_alias from User original_user_alias",
                queryRewriter = MyRepository.class)
		List<User> findByNonNativeQuery(String param);

		@Override
		default String rewrite(String query, Sort sort) {
			return query.replaceAll("original_user_alias", "rewritten_user_alias");
		}
}

    根据您对 `QueryRewriter` 的使用方式，可能需要配置多个实例，并将它们分别注册到应用上下文中。

    在基于 CDI 的环境中，Spring Data JPA 将在 BeanManager 中搜索您实现的QueryRewriter实例。

    使用 Sort

    排序可以通过提供 `PageRequest` 或使用 `Sort` 直接完成。`Sort` 中的 `Order` 实例实际使用的属性需要与领域模型匹配，这意味着它们必须解析为查询中使用的属性或别名。JPQL 将其定义为一个状态字段路径表达式。

    使用任何不可引用的路径表达式将导致 Exception。

    然而，将 `Sort` 与 @Query 结合使用，允许你在 `ORDER BY` 子句中插入包含函数的非路径检查的 `Order` 实例。这是可行的，因为 `Order` 会被追加到给定的查询字符串中。默认情况下，Spring Data JPA 会拒绝任何包含函数调用的 `Order` 实例，但你可以通过使用 `JpaSort.unsafe` 来添加可能存在风险的排序。

    以下示例使用了 `Sort` 和 `JpaSort`，其中包括 `JpaSort` 上的一个不安全选项：

    示例 14。使用Sort和JpaSort
    public interface UserRepository extends JpaRepository<User, Long> {

  @Query("select u from User u where u.lastname like ?1%")
  List<User> findByAndSort(String lastname, Sort sort);

  @Query("select u.id, LENGTH(u.firstname) as fn_len from User u where u.lastname like ?1%")
  List<Object[]> findByAsArrayAndSort(String lastname, Sort sort);
}

repo.findByAndSort("lannister", Sort.by("firstname"));                (1)
repo.findByAndSort("stark", Sort.by("LENGTH(firstname)"));            (2)
repo.findByAndSort("targaryen", JpaSort.unsafe("LENGTH(firstname)")); (3)
repo.findByAsArrayAndSort("bolton", Sort.by("fn_len"));               (4)
    1 指向领域模型属性的有效 Sort 表达式。
    2 包含函数调用的无效 Sort。抛出异常。
    3 包含显式标记为 不安全 的 Order 的有效 Sort。
    4 指向别名函数的有效 Sort 表达式。

    JpaSort.unsafe(…) limitations

    JpaSort.unsafe(…) 以两种模式运行：

    • 当与派生查询或基于字符串的查询一起使用时，顺序字符串会被追加到查询中。

    • 当与示例查询或规范（使用CriteriaQuery）一起使用时，排序表达式会被解析并作为表达式添加到CriteriaQuery中。

    • JpaSort.JpaOrder.withUnsafe(…) 会创建一个应用了当前排序方向、大小写敏感性和空值处理策略的新的 JpaSort 对象，作用于指定的属性。查询表达式可以包含函数调用、各种子句（例如 CASE WHEN、算术表达式）或属性路径。排序转换不支持子查询表达式、TREAT 和 CAST。

    滚动大型查询结果

    在处理大型数据集时，滚动查询可以帮助高效地处理这些结果，而无需将所有结果加载到内存中。

    您有多种方式消费大型查询结果：

    1. 分页。 在上一章中，您已经学习了Pageable和PageRequest。

    2. 基于偏移量的滚动。 与分页相比，这是一种更轻量级的变体，因为它不需要总结果数量。

    3. 基于键集的滚动。 该方法通过利用数据库索引，避免了基于偏移量的结果检索的缺点。

    了解更多关于针对您的特定配置应使用哪种方法的信息。

    您可以使用滚动 API 配合查询方法，例如示例查询和Querydsl。

    目前尚不支持使用基于字符串的查询方法进行滚动操作。 此外，也不支持使用存储的 @Procedure 查询方法进行滚动操作。

    使用命名参数

    默认情况下，Spring Data JPA 使用基于位置的参数绑定，如前面所有示例中所述。这使得在重构时，查询方法容易因参数位置的变化而引发错误。为解决此问题，您可以使用 @Param 注解为方法参数指定具体名称，并在查询中绑定该名称，如下例所示：

    示例 15：使用命名参数
    public interface UserRepository extends JpaRepository<User, Long> {

  @Query("select u from User u where u.firstname = :firstname or u.lastname = :lastname")
  User findByLastnameOrFirstname(@Param("lastname") String lastname,
                                 @Param("firstname") String firstname);
}
    方法参数将根据其在定义查询中的顺序进行交换。
    从版本 4 开始，Spring 完全支持基于 -parameters 编译器标志的 Java 8 参数名称发现功能。通过在构建中使用此标志作为调试信息的替代方案，您可以省略命名参数的 @Param 注解。

    模板化查询和表达式

    我们支持在通过 `@Query` 手动定义的查询中使用受限表达式。 当执行该查询时，这些表达式将针对一组预定义的变量进行求值。

    如果您不熟悉值表达式，请参阅值表达式基础以了解 SpEL 表达式和属性占位符。

    Spring Data JPA 支持一个名为 `entityName` 的模板变量。 其用法为 `select x from #{#entityName} x`。 该变量会插入与给定存储库关联的域类型的 `entityName`。 `entityName` 的解析方式如下： * 如果域类型在 `@Entity` 注解中设置了 name 属性，则使用该属性值； * 否则，使用域类型的简单类名。

    以下示例展示了在查询字符串中使用#{#entityName}表达式的一个用例，用于定义一个包含查询方法和手动定义查询的仓储接口：

    示例 16：在仓储查询方法中使用 SpEL 表达式：实体名称
    @Entity
public class User {

  @Id
  @GeneratedValue
  Long id;

  String lastname;
}

public interface UserRepository extends JpaRepository<User,Long> {

  @Query("select u from #{#entityName} u where u.lastname = ?1")
  List<User> findByLastname(String lastname);
}

    为避免在 `@Query` 注解的查询字符串中直接声明实体名称，您可以使用 `#{#entityName}` 变量。

    可以使用 @Entity 注解来自定义 entityName。 SpEL 表达式不支持在 orm.xml 中进行自定义。

    当然，您也可以在查询声明中直接使用 `User`，但这需要同时修改查询本身。 对 `#entityName` 的引用可以拾取未来可能将 `User` 类重映射到不同实体名称的情况（例如，通过使用 `@Entity(name = "MyUser")`）。

    在查询字符串中使用 `#{#entityName}` 表达式的另一个用例是：定义一个通用仓储接口，并为具体的领域类型创建专门的仓储接口。为了避免在具体接口中重复定义自定义查询方法，您可以在通用仓储接口的 `@Query` 注解的查询字符串中使用实体名称表达式，如下例所示：

    示例 17：在仓储查询方法中使用 SpEL 表达式——带继承的实体名称
    @MappedSuperclass
public abstract class AbstractMappedType {
  …
  String attribute;
}

@Entity
public class ConcreteType extends AbstractMappedType { … }

@NoRepositoryBean
public interface MappedTypeRepository<T extends AbstractMappedType>
  extends Repository<T, Long> {

  @Query("select t from #{#entityName} t where t.attribute = ?1")
  List<T> findAllByAttribute(String attribute);
}

public interface ConcreteRepository
  extends MappedTypeRepository<ConcreteType> { … }

    在前面的示例中，MappedTypeRepository 接口是几个扩展自 AbstractMappedType 的领域类型的通用父接口。它还定义了通用的 findAllByAttribute(…) 方法，该方法可用于专用仓库接口的实例。如果您现在在 ConcreteRepository 上调用 findAllByAttribute(…)，查询将变为 select t from ConcreteType t where t.attribute = ?1。

    您还可以使用表达式来控制方法参数。在这些表达式中，实体名称不可用，但参数是可用的。它们可以通过名称或索引进行访问，如下面的示例所示。

    示例 18：在仓储查询方法中使用值表达式：访问参数
    @Query("select u from User u where u.firstname = ?1 and u.firstname=?#{[0]} and u.emailAddress = ?#{principal.emailAddress}")
List<User> findByFirstnameAndCurrentUserWithCustomQuery(String firstname);

    对于 `like` 条件，通常希望向字符串类型的参数开头或末尾追加 `%`。这可以通过在绑定参数标记或 SpEL 表达式前或后追加 `%` 来实现。以下示例再次演示了这一点。

    示例 19：在仓储查询方法中使用值表达式：通配符快捷方式
    @Query("select u from User u where u.lastname like %:#{[0]}% and u.lastname like %:lastname%")
List<User> findByLastnameWithSpelExpression(@Param("lastname") String lastname);

    在使用来自不安全源的值的 `like` 条件时，应对这些值进行清理，以防止其包含通配符，从而避免攻击者获取超出其权限范围的数据。为此，SpEL 上下文中提供了 `escape(String)` 方法。该方法会在第一个参数中所有 `_` 和 `%` 实例前添加第二个参数中的单个字符作为转义字符。结合 JPQL 和标准 SQL 中可用的 `like` 表达式的 `escape` 子句，这种方法可以方便地清理绑定参数。

    示例 20：在仓储查询方法中使用值表达式：清理输入值
    @Query("select u from User u where u.firstname like %?#{escape([0])}% escape ?#{escapeCharacter()}")
List<User> findContainingEscaped(String namePart);

    在仓库接口中给定此方法声明，findContainingEscaped("Peter_") 将找到 Peter_Parker 但不会找到 Peter Parker。 可以通过设置 @EnableJpaRepositories 注解的 escapeCharacter 来配置所使用的转义字符。 请注意，SpEL 上下文中可用的 escape(String) 方法仅会转义 SQL 和 JPQL 标准通配符 _ 和 %。 如果底层数据库或 JPA 实现支持额外的通配符，这些通配符将不会被转义。

    示例 21：在仓储查询方法中使用值表达式：配置属性
    @Query("select u from User u where u.applicationName = ?${spring.application.name:unknown}")
List<User> findContainingEscaped(String namePart);

    在查询方法中，您也可以引用配置属性名称（包括回退值），以便在运行时从Environment 解析属性。 属性的评估发生在查询执行时。 通常，属性占位符会解析为类似字符串的值。

    其他方法

    Spring Data JPA 提供了多种构建查询的方法。 但有时，您的查询可能过于复杂，无法使用这些技术来实现。 在这种情况下，请考虑：

    • 如果尚未这样做，只需使用@Query自行编写查询即可。

    • 如果这无法满足您的需求，可以考虑实现自定义实现。这样您就可以在仓储中注册方法，而将具体的实现完全交由您自行决定。这将使您能够：

      • 直接与 EntityManager 通信（编写纯 HQL/JPQL/EQL/原生 SQL，或使用Criteria API）

      • 利用 Spring Framework 的JdbcTemplate（原生 SQL）

      • 使用另一个第三方数据库工具包。

    • 另一种选择是将查询放入数据库中，然后使用 Spring Data JPA 的@StoredProcedure 注解，或者如果它是一个数据库函数，则使用@Query 注解并通过 CALL 调用它。

    这些策略在您需要最大程度控制查询，同时仍让 Spring Data JPA 负责资源管理时最为有效。

    修改查询

    前面的所有章节都描述了如何声明查询以访问给定的实体或实体集合。 您可以通过使用Spring Data 存储库的自定义实现中描述的自定义方法设施，添加自定义的修改行为。 由于这种方法适用于全面的自定义功能，因此对于仅需参数绑定的查询，您可以通过在查询方法上标注@Modifying来对其进行修改，如下例所示：

    示例 22：声明操纵查询
    @Modifying
@Query("update User u set u.firstname = ?1 where u.lastname = ?2")
int setFixedFirstnameFor(String firstname, String lastname);

    这样会将注解到该方法上的查询触发为更新查询，而非选择查询。由于在执行修改查询后，EntityManager 可能包含过期的实体，我们不会自动清空它（有关详细信息请参阅 JavaDoc 中关于 EntityManager.clear() 的说明），因为这实际上会丢弃 EntityManager 中所有尚未刷新的待处理更改。 如果您希望自动清空 EntityManager，可以将 @Modifying 注解的 clearAutomatically 属性设置为 true。

    `@Modifying` 注解仅在结合 `@Query` 注解使用时才有效。 派生查询方法或自定义方法不需要此注解。

    派生删除查询

    Spring Data JPA 还支持派生删除查询，让您无需显式声明 JPQL 查询即可实现删除操作，如下例所示：

    示例 23：使用派生删除查询
    interface UserRepository extends Repository<User, Long> {

  void deleteByRoleId(long roleId);

  @Modifying
  @Query("delete from User u where u.role.id = ?1")
  void deleteInBulkByRoleId(long roleId);
}

    尽管 `deleteByRoleId(…)` 方法看起来基本上会产生与 `deleteInBulkByRoleId(…)` 相同的结果，但这两个方法声明在执行方式上存在重要区别。 正如名称所示，后者方法会向数据库发出单个 JPQL 查询（即注解中定义的那个）。 这意味着即使当前已加载的 `User` 实例也不会触发生命周期回调。

    为了确保生命周期查询确实被调用，对 `deleteByRoleId(…)` 的调用会先执行一次查询，然后逐个删除返回的实例，以便持久化提供者能够真正在这些实体上调用 `@PreRemove` 回调。

    实际上，派生删除查询是运行查询后对结果调用 `CrudRepository.delete(Iterable<User> users)` 的快捷方式，并使其行为与其他 `delete(…)` 方法的实现保持一致。

    删除大量对象时，需考虑性能影响以确保有足够的内存可用。所有生成的对象在删除前都会先加载到内存中，并在会话中保留，直到刷新或完成事务为止。

    应用查询提示

    要将 JPA 查询提示应用于您在存储库接口中声明的查询，可以使用 `@QueryHints` 注解。 该注解接受一个由 JPA `@QueryHint` 注解组成的数组，以及一个布尔标志位，用于在应用分页时可能禁用针对额外计数查询（即触发分页时产生的附加 COUNT 查询）所应用的提示，示例如下：

    示例 24：在仓储方法中使用查询提示
    public interface UserRepository extends Repository<User, Long> {

  @QueryHints(value = { @QueryHint(name = "name", value = "value")},
              forCounting = false)
  Page<User> findByLastname(String lastname, Pageable pageable);
}

    上述声明将对实际查询应用配置的 `@QueryHint`，但不会将其应用于用于计算总页数的计数查询。

    使用 Java Stream<T> 时，请结合您的 JPA 提供程序和 JDBC 驱动程序审查Stream语义和资源处理，特别关注特定于提供程序的获取行为以及驱动程序的获取大小设置。

    为查询添加注释

    有时，您需要根据数据库性能对查询进行调试。 数据库管理员向您展示的查询可能与使用 `@Query` 编写的查询看起来非常不同，或者与您推测的 Spring Data JPA 为自定义查找方法或示例查询所生成的查询完全不同。

    为简化此过程，您可以通过应用 `@Meta` 注解，在几乎任何 JPA 操作中插入自定义注释，无论是查询还是其他操作。

    示例 25。将@Meta注解应用于仓储操作。
    public interface RoleRepository extends JpaRepository<Role, Integer> {

	@Meta(comment = "find roles by name")
	List<Role> findByName(String name);

	@Override
	@Meta(comment = "find roles using QBE")
	<S extends Role> List<S> findAll(Example<S> example);

	@Meta(comment = "count roles for a given name")
	long countByName(String name);

	@Override
	@Meta(comment = "exists based on QBE")
	<S extends Role> boolean exists(Example<S> example);
}

    此示例仓库混合使用了自定义查找器以及覆盖从 `JpaRepository` 继承的操作。无论采用哪种方式，`@Meta` 注解都允许您添加一个 `comment`，该注释将在查询发送至数据库之前插入到查询语句中。

    同样重要的是，此功能不仅限于查询操作，还适用于count和exists操作。虽然未在此展示，它同样适用于某些delete操作。

    虽然我们已尽可能在所有地方应用此功能，但底层 `EntityManager` 的某些操作并不支持注释。例如，`entityManager.createQuery()` 明确文档说明支持注释，但 `entityManager.find()` 操作则不支持。

    JPQL 日志记录或 SQL 日志记录均不是 JPA 的标准功能，因此每个提供者都需要进行自定义配置，如下文各节所示。

    启用 Hibernate 注释

    要在 Hibernate 中启用查询注释，必须将hibernate.use_sql_comments设置为true。

    如果您使用的是基于 Java 的配置设置，可以像这样进行配置：

	<properties>
		<property name="hibernate.use_sql_comments" value="true" />
	</properties>
</persistence-unit>

    最后，如果您使用的是 Spring Boot，可以在您的 `application.properties` 文件中设置它：

    示例 28：基于属性的 Spring Boot 配置

    配置获取图和加载图

    JPA 2.1 规范引入了对指定 Fetch-和 LoadGraph 的支持，我们也通过 `@EntityGraph` 注解提供了该支持，该注解允许您引用 `@NamedEntityGraph` 定义。您可以在实体上使用此注解来配置查询结果的获取计划。可以通过在 `@EntityGraph` 注解上使用 `type` 属性来配置获取的类型（`Fetch` 或 `Load`）。有关进一步参考，请查看 JPA 2.1 规范第 3.7.4 节。

    以下示例展示了如何在实体上定义命名实体图：

    示例 32：在实体上定义命名实体图。
    @Entity
@NamedEntityGraph(name = "GroupInfo.detail",
  attributeNodes = @NamedAttributeNode("members"))
public class GroupInfo {

  // default fetch mode is lazy.
  @ManyToMany
  List<GroupMember> members = new ArrayList<GroupMember>();

  …
}

    以下示例展示了如何在存储库查询方法中引用命名实体图：

    示例 33：在存储库查询方法中引用命名实体图定义。
    public interface GroupRepository extends CrudRepository<GroupInfo, String> {

  @EntityGraph(value = "GroupInfo.detail", type = EntityGraphType.LOAD)
  GroupInfo getByGroupName(String name);

}

    还可以使用 `@EntityGraph` 定义临时实体图。提供的 `attributePaths` 会被转换为相应的 `EntityGraph`，而无需像以下示例中那样在域类型上显式添加 `@NamedEntityGraph`：

    示例 34：在存储库查询方法中使用临时实体图定义
    public interface GroupRepository extends CrudRepository<GroupInfo, String> {

  @EntityGraph(attributePaths = { "members" })
  GroupInfo getByGroupName(String name);

}

    Scrolling

    滚动是一种更细粒度的方法，用于遍历大型结果集的分块数据。 滚动包括稳定排序、滚动类型（基于偏移量或基于键集的滚动）以及结果限制。 您可以通过使用属性名称定义简单的排序表达式，并通过查询推导使用 Top 或 First 关键字 定义静态的结果限制。 您可以连接表达式以将多个条件收集到一个表达式中。

    滚动查询返回一个 `Window<T>`，允许获取元素的滚动位置以获取下一个 `Window<T>`，直到您的应用程序消费完整个查询结果。 类似于通过获取下一批结果来消费 Java 的 `Iterator<List<…>>`，查询结果滚动让您可以通过 `ScrollPosition` 访问位置，方式如下所示：

    Window<User> users = repository.findFirst10ByLastnameOrderByFirstname("Doe", ScrollPosition.offset());
do {

  for (User u : users) {
    // consume the user
  }

  if (users.isLast() || users.isEmpty()) {
    break;
  }

  // obtain the next Scroll
  users = repository.findFirst10ByLastnameOrderByFirstname("Doe", users.positionAt(users.size() - 1));
} while (!users.isEmpty());

    `ScrollPosition` 标识了包含整个查询结果的元素的精确位置。 查询执行将位置参数视为排他性的，结果将从给定位置之后开始返回。 `ScrollPosition#offset()` 和 `ScrollPosition#keyset()` 是 `ScrollPosition` 的特殊形式，用于指示滚动操作的起始点。

    上述示例展示了静态排序和限制。 您可以定义替代的查询方法，接受一个 `Sort` 对象以定义更复杂的排序顺序或按请求进行排序。 同样地，提供一个 `Limit` 对象允许您按请求定义动态限制，而不是应用静态限制。 有关动态排序和限制的更多信息，请参阅查询方法详情。

    遍历并消费Window实例需要大量的条件判断才能实现最优的数据库往返操作，这很容易变成一项重复性工作，而使用WindowIterator可以简化这一过程。

    `WindowIterator` 提供了一种工具，通过消除检查下一个 `Window` 是否存在并应用 `ScrollPosition` 的需求，从而简化了在多个 `Window` 之间滚动浏览的操作。

    WindowIterator<User> users = WindowIterator.of(position -> repository.findFirst10ByLastnameOrderByFirstname("Doe", position))
  .startingAt(ScrollPosition.offset());

while (users.hasNext()) {
  User u = users.next();
  // consume the user
}

    使用偏移量进行滚动

    偏移分页类似于传统分页，它使用一个偏移量（Offset）计数器来跳过指定数量的结果，并让数据源仅返回从给定偏移量开始的结果。 这种简单的机制可以避免将大量结果发送给客户端应用程序。 然而，大多数数据库要求在服务器返回结果之前，必须先将完整的查询结果物化到内存中。

    示例 35：在仓储查询方法中使用OffsetScrollPosition
    interface UserRepository extends Repository<User, Long> {

  Window<User> findFirst10ByLastnameOrderByFirstname(String lastname, OffsetScrollPosition position);
}

WindowIterator<User> users = WindowIterator.of(position -> repository.findFirst10ByLastnameOrderByFirstname("Doe", position))
  .startingAt(OffsetScrollPosition.initial()); (1)
    1 从偏移量为 0 开始，以包含位置 0 处的元素。

    `ScrollPosition.offset()` 与 `ScrollPosition.offset(0L)` 之间存在区别。前者表示滚动操作的开始，指向一个不特定的偏移量；而后者则标识结果中的第一个元素（位于位置 `0`）。鉴于滚动的**独占性**，使用 `ScrollPosition.offset(0)` 会跳过第一个元素并将其转换为偏移量 `1`。

    使用键集过滤进行滚动

    基于偏移量的滚动要求大多数数据库在服务器返回结果之前，先将整个结果集物化。因此，虽然客户端仅能看到请求结果的一部分，但您的服务器仍需构建完整的结果集，从而导致额外的负载。

    键集过滤方法通过利用数据库的内置功能实现子集检索，旨在降低单个查询的计算和 I/O 需求。 该方法维护一组用于恢复滚动操作的键，通过将键传入查询来有效修改过滤条件。

    Keyset-Filtering 的核心思想是依据稳定的排序顺序开始检索结果。当你希望滚动到下一批数据时，会获取一个 ScrollPosition，该位置用于在已排序的结果中重建当前位置。ScrollPosition 捕获了当前 Window 内最后一个实体的键集（keyset）。执行查询时，重建过程会将条件子句重写为包含所有排序字段和主键，以便数据库能够利用潜在索引来运行查询。数据库只需根据给定的键集位置构建一个较小的结果集，而无需完全生成一个大结果集再跳过部分数据以到达特定的偏移量。

    键集过滤要求用于排序的键属性必须为非空值。此限制是由于存储特定比较运算符对 `null` 值的处理方式以及需要在索引源上运行查询所导致的。在可空属性上执行键集过滤将导致意外结果。
    使用 KeysetScrollPosition 与仓储查询方法
    interface UserRepository extends Repository<User, Long> {

  Window<User> findFirst10ByLastnameOrderByFirstname(String lastname, KeysetScrollPosition position);
}

WindowIterator<User> users = WindowIterator.of(position -> repository.findFirst10ByLastnameOrderByFirstname("Doe", position))
  .startingAt(ScrollPosition.keyset()); (1)
    1 从最开头开始，不要应用额外的过滤。

    当数据库中存在与排序字段匹配的索引时，键集过滤效果最佳，因此静态排序非常适用。 应用键集过滤的滚动查询要求查询返回用于排序顺序的属性，并且这些属性必须在返回的实体中进行映射。

    您可以使用接口和 DTO 投影，但请确保包含所有已排序的属性，以避免键集提取失败。

    在指定 `Sort` 顺序时，只需包含与查询相关的排序属性即可；如果您不希望确保查询结果唯一，则无需为此操心。键集查询机制会通过添加主键（或复合主键的其余部分）来修正您的排序顺序，从而保证每个查询结果都是唯一的。
