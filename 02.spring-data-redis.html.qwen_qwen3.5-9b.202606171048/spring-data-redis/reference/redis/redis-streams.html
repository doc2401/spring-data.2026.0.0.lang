    Redis 流

    Redis Streams 以抽象方式对日志数据结构进行建模。通常，日志是追加写的数据结构，可以从起始位置、随机位置或流式读取新消息的方式进行消费。

    有关 Redis Streams 的更多信息，请参阅 Redis 参考文档。

    Redis Streams 的功能大致可分为两个领域：

    • 追加记录

    • 记录消费

    尽管此模式与发布/订阅模式具有相似之处，但主要区别在于消息的持久化方式及其消费机制。

    Pub/Sub 依赖于瞬态消息的广播（即：如果不监听，就会错过消息），而 Redis Stream 使用一种持久化的追加只读数据类型，该类型会保留消息直到流被修剪。在消费模式上的另一个区别是，Pub/Sub 注册的是服务器端订阅，Redis 会将到达的消息推送给客户端；而 Redis Streams 则需要客户端主动轮询。

    org.springframework.data.redis.connection 和 org.springframework.data.redis.stream 包提供了 Redis Streams 的核心功能。

    Appending

    要发送记录，您可以像使用其他操作一样，选择使用低级别的RedisConnection或高级的StreamOperations。这两个实体都提供add（即xAdd）方法，该方法接受记录和目标流作为参数。虽然RedisConnection需要原始数据（字节数组），但StreamOperations允许传入任意对象作为记录，如下例所示：

    // append message through connection
RedisConnection con = …
byte[] stream = …
ByteRecord record = StreamRecords.rawBytes(…).withStreamKey(stream);
con.xAdd(record);

// append message through RedisTemplate
RedisTemplate template = …
StringRecord record = StreamRecords.string(…).withStreamKey("my-stream");
template.opsForStream().add(record);

    流记录携带一个 `Map` 作为其负载，该 Map 由键值对元组组成。向流追加一条记录会返回一个 `RecordId`，该 ID 可用作后续引用。

    Consuming

    在消费端，用户可以消费一个或多个流。Redis 流提供了读取命令，允许从已知流内容中的任意位置（随机访问）开始消费流，并能够越过流的末尾以消费新的流记录。

    在底层，RedisConnection 提供了 xRead 和 xReadGroup 方法，分别对应 Redis 中用于读取流以及在消费者组内读取的命令。请注意，多个流可以作为参数使用。

    Redis 中的订阅命令可能会阻塞。也就是说，在连接上调用 xRead 会导致当前线程阻塞，因为它开始等待消息。只有当读取命令超时或收到消息时，该线程才会被释放。

    要消费流消息，可以在应用程序代码中轮询消息，也可以使用两种通过消息监听容器进行异步接收方式之一：命令式或响应式。每当有新记录到达时，容器会通知应用程序代码。

    同步接收

    虽然流式消费通常与异步处理相关联，但也可以同步地消费消息。重载的 `StreamOperations.read(…)` 方法提供了此功能。在同步接收期间，调用线程可能会阻塞，直到有消息可用为止。StreamReadOptions.block 属性指定接收者在放弃等待消息之前应等待多长时间。

    // Read message through RedisTemplate
RedisTemplate template = …

List<MapRecord<K, HK, HV>> messages = template.opsForStream().read(StreamReadOptions.empty().count(2),
				StreamOffset.latest("my-stream"));

List<MapRecord<K, HK, HV>> messages = template.opsForStream().read(Consumer.from("my-group", "my-consumer"),
				StreamReadOptions.empty().count(2),
				StreamOffset.create("my-stream", ReadOffset.lastConsumed()))

    通过消息监听器容器进行异步接收

    由于其阻塞特性，低级轮询并不理想，因为每个消费者都需要进行连接和线程管理。为缓解这一问题，Spring Data 提供了消息监听器，它们承担了所有繁重的工作。如果您熟悉 EJB 和 JMS，您会发现这些概念非常熟悉，因为它们的设计尽可能接近 Spring Framework 的支持及其消息驱动的 POJO（MDP）。

    Spring Data 提供了两种针对所用编程模型量身定制的实现：

    • StreamMessageListenerContainer 充当命令式编程模型的消息监听容器。它用于从 Redis Stream 消费记录，并驱动注入到其中的 StreamListener 实例。

    • StreamReceiver 提供了消息监听器的响应式变体。它用于从 Redis Stream 消费消息，将其视为可能无限的流，并通过 Flux 发出流消息。

    StreamMessageListenerContainer 和 StreamReceiver 负责消息接收的所有线程管理以及将消息分派到监听器进行处理。消息监听器容器/接收器是 MDP 与消息提供者之间的中介，负责注册接收消息、资源的获取与释放、异常转换等工作。这使得应用程序开发者可以专注于编写（可能较为复杂的）与接收消息（并对之做出反应）相关的业务逻辑，而将繁琐的 Redis 基础设施细节委托给框架处理。

    两个容器均支持运行时配置更改，因此您可以在应用程序运行期间添加或删除订阅，而无需重启。此外，该容器采用懒订阅方式，仅在需要时才使用 RedisConnection。如果所有监听器都已取消订阅，它会自动执行清理操作并释放线程。

    Imperative StreamMessageListenerContainer

    与 EJB 世界中的消息驱动 Bean (MDB) 类似，流驱动 POJO (SDP) 充当流消息的接收器。对 SDP 的唯一限制是它必须实现 StreamListener 接口。此外，请注意，如果您的 POJO 在多个线程上接收消息，则必须确保您的实现是线程安全的。

    class ExampleStreamListener implements StreamListener<String, MapRecord<String, String, String>> {

	@Override
	public void onMessage(MapRecord<String, String, String> message) {

		System.out.println("MessageId: " + message.getId());
		System.out.println("Stream: " + message.getStream());
		System.out.println("Body: " + message.getValue());
	}
}

    StreamListener 是一个函数式接口，因此其实现可以使用 Lambda 形式重写：

    message -> {

    System.out.println("MessageId: " + message.getId());
    System.out.println("Stream: " + message.getStream());
    System.out.println("Body: " + message.getValue());
};

    一旦您实现了 `StreamListener`，接下来就需要创建一个消息监听器容器并注册订阅：

    RedisConnectionFactory connectionFactory = …
StreamListener<String, MapRecord<String, String, String>> streamListener = …

StreamMessageListenerContainerOptions<String, MapRecord<String, String, String>> containerOptions = StreamMessageListenerContainerOptions
			.builder().pollTimeout(Duration.ofMillis(100)).build();

StreamMessageListenerContainer<String, MapRecord<String, String, String>> container = StreamMessageListenerContainer.create(connectionFactory,
				containerOptions);

Subscription subscription = container.receive(StreamOffset.fromStart("my-stream"), streamListener);

    请参照各种消息监听器容器的 Javadoc，以获取每个实现所支持功能的完整描述。

    Reactive StreamReceiver

    流式数据源的响应式消费通常通过事件或消息的 `Flux` 来实现。响应式接收器实现提供了 `StreamReceiver``及其重载的`receive(…)`方法。与`StreamMessageListenerContainer`相比，响应式方法所需的底层资源（如线程）更少，因为它利用了驱动程序提供的线程资源。接收流是一个按需发布的`StreamMessage`发布者：

    Flux<MapRecord<String, String, String>> messages = …

return messages.doOnNext(it -> {
    System.out.println("MessageId: " + message.getId());
    System.out.println("Stream: " + message.getStream());
    System.out.println("Body: " + message.getValue());
});

    现在我们需要创建 `StreamReceiver` 并注册订阅以消费流消息：

    ReactiveRedisConnectionFactory connectionFactory = …

StreamReceiverOptions<String, MapRecord<String, String, String>> options = StreamReceiverOptions.builder().pollTimeout(Duration.ofMillis(100))
				.build();
StreamReceiver<String, MapRecord<String, String, String>> receiver = StreamReceiver.create(connectionFactory, options);

Flux<MapRecord<String, String, String>> messages = receiver.receive(StreamOffset.fromStart("my-stream"));

    请参照各种消息监听器容器的 Javadoc，以获取每个实现所支持功能的完整描述。

    按需消费利用背压信号来激活和停用轮询。当需求得到满足时，StreamReceiver 订阅会暂停轮询，直到订阅者发出进一步的需求信号。根据 ReadOffset 策略的不同，这可能导致消息被跳过。

    Acknowledge strategies

    当通过 `Consumer Group` 读取消息时，服务器会记住某条消息已被投递，并将其添加到待处理条目列表（PEL）中。该列表包含已投递但尚未确认的消息。
    必须通过 `StreamOperations.acknowledge` 对消息进行确认，才能将其从待处理条目列表中移除，如下面的代码片段所示。

    StreamMessageListenerContainer<String, MapRecord<String, String, String>> container = ...

container.receive(Consumer.from("my-group", "my-consumer"), (1)
	StreamOffset.create("my-stream", ReadOffset.lastConsumed()),
    msg -> {

	    // ...
	    redisTemplate.opsForStream().acknowledge("my-group", msg); (2)
    });
    1 从组 my-group 中读取为 my-consumer。接收到的消息未被确认。
    2 处理完成后确认消息。
    若要自动确认接收到的消息，请使用 receiveAutoAck 而非 receive。

    ReadOffset strategies

    流读取操作接受一个读取偏移量规格，用于从指定偏移量开始消费消息。ReadOffset代表读取偏移量规格。Redis 支持三种变体的偏移量，具体取决于您是独立消费流还是在消费者组内消费：

    • ReadOffset.latest() – 读取最新消息。

    • ReadOffset.from(…) – 从特定消息 ID 之后开始读取。

    • ReadOffset.lastConsumed() – 读取最后一条已消费消息 ID 之后的内容（仅适用于消费者组）。

    在基于消息容器的消费场景中，消费消息时需要推进（或递增）读取偏移量。推进操作取决于请求的 `ReadOffset` 以及消费模式（是否使用消费者组）。以下矩阵说明了容器如何推进 `ReadOffset`：

    表 1。ReadOffset 推进
    读取偏移量 独立模式 消费者组

    Latest

    阅读最新消息

    阅读最新消息

    使用上次看到的消息作为下一条消息的 MessageId。

    使用上次看到的消息作为下一条消息的 MessageId。

    根据消费者组最后消费的消息

    从特定消息 ID 和最后消费的消息读取可被视为安全操作，能够确保消费所有追加到流中的消息。使用最新消息进行读取可能会跳过在轮询操作处于死时间期间添加到流中的消息。轮询会引入一段死时间，在此期间各个轮询命令之间可能会有消息到达。流消费并非线性连续读取，而是被分割为重复的 `XREAD` 调用。

    Serialization

    发送到流中的任何记录都需要序列化为二进制格式。由于流与哈希数据结构紧密相关，因此流键、字段名和值使用在 `RedisTemplate` 上配置的相应序列化器。

    表 2。流序列化
    流属性 序列化器 描述

    key

    keySerializer

    用于 `Record#getStream()`

    field

    hashKeySerializer

    用于负载中每个地图键的

    value

    hashValueSerializer

    用于负载中的每个地图值。

    请检查正在使用的RedisSerializer，并注意如果您决定不使用任何序列化器，请确保这些值已经是二进制格式。

    对象映射

    简单值

    StreamOperations 允许通过 ObjectRecord 直接将简单值追加到流中，而无需将这些值放入 Map 结构中。该值随后会被分配给一个 payload 字段，并在读取该值时进行提取。

    ObjectRecord<String, String> record = StreamRecords.newRecord()
    .in("my-stream")
    .ofObject("my-value");

redisTemplate()
    .opsForStream()
    .add(record); (1)

List<ObjectRecord<String, String>> records = redisTemplate()
    .opsForStream()
    .read(String.class, StreamOffset.fromStart("my-stream"));
    1 XADD my-stream * "_class" "java.lang.String" "_raw" "my-value"

    `ObjectRecord` 会经历与其他所有记录完全相同的序列化过程，因此也可以通过返回 `MapRecord` 的非类型化读取操作来获取该记录。

    复数

    向流中添加复杂值可以通过以下三种方式实现：

    • 使用简单值（例如字符串形式的 JSON 表示）进行转换。

    • 使用合适的`RedisSerializer`序列化该值。

    • 将值转换为适合使用HashMapper进行序列化的Map。

    第一种变体是最直接的一种，但它忽略了流结构所提供的字段值功能；不过，流中的值仍然可供其他消费者读取。 第二种选项具有与第一种相同的好处，但可能会导致非常具体的消费者限制，因为所有消费者都必须实现相同的序列化机制。 `HashMapper` 方法则更为复杂，它利用了流的哈希结构，同时展平了源数据。只要选择合适的序列化器组合，其他消费者仍然能够读取记录。

    HashMappers 将负载转换为具有特定类型的 Map。请确保使用能够（反）序列化哈希的 Hash-Key 和 Hash-Value 序列化器。 
    ObjectRecord<String, User> record = StreamRecords.newRecord()
    .in("user-logon")
    .ofObject(new User("night", "angel"));

redisTemplate()
    .opsForStream()
    .add(record); (1)

List<ObjectRecord<String, User>> records = redisTemplate()
    .opsForStream()
    .read(User.class, StreamOffset.fromStart("user-logon"));
    1 XADD user-logon * "_class" "com.example.User" "firstname" "night" "lastname" "angel"

    StreamOperations 默认使用 ObjectHashMapper。 在获取 StreamOperations 时，您可以提供一个符合您需求的 HashMapper。

    redisTemplate()
    .opsForStream(new JacksonHashMapper(true))
    .add(record); (1)
    1 XADD user-logon * "firstname" "night" "@class" "com.example.User" "lastname" "angel"

    StreamMessageListenerContainer 可能无法感知定义在领域类型上的任何 @TypeAlias，因为这些需要通过 MappingContext 进行解析。请确保使用 initialEntitySet 来初始化 RedisMappingContext。

    @Bean
RedisMappingContext redisMappingContext() {
    RedisMappingContext ctx = new RedisMappingContext();
    ctx.setInitialEntitySet(Collections.singleton(Person.class));
    return ctx;
}

@Bean
RedisConverter redisConverter(RedisMappingContext mappingContext) {
    return new MappingRedisConverter(mappingContext);
}

@Bean
ObjectHashMapper hashMapper(RedisConverter converter) {
    return new ObjectHashMapper(converter);
}

@Bean
StreamMessageListenerContainer streamMessageListenerContainer(RedisConnectionFactory connectionFactory, ObjectHashMapper hashMapper) {
    StreamMessageListenerContainerOptions<String, ObjectRecord<String, Object>> options = StreamMessageListenerContainerOptions.builder()
            .objectMapper(hashMapper)
            .build();

    return StreamMessageListenerContainer.create(connectionFactory, options);
}
