    Redis 缓存

    Spring Data Redis 在 `org.springframework.data.redis.cache` 包中提供了 Spring Framework 的缓存抽象的实现。 要将 Redis 用作底层实现，请在配置中添加RedisCacheManager，如下所示：

    @Bean
public RedisCacheManager cacheManager(RedisConnectionFactory connectionFactory) {
    return RedisCacheManager.create(connectionFactory);
}

    RedisCacheManager 的行为可以通过 RedisCacheManager.RedisCacheManagerBuilder 进行配置，从而允许您设置默认的 RedisCacheManager、事务行为以及预定义的缓存。

    RedisCacheManager cacheManager = RedisCacheManager.builder(connectionFactory)
    .cacheDefaults(RedisCacheConfiguration.defaultCacheConfig())
    .transactionAware()
    .withInitialCacheConfigurations(Collections.singletonMap("predefined",
        RedisCacheConfiguration.defaultCacheConfig().disableCachingNullValues()))
    .build();

    如前例所示，RedisCacheManager 支持针对每个缓存进行自定义配置。

    由 RedisCacheManager 创建的 RedisCache 的行为由 RedisCacheConfiguration 定义。 该配置允许您设置键的过期时间、前缀，以及用于在二进制存储格式之间进行转换的 RedisSerializer 实现，如下例所示：

    RedisCacheConfiguration cacheConfiguration = RedisCacheConfiguration.defaultCacheConfig()
    .entryTtl(Duration.ofSeconds(1))
    .disableCachingNullValues();

    RedisCacheManager 默认使用无锁的 RedisCacheWriter 来读写二进制值。 无锁缓存能够提高吞吐量。 由于缺乏条目锁定，Cache 的 putIfAbsent 和 clean 操作可能会导致重叠且非原子的命令，因为这些操作需要向 Redis 发送多个命令。 带锁的实现通过设置显式的锁键并检查该键是否存在来防止命令重叠，但这会导致额外的请求以及潜在的命令等待时间。

    锁定是在缓存级别上应用的，而不是针对每个缓存条目。

    可以按照以下方式选择启用锁定行为：

    RedisCacheManager cacheManager = RedisCacheManager
    .builder(RedisCacheWriter.lockingRedisCacheWriter(connectionFactory))
    .cacheDefaults(RedisCacheConfiguration.defaultCacheConfig())
    ...

    默认情况下，缓存条目的任何 `key` 都会以实际的缓存名称加上两个冒号（`::`）作为前缀。这种行为可以更改为静态前缀或计算前缀。

    以下示例展示了如何设置静态前缀：

    // static key prefix
RedisCacheConfiguration.defaultCacheConfig().prefixCacheNameWith("(͡° ᴥ ͡°)");

The following example shows how to set a computed prefix:

// computed key prefix
RedisCacheConfiguration.defaultCacheConfig()
    .computePrefixWith(cacheName -> "¯\_(ツ)_/¯" + cacheName);

    缓存实现默认使用KEYS和DEL命令来清除缓存。KEYS在大型键空间中可能导致性能问题。因此，可以创建一个带有BatchStrategy的默认RedisCacheWriter，以切换到基于SCAN的批处理策略。SCAN策略需要指定一个批次大小，以避免过多的 Redis 命令往返：

    RedisCacheManager cacheManager = RedisCacheManager
    .builder(RedisCacheWriter.nonLockingRedisCacheWriter(connectionFactory, BatchStrategies.scan(1000)))
    .cacheDefaults(RedisCacheConfiguration.defaultCacheConfig())
    ...

    `KEYS` 批处理策略在使用任何驱动和 Redis 操作模式（独立模式、集群模式）时均得到完全支持。 使用 Lettuce 驱动时，`SCAN` 命令得到完全支持。 Jedis 仅在非集群模式下支持 `SCAN` 命令。

    默认情况下，RedisCache 的统计功能处于禁用状态。 使用 RedisCacheManagerBuilder.enableStatistics() 可通过 RedisCache#getStatistics() 收集本地 命中 和 未命中 数据，并返回所收集数据的快照。

    Redis 缓存过期

    时间到空闲（TTI）和时间到生存（TTL）的实现，在不同数据存储中的定义和行为甚至存在差异。

    一般来说：

    • 生存时间（TTL）过期 - TTL 仅在创建或更新数据访问操作时被设置和重置。 只要条目在 TTL 过期超时之前被写入（包括创建时），其超时时间就会重置为配置的 TTL 过期超时时长。 例如，如果 TTL 过期超时设置为 5 分钟，则在条目创建时将超时设为 5 分钟；此后在该 5 分钟间隔内任何一次更新操作都会将超时重置为 5 分钟。 如果在 5 分钟内未发生任何更新，即使在此期间读取了多次条目，甚至仅读取了一次，该条目仍会过期。 声明 TTL 过期策略时，必须写入条目以防止其过期。

    • 空闲超时时间（TTI）过期——TTI 在条目被读取或更新时会被重置，这实际上是对 TTL 过期策略的扩展。

    无论对条目执行何种类型的数据访问操作（读取、写入或其他），只要配置了 TTL，某些数据存储会在 TTL 到期时使该条目失效。 在设置并配置的 TTL 过期超时时间到达后，该条目将被无条件地从数据存储中驱逐。 驱逐操作（例如：销毁、使无效、持久化存储中的溢出到磁盘等）因数据存储而异。

    Time-To-Live (TTL) Expiration

    Spring Data Redis 的 ``Cache`实现支持缓存条目的生存时间(TTL)过期。用户可以通过提供新的``RedisCacheWriter.TtlFunction`接口的实现，以固定``Duration`或为每个缓存条目动态计算``Duration`的方式配置 TTL 过期超时时间。

    RedisCacheWriter.TtlFunction 接口是在 Spring Data Redis 3.2.0 版本中引入的。

    如果所有缓存条目都应在设定的时间后过期，只需配置一个带有固定 `Duration` 的 TTL 过期超时，如下所示：

    RedisCacheConfiguration fiveMinuteTtlExpirationDefaults =
    RedisCacheConfiguration.defaultCacheConfig().enableTtl(Duration.ofMinutes(5));

    然而，如果需要根据缓存条目变化 TTL 过期超时时间，则必须提供自定义的RedisCacheWriter.TtlFunction接口实现：

    enum MyCustomTtlFunction implements TtlFunction {

    INSTANCE;

    @Override
    public Duration getTimeToLive(Object key, @Nullable Object value) {
        // compute a TTL expiration timeout (Duration) based on the cache entry key and/or value
    }
}

    在底层实现中，一个固定的 `Duration` 类型的 TTL 过期时间被封装在一个 `TtlFunction` 实现中，该实现返回所提供的 `Duration`。

    然后，您可以使用以下方法在全局范围内配置固定的 `Duration` 或动态的、针对每个缓存条目的 `Duration` TTL 过期时间：

    全局固定持续时间 TTL 过期超时
    RedisCacheManager cacheManager = RedisCacheManager.builder(redisConnectionFactory)
    .cacheDefaults(fiveMinuteTtlExpirationDefaults)
    .build();

    Or, alternatively:

    全局动态计算的每缓存条目持续时间 TTL 过期超时时间
    RedisCacheConfiguration defaults = RedisCacheConfiguration.defaultCacheConfig()
        .entryTtl(MyCustomTtlFunction.INSTANCE);

RedisCacheManager cacheManager = RedisCacheManager.builder(redisConnectionFactory)
    .cacheDefaults(defaults)
    .build();

    当然，您可以使用以下方法同时结合全局和每缓存的配置：

    全局固定持续时间 TTL 过期超时
    RedisCacheConfiguration predefined = RedisCacheConfiguration.defaultCacheConfig()
                                         .entryTtl(MyCustomTtlFunction.INSTANCE);

Map<String, RedisCacheConfiguration> initialCaches = Collections.singletonMap("predefined", predefined);

RedisCacheManager cacheManager = RedisCacheManager.builder(redisConnectionFactory)
    .cacheDefaults(fiveMinuteTtlExpirationDefaults)
    .withInitialCacheConfigurations(initialCaches)
    .build();

    Time-To-Idle (TTI) Expiration

    Redis 本身并不支持真正的空闲时间（TTI）过期概念。 不过，使用 Spring Data Redis 的缓存实现，可以实现类似空闲时间过期的行为。

    Spring Data Redis 缓存实现中的 TTI 配置必须显式启用，即采用 opt-in 模式。此外，您还必须通过固定 `Duration` 或上述 `Redis Cache Expiration` 中描述的自定义 `TtlFunction` 接口实现来提供 TTL 配置。

    例如：

    @Configuration
@EnableCaching
class RedisConfiguration {

    @Bean
    RedisConnectionFactory redisConnectionFactory() {
        // ...
    }

    @Bean
    RedisCacheManager cacheManager(RedisConnectionFactory connectionFactory) {

        RedisCacheConfiguration defaults = RedisCacheConfiguration.defaultCacheConfig()
            .entryTtl(Duration.ofMinutes(5))
            .enableTimeToIdle();

        return RedisCacheManager.builder(connectionFactory)
            .cacheDefaults(defaults)
            .build();
    }
}

    由于 Redis 服务器未实现真正的 TTI（Time To Idle）概念，因此只能通过支持过期选项的 Redis 命令来实现 TTI。 在 Redis 中，“过期”在技术上是一种时间到活（TTL）策略。 然而，可以在读取键的值时传递 TTL 过期时间，从而有效地重置 TTL 过期超时时间，正如 Spring Data Redis 中的 `Cache.get(key)` 操作当前所做的那样。

    `RedisCache.get(key)` 通过调用 Redis 的 `GETEX` 命令实现。

    Redis 的 GETEX 命令仅在 Redis 6.2.0 及更高版本中可用。因此，如果您未使用 Redis 6.2.0 或更高版本，则无法使用 Spring Data Redis 的 TTI 过期功能。如果在不兼容的 Redis（服务器）版本上启用 TTI，将抛出命令执行异常。系统不会尝试判断 Redis 服务器版本是否正确以及是否支持 GETEX 命令。

    要在 Spring Data Redis 应用程序中实现真正的空闲时间（TTI）过期行为，则必须在每次读取或写入操作时一致地对条目进行访问并设置（TTL）过期时间。此规则没有例外。 如果您的 Spring Data Redis 应用程序混合使用了不同的数据访问模式（例如：缓存、使用 RedisTemplate 调用操作，以及可能尤其是使用 Spring Data Repository CRUD 操作），那么即使设置了 TTL 过期时间，访问某个条目也不一定能阻止该条目过期。 例如，一个条目可能在带有 TTL 过期时间的 @Cacheable 服务方法调用期间被“放入”（写入）缓存（即执行 SET <expiration options>），随后在过期超时之前使用 Spring Data Redis Repository 进行读取（使用不带过期选项的 GET）。 如果不指定过期选项而简单执行 GET，将不会重置条目的 TTL 过期时间。因此，即使刚刚读取了该条目，它仍可能在下次数据访问操作之前过期。 由于 Redis 服务器无法强制执行此规则，因此当配置了空闲时间过期时，您的应用程序有责任在适当的情况下，无论是在缓存内还是缓存外，一致地访问条目。
