    定义查询方法

    仓库代理有两种方式从方法名派生出特定存储的查询：

    • 通过直接从方法名推导查询。

    • 通过使用手动定义的查询。

    可用选项取决于具体商店。 然而，必须有一种策略来决定实际生成的查询。 下一节将介绍可用的选项。

    查询查找策略

    仓库基础设施可采用以下策略来解析查询。 使用 XML 配置时，可通过 `query-lookup-strategy` 属性在命名空间级别进行策略配置。 对于 Java 配置，可使用 `EnableJpaRepositories` 注解的 `queryLookupStrategy` 属性。 某些策略可能不适用于特定的数据存储源。

    • CREATE 尝试从查询方法名构建特定存储库的查询。 一般方法是移除给定的一组已知前缀，然后解析剩余的方法部分。 您可以在“查询创建"中了解更多关于查询构建的内容。

    • USE_DECLARED_QUERY 尝试查找已声明的查询，若未找到则抛出异常。 该查询可通过某个位置的注解定义，或通过其他方式声明。 请参阅特定存储器的文档以了解其可用的选项。 如果在引导阶段，仓库基础设施未能找到对应方法的已声明查询，则操作将失败。

    • CREATE_IF_NOT_FOUND（默认值）结合了 CREATE 和 USE_DECLARED_QUERY。 它首先查找已声明的查询，如果未找到已声明的查询，则创建基于自定义方法名的查询。 这是默认的查找策略，因此如果您没有显式配置任何内容，将使用此策略。 它允许通过方法名快速定义查询，同时也支持根据需要引入已声明的查询来对这些查询进行自定义调整。

    查询创建

    Spring Data 存储库基础设施中内置的查询构建器机制，可用于构建针对存储库实体的约束查询。

    以下示例展示了如何创建多个查询：

    通过方法名创建查询
    interface PersonRepository extends Repository<Person, Long> {

  List<Person> findByEmailAddressAndLastname(EmailAddress emailAddress, String lastname);

  // Enables the distinct flag for the query
  List<Person> findDistinctPeopleByLastnameOrFirstname(String lastname, String firstname);
  List<Person> findPeopleDistinctByLastnameOrFirstname(String lastname, String firstname);

  // Enabling ignoring case for an individual property
  List<Person> findByLastnameIgnoreCase(String lastname);
  // Enabling ignoring case for all suitable properties
  List<Person> findByLastnameAndFirstnameAllIgnoreCase(String lastname, String firstname);

  // Enabling static ORDER BY for a query
  List<Person> findByLastnameOrderByFirstnameAsc(String lastname);
  List<Person> findByLastnameOrderByFirstnameDesc(String lastname);
}

    查询方法名称的解析分为主体和谓词两部分。第一部分（如 `find…By`、`exists…By`）定义查询的主体，第二部分构成谓词。引入子句（即主体）可以包含进一步的表达式。在 `find`（或其他引入关键字）与 `By` 之间的任何文本均被视为描述性内容，除非使用了结果限制关键字之一，例如使用 `Distinct` 为要创建的查询设置 distinct 标志，或使用 Top/First 来限制查询结果。

    附录包含查询方法主题关键词的完整列表以及查询方法谓词关键词，包括排序和大小写修饰符。 然而，第一个By充当分隔符，用于指示实际谓词条件的开始。 在最基本的层面上，您可以定义实体属性的条件，并使用And和Or将它们连接起来。

    解析方法的实际结果取决于您创建查询所使用的数据持久化存储。 不过，有一些通用事项需要注意：

    • 表达式通常是属性遍历与可拼接运算符的组合。 您可以使用 `AND` 和 `OR` 组合属性表达式。 此外，属性表达式还支持诸如 `Between`、`LessThan`、`GreaterThan` 和 `Like` 等运算符。 支持的运算符可能因数据存储而异，请查阅相应的参考文档部分。

    • 方法解析器支持为单个属性设置IgnoreCase标志（例如findByLastnameIgnoreCase(…)），或为所有支持忽略大小写的类型的所有属性设置该标志（通常是String实例——例如findByLastnameAndFirstnameAllIgnoreCase(…)）。 是否支持忽略大小写可能因存储而异，因此请查阅相关存储的特定查询方法的参考文档中的相应部分。

    • 您可以通过在查询方法中附加引用属性的 `OrderBy` 子句，并提供排序方向（`Asc` 或 `Desc`）来应用静态排序。 要创建支持动态排序的查询方法，请参阅“分页、迭代大量结果、排序与限制"。

    保留方法名

    虽然派生仓库方法通过名称绑定到属性，但在针对标识符（identifier）属性的某些从基础仓库继承的方法名上存在例外情况。这些保留方法（例如 CrudRepository#findById 或简写为 findById）将始终针对标识符属性，而不管声明方法中实际使用的属性名称是什么。

    考虑以下域类型，它包含一个通过 @Id 标记为标识符的属性 pk，以及一个名为 id 的属性。 在这种情况下，您需要特别注意查找方法的命名，因为它们可能与预定义的签名发生冲突：

    class User {
  @Id Long pk;                          (1)

  Long id;                              (2)

  // …
}

interface UserRepository extends Repository<User, Long> {

  Optional<User> findById(Long id);     (3)

  Optional<User> findByPk(Long pk);     (4)

  Optional<User> findUserById(Long id); (5)
}
    1 标识符属性（主键）。
    2 一个名为 id 的属性，但不是标识符。
    3 针对 pk 属性（即标记有 @Id 且被视为标识符的属性），因为它引用的是 CrudRepository 基础仓库方法。因此，它不是基于 id 作为属性名所暗示的派生查询，而是属于保留方法之一。
    4 通过名称针对 pk 属性，因为这是一个派生查询。
    5 通过在 find 和 by 之间使用描述性标记来针对 id 属性，以避免与保留方法发生冲突。

    这种特殊行为不仅针对查找方法，同样适用于 exists 和 delete 方法。有关方法的列表，请参阅“仓库查询关键字"。

    属性表达式

    属性表达式只能引用托管实体的直接属性，如前例所示。 在查询创建时，您已确保解析的属性是托管领域类的属性。 然而，您也可以通过遍历嵌套属性来定义约束条件。 请考虑以下方法签名：

    List<Person> findByAddressZipCode(ZipCode zipCode);

    假设一个Person拥有一个包含ZipCode的Address。在这种情况下，该方法会创建x.address.zipCode属性遍历。解析算法首先将整个部分（AddressZipCode）解释为属性，并检查领域类中是否存在同名（未首字母大写）的属性。如果算法成功找到该属性，则使用它；否则，算法将从右侧按驼峰命名法将源字符串拆分为头部和尾部，并尝试查找对应的属性——在本例中即为AddressZip和Code。如果算法找到了具有该头部的属性，它将取尾部并继续从该处向下构建树结构，按照上述方式拆分尾部。如果第一次拆分不匹配，算法则将拆分点向左移动（Address, ZipCode）并继续尝试。

    虽然这在大多数情况下是可行的，但算法仍有可能选择错误的属性。 假设 `Person` 类还有一个 `addressZip` 属性。 算法会在第一次拆分轮次中匹配到该属性并错误地选中它，从而导致失败（因为 `addressZip` 的类型可能没有 `code` 属性）。

    要解决此歧义，您可以在方法名中使用 `_` 来手动定义遍历点。因此，我们的方法名如下：

    List<Person> findByAddress_ZipCode(ZipCode zipCode);

    由于我们将下划线（_）视为保留字符，因此强烈建议遵循标准的 Java 命名规范（即不在属性名中使用下划线，而是采用驼峰命名法）。
    以下划线开头的字段名：

    字段名称可以以下划线开头，例如 String _name。 请确保保留 _ 作为前缀（如 _name），并使用双下划线 _ 来分隔嵌套路径，例如 user__name。

    大写字段名：

    全大写的字段名可直接使用。 如适用，嵌套路径需通过 `_` 进行拆分，例如 `USER_name`。

    第二个字母为大写的字段名：

    由小写字母开头后跟大写字母的字段名（如String qCode）可以通过使用两个大写字母开头的方式解析，例如QCode。请注意潜在的路径歧义问题。

    路径歧义：

    在以下示例中，属性 qCode 和 q（其中 q 包含一个名为 code 的属性）的排列方式，会导致路径 QCode 产生歧义。

    record Container(String qCode, Code q) {}
record Code(String code) {}

    由于属性直接匹配会被优先考虑，因此不会考虑任何潜在的嵌套路径，算法将选择qCode字段。 若要选择q中的code字段，则必须使用下划线表示法Q_Code。

    返回集合或可迭代对象的 Repository 方法

    返回多个结果的查询方法可以使用标准的 Java `Iterable`、`List` 和 `Set`。 除此之外，我们还支持返回 Spring Data 的 `Streamable`（这是 `Iterable` 的自定义扩展），以及由 Vavr 提供的集合类型。 请参阅附录中关于所有可能的查询方法返回类型的说明：查询方法返回类型参考。

    将 Streamable 用作查询方法的返回类型

    您可以使用 Streamable 作为 Iterable 或任何集合类型的替代方案。它提供了访问非并行 Stream 的便捷方法（这是 Iterable 所缺失的），并支持直接对元素执行 ….filter(…) 和 ….map(…) 操作，同时能够将 Streamable 与其他流进行拼接：

    使用 Streamable 组合查询方法的结果
    interface PersonRepository extends Repository<Person, Long> {
  Streamable<Person> findByFirstnameContaining(String firstname);
  Streamable<Person> findByLastnameContaining(String lastname);
}

Streamable<Person> result = repository.findByFirstnameContaining("av")
  .and(repository.findByLastnameContaining("ea"));

    返回自定义可流式包装类型

    为集合提供专用包装类型是一种常用模式，用于为返回多个元素的查询结果提供 API。 通常，这些类型通过调用返回集合样式的类型的仓库方法，并手动创建包装类型的实例来使用。 您可以避免这一额外步骤，因为 Spring Data 允许在满足以下条件时将这些包装类型用作查询方法的返回类型：

    1. 该类型实现了Streamable。

    2. 该类型暴露了一个构造函数或名为 `of(…)` 或 `valueOf(…)` 的静态工厂方法，该方法接受一个 `Streamable` 类型的参数。

    以下列表展示了一个示例：

    class Product {                                         (1)
  MonetaryAmount getPrice() { … }
}

@RequiredArgsConstructor(staticName = "of")
class Products implements Streamable<Product> {         (2)

  private final Streamable<Product> streamable;

  public MonetaryAmount getTotal() {                    (3)
    return streamable.stream()
      .map(Product::getPrice)
      .reduce(Money.of(0), MonetaryAmount::add);
  }


  @Override
  public Iterator<Product> iterator() {                 (4)
    return streamable.iterator();
  }
}

interface ProductRepository extends Repository<Product, Long> {
  Products findAllByDescriptionContaining(String text); (5)
}
    1 一个 Product 实体，提供 API 以访问产品价格。
    2 一种用于 Streamable<Product> 的包装类型，可通过使用 Products.of(…)（由 Lombok 注解创建的工厂方法）构建。采用接受 Streamable<Product> 的标准构造函数亦可。
    3 该包装类型提供额外的 API，可在 Streamable<Product> 上计算新值。
    4 实现 Streamable 接口，并将调用委托给实际结果。
    5 该包装类型 Products 可直接用作查询方法的返回类型。无需返回 Streamable<Product> 并在存储库客户端中手动将其包装。

    Vavr 集合支持

    Vavr 是一个在 Java 中拥抱函数式编程概念的库。 它提供了一组自定义的集合类型，可作为查询方法的返回类型使用，如下表所示：

    Vavr 集合类型 使用的 Vavr 实现类型 有效的 Java 源类型

    io.vavr.collection.Seq

    io.vavr.collection.List

    java.util.Iterable

    io.vavr.collection.Set

    io.vavr.collection.LinkedHashSet

    java.util.Iterable

    io.vavr.collection.Map

    io.vavr.collection.LinkedHashMap

    java.util.Map

    您可以使用第一列（或其子类型）中的类型作为查询方法的返回类型，并根据实际查询结果（第三列）的 Java 类型，将第二列中的类型用作实现类型。 或者，您也可以声明 `Traversable`（Vavr 中 `Iterable` 的等价类型），然后从实际的返回值推导出实现类。也就是说，`java.util.List` 会被转换为 Vavr 的 `List` 或 `Seq`，`java.util.Set` 会转换为 Vavr 的 `LinkedHashSet` `Set`，依此类推。

    流式查询结果

    您可以使用 `Stream<T>` 作为返回类型，以增量方式处理查询方法的结果。 与将查询结果包装在 `Stream` 中不同，数据源特定的方法用于执行流式处理，如下例所示：

    使用 Java 8 的 `Stream<T>` 流式处理查询结果。
    @Query("select u from User u")
Stream<User> findAllByCustomQueryAndStream();

Stream<User> readAllByFirstnameNotNull();

@Query("select u from User u")
Stream<User> streamAllPaged(Pageable pageable);
    Stream 可能封装了底层数据存储特定的资源，因此在使用后必须关闭。您可以使用 close() 方法手动关闭 Stream，或者使用 try-with-resources 块进行关闭，如下例所示：
    在 `try-with-resources` 块中使用 `Stream<T>`。
    try (Stream<User> stream = repository.findAllByCustomQueryAndStream()) {
  stream.forEach(…);
}
    并非所有的 Spring Data 模块当前都支持将 Stream<T> 作为返回类型。

    异步查询结果

    您可以使用Spring 的异步方法执行能力来异步运行存储库查询。这意味着方法在调用后会立即返回，而实际的查询将在提交给 Spring TaskExecutor 的任务中执行。异步查询与响应式查询不同，不应混合使用。有关响应式支持的更多详细信息，请参阅特定存储器的文档。以下示例展示了多种异步查询：

    @Async
Future<User> findByFirstname(String firstname);               (1)

@Async
CompletableFuture<User> findOneByFirstname(String firstname); (2)
    1 使用 java.util.concurrent.Future 作为返回类型。
    2 使用 java.util.concurrent.CompletableFuture 作为返回类型。

    分页、遍历大量结果、排序与限制

    要在查询中处理参数，请按照前面示例中所示定义方法参数。 此外，基础设施还识别某些特定类型（如Pageable、Sort和Limit），以便动态地为查询应用分页、排序和限制功能。 以下示例展示了这些功能：

    在查询方法中使用 `Pageable`、`Slice`、`Sort` 和 `Limit`。
    Page<User> findByLastname(String lastname, Pageable pageable);

Slice<User> findByLastname(String lastname, Pageable pageable);

List<User> findByLastname(String lastname, Sort sort);

List<User> findByLastname(String lastname, Sort sort, Limit limit);

List<User> findByLastname(String lastname, Pageable pageable);
    接受 Sort、Pageable 和 Limit 的 API 期望传入非 null 值。如果您不想应用任何排序或分页，请使用 Sort.unsorted()、Pageable.unpaged() 和 Limit.unlimited()。

    第一种方法允许您将一个 `org.springframework.data.domain.Pageable` 实例传递给查询方法，从而为静态定义的查询动态添加分页功能。 `Page` 对象了解可用的元素总数和页面总数。这是通过基础设施触发计数查询来计算总体数量来实现的。由于这可能成本较高（具体取决于所使用的存储），您可以改为返回一个 `Slice`。 `Slice` 仅知道是否存在下一个 `Slice`，这在遍历较大的结果集时可能已足够。

    排序选项同样通过Pageable实例进行处理。 如果您仅需排序功能，只需在方法中添加一个org.springframework.data.domain.Sort参数即可。 如您所见，返回一个List也是可行的。 在这种情况下，构建实际Page实例所需的额外元数据不会被创建（这也意味着原本必要的额外计数查询将不会被执行）。 相反，它会将查询限制为仅检索指定范围内的实体。

    要获取整个查询的总页数，您需要触发额外的计数查询。默认情况下，该查询是基于您实际触发的查询生成的。

    特殊参数在查询方法中只能使用一次。
    上述部分特殊参数互斥。 请考虑以下无效参数组合列表。

    Parameters Example Reason

    Pageable and Sort

    findBy…​(Pageable page, Sort sort)

    `Pageable` 已经定义了 `Sort`

    Pageable and Limit

    findBy…​(Pageable page, Limit limit)

    Pageable 已定义了限制。

    `Top` 关键字可与 `Pageable` 一起使用：`Top` 定义结果的最大总数，而 `Pageable` 参数可进一步减少该数量。

    哪种方法更合适？

    Spring Data 抽象所提供的价值，或许最好通过下表所示的查询方法可能返回的类型来体现。 该表展示了可以从查询方法中返回哪些类型。

    表 1。消耗大量查询结果
    方法 获取的数据量 查询结构 约束条件

    List<T>

    所有结果。

    单个查询。

    查询结果可能会耗尽所有内存。获取全部数据可能需要耗费大量时间。

    Streamable<T>

    所有结果。

    单个查询。

    查询结果可能会耗尽所有内存。获取全部数据可能需要耗费大量时间。

    Stream<T>

    分块（逐个或分批），具体取决于对 `Stream` 的消费方式。

    通常使用游标执行单个查询。

    使用后必须关闭流，以避免资源泄漏。

    Flux<T>

    分块（逐个或分批），具体取决于Flux的消耗方式。

    通常使用游标执行单个查询。

    存储模块必须提供响应式基础设施。

    Slice<T>

    Pageable.getPageSize() + 1 at Pageable.getOffset()

    执行一对多查询以获取数据，起始位置为Pageable.getOffset()，并应用限制。

    一个 `Slice` 只能导航到下一个 `Slice`。

    • Slice 提供详细信息，说明是否还有更多数据需要获取。

    • 当偏移量过大时，基于偏移的查询会变得低效，因为数据库仍然需要生成完整的结果集。

    Page<T>

    Pageable.getPageSize() at Pageable.getOffset()

    从 `Pageable.getOffset()` 开始的一对多查询应用了限制。此外，可能需要执行 `COUNT(…)` 查询以确定元素总数。

    很多时候，需要执行代价高昂的COUNT(…)查询。

    • 当偏移量过大时，基于偏移的查询会变得低效，因为数据库仍然需要生成完整的结果集。

    分页与排序

    您可以使用属性名称定义简单的排序表达式。 您可以连接多个表达式，将多个条件合并为一个表达式。

    定义排序表达式
    Sort sort = Sort.by("firstname").ascending()
  .and(Sort.by("lastname").descending());

    若要采用更类型安全的方式定义排序表达式，请首先指定要定义排序表达式的类型，然后使用方法引用来定义用于排序的属性。

    使用类型安全 API 定义排序表达式
    TypedSort<Person> person = Sort.sort(Person.class);

Sort sort = person.by(Person::getFirstname).ascending()
  .and(person.by(Person::getLastname).descending());
    TypedSort.by(…) 使用运行时代理（通常通过 CGLib 实现），这在使用 GraalVM Native Image 等工具进行原生镜像编译时可能会产生干扰。

    如果您的商店实现支持 Querydsl，您还可以使用生成的元模型类型来定义排序表达式：

    使用 Querydsl API 定义排序表达式
    QSort sort = QSort.by(QPerson.firstname.asc())
  .and(QSort.by(QPerson.lastname.desc()));

    限制查询结果

    除了分页，还可以使用专用的 Limit 参数来限制结果集大小。 您也可以通过在查询方法中使用 First 或 Top 关键字来限制结果集，这两个关键字可以互换使用，但不能与 Limit 参数混用。 您可以在 Top 或 First 后附加一个可选的数值，以指定要返回的最大结果集大小。 如果省略该数值，则默认假设结果集大小为 1。 以下示例展示了如何限制查询结果的大小：

    使用 Top 和 First 限制查询结果的大小
    List<User> findByLastname(String lastname, Limit limit);

User findFirstByOrderByLastnameAsc();

User findTopByLastnameOrderByAgeDesc(String lastname);

Page<User> queryFirst10ByLastname(String lastname, Pageable pageable);

Slice<User> findTop3By(Pageable pageable);

List<User> findFirst10ByLastname(String lastname, Sort sort);

List<User> findTop10ByLastname(String lastname, Pageable pageable);

    限制表达式同样支持对支持 DISTINCT 查询的数据存储使用Distinct关键字。此外，对于将结果集限制为单个实例的查询，支持使用Optional关键字将结果包装起来。

    如果针对限制查询的排序或切片操作（以及可用页面数量的计算）被应用，则这些操作将在限定结果内部执行。

    通过结合使用 Sort 参数对结果进行动态排序，您可以表达查询“K 个最小”以及“K 个最大”元素的方法。
