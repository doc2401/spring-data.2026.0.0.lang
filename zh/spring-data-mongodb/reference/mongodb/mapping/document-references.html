    使用 DBRefs

    映射框架无需存储嵌入在文档中的子对象。 您也可以将它们单独存储，并使用 `DBRef` 引用该文档。 当从 MongoDB 加载对象时，这些引用会被急切解析，从而返回一个与直接嵌入在顶层文档中时外观相同的映射对象。

    以下示例使用 DBRef 引用一个独立于其所在对象之外的特定文档（为简洁起见，此处同时展示了两个类）：

    @Document
public class Account {

  @Id
  private ObjectId id;
  private Float total;
}

@Document
public class Person {

  @Id
  private ObjectId id;
  @Indexed
  private Integer ssn;
  @DBRef
  private List<Account> accounts;
}

    您无需使用 `@OneToMany` 或类似的机制，因为对象列表本身已告知映射框架存在一对多关系。 当对象存储于 MongoDB 时，其中包含的是 DBRefs 列表，而非 `Account` 对象本身。 在处理 `DBRef` 集合的加载时，建议将集合类型中持有的引用限制为特定的 MongoDB 集合。 这样做可以批量加载所有引用；而指向不同 MongoDB 集合的引用则需逐个解析。

    映射框架不支持级联保存。 如果您修改了被 Person 对象引用的 Account 对象，则必须单独保存该 Account 对象。 对 Person 对象调用 save 方法不会自动保存 accounts 属性中的 Account 对象。

    DBRef 也可以采用惰性解析。在这种情况下，实际的对象或引用集合会在首次访问该属性时进行解析。请使用 @DBRef 的 lazy 属性来指定此行为。那些同样被定义为惰性加载 DBRef 且用作构造函数参数的必需属性，也会被惰性加载代理所装饰，从而确保对数据库和网络的负载尽可能小。

    懒加载的 DBRef 可能难以调试。请确保工具不会意外触发代理解析，例如通过调用 toString() 或某些内联调试渲染调用的属性获取器。建议为 org.springframework.data.mongodb.core.convert.DefaultDbRefResolver 启用 trace 日志记录，以深入了解 DBRef 的解析过程。
    虽然技术上可行，但应避免保存通过引用根对象的属性获取到的单个懒加载实体。
    懒加载可能需要类代理，而后者可能需要访问 JDK 内部机制。自 Java 16+ 起，由于JEP 396：默认强封装 JDK 内部机制，这些内部机制不再开放。 对于此类情况，请考虑回退到接口类型（例如，将ArrayList改为List），或提供所需的--add-opens参数。

    使用文档引用

    使用@DocumentReference提供了一种灵活的方式来引用 MongoDB 中的实体。虽然其目标与使用DBRefs相同，但存储表示形式有所不同。DBRef会解析为具有固定结构的文档，该结构在MongoDB 参考文档中有详细说明。
    文档引用并不遵循特定格式。它们可以是任何内容：单个值、整个文档，基本上是可以存储在 MongoDB 中的任何东西。默认情况下，映射层将使用被引用实体的id值进行存储和检索，如下面的示例所示。

    @Document
class Account {

  @Id
  String id;
  Float total;
}

@Document
class Person {

  @Id
  String id;

  @DocumentReference                                   (1)
  List<Account> accounts;
}
    Account account = …

template.insert(account);                               (2)

template.update(Person.class)
  .matching(where("id").is(…))
  .apply(new Update().push("accounts").value(account)) (3)
  .first();
    {
  "_id" : …,
  "accounts" : [ "6509b9e" … ]                        (4)
}
    1 标记要引用的 Account 值集合。
    2 映射框架不处理级联保存，因此请确保单独持久化引用的实体。
    3 将引用添加到现有实体中。
    4 引用的 Account 实体表示为其 _id 值的数组。

    上面的示例使用基于 `_id` 的获取查询（`{ '_id' : ?#{#target} }`）进行数据检索，并急切解析关联实体。 可以使用 `@DocumentReference` 的属性来更改解析默认值（如下所列）。

    表 1。@DocumentReference 默认值
    Attribute Description Default

    db

    用于集合查找的目标数据库名称。

    MongoDatabaseFactory.getMongoDatabase()

    collection

    目标集合名称。

    注释属性的域类型，对于类似Collection或Map的属性分别为值类型和集合名称。

    lookup

    使用 SpEL 表达式通过 `#target` 作为标记来评估占位符的单文档查找查询。`Collection` 类型或 `Map` 类型的属性会通过 `$or` 操作符组合单个查找结果。

    基于加载的源值使用 `_id` 字段的查询（`{ '_id' : ?#{#target} }`）。

    sort

    用于在服务器端对结果文档进行排序。

    默认情况下无结果。 对于类似 `Collection` 的属性，其结果顺序将基于所使用的查找查询尽力恢复。

    lazy

    如果设置为 `true`，则首次访问该属性时值解析会被延迟。

    默认情况下，急切地解析属性。
    懒加载可能需要类代理，而后者又可能需要访问 JDK 内部机制。自 Java 16+ 起，由于JEP 396：默认强封装 JDK 内部机制，这些内部机制不再开放。 对于此类情况，请考虑回退到接口类型（例如，将ArrayList替换为List），或提供所需的--add-opens参数。

    @DocumentReference(lookup) 允许定义不同于 _id 字段的过滤查询，从而提供了一种灵活的方式来定义实体间的引用关系，如下面的示例所示：书籍的 Publisher 通过其缩写而非内部 id 进行引用。

    @Document
class Book {

  @Id
  ObjectId id;
  String title;
  List<String> author;

  @Field("publisher_ac")
  @DocumentReference(lookup = "{ 'acronym' : ?#{#target} }") (1)
  Publisher publisher;
}

@Document
class Publisher {

  @Id
  ObjectId id;
  String acronym;                                            (1)
  String name;

  @DocumentReference(lazy = true)                            (2)
  List<Book> books;

}
    Book document
    {
  "_id" : 9a48e32,
  "title" : "The Warded Man",
  "author" : ["Peter V. Brett"],
  "publisher_ac" : "DR"
}
    Publisher document
    {
  "_id" : 1a23e45,
  "acronym" : "DR",
  "name" : "Del Rey",
  …
}
    1 使用 acronym 字段查询 Publisher 集合中的实体。
    2 懒加载回指到 Book 集合的引用。

    上述片段展示了在处理自定义引用对象时的读取方面。写入则需要一些额外的设置，因为映射信息并未表达#target的来源。映射层需要在目标文档与DocumentPointer之间注册一个Converter转换器，如下所示：

    @WritingConverter
class PublisherReferenceConverter implements Converter<Publisher, DocumentPointer<String>> {

	@Override
	public DocumentPointer<String> convert(Publisher source) {
		return () -> source.getAcronym();
	}
}

    如果未提供 `DocumentPointer` 转换器，则可以根据给定的查找查询计算目标引用文档。 在这种情况下，关联目标属性的评估方式如下所示的示例中展示。

    @Document
class Book {

  @Id
  ObjectId id;
  String title;
  List<String> author;

  @DocumentReference(lookup = "{ 'acronym' : ?#{acc} }") (1) (2)
  Publisher publisher;
}

@Document
class Publisher {

  @Id
  ObjectId id;
  String acronym;                                        (1)
  String name;

  // ...
}
    {
  "_id" : 9a48e32,
  "title" : "The Warded Man",
  "author" : ["Peter V. Brett"],
  "publisher" : {
    "acc" : "DOC"
  }
}
    1 使用 acronym 字段查询 Publisher 集合中的实体。
    2 查找查询的字段值占位符（如 acc）用于构建引用文档。

    同样，可以通过组合使用@ReadonlyProperty和@DocumentReference来建模关系型风格的一对多（One-To-Many）引用。这种方法允许在引用文档中存储链接值，而不是在拥有文档中存储，如下面的示例所示。

    @Document
class Book {

  @Id
  ObjectId id;
  String title;
  List<String> author;

  ObjectId publisherId;                                        (1)
}

@Document
class Publisher {

  @Id
  ObjectId id;
  String acronym;
  String name;

  @ReadOnlyProperty                                            (2)
  @DocumentReference(lookup="{'publisherId':?#{#self._id} }")  (3)
  List<Book> books;
}
    Book document
    {
  "_id" : 9a48e32,
  "title" : "The Warded Man",
  "author" : ["Peter V. Brett"],
  "publisherId" : 8cfb002
}
    Publisher document
    {
  "_id" : 8cfb002,
  "acronym" : "DR",
  "name" : "Del Rey"
}
    1 通过将 Publisher.id 存储在 Book 文档中，建立从 Book（引用方）到 Publisher（所有者）的链接。
    2 将存储引用的属性标记为只读。 这可以防止在 Publisher 文档中存储对单个 Book 的引用。
    3 使用 #self 变量访问 Publisher 文档内的值，并在此检索具有匹配 publisherId 的 Books。

    在以上条件具备的情况下，可以对实体之间的各种关联进行建模。请查看下方非穷尽的示例列表，以了解其可能性。

    示例 1：使用 id 字段进行简单文档引用
    class Entity {
  @DocumentReference
  ReferencedObject ref;
}
    // entity
{
  "_id" : "8cfb002",
  "ref" : "9a48e32" (1)
}

// referenced object
{
  "_id" : "9a48e32" (1)
}
    1 简单的 MongoDB 类型无需进一步配置即可直接使用。
    示例 2：使用显式查询的 `id` 字段进行简单文档引用
    class Entity {
  @DocumentReference(lookup = "{ '_id' : '?#{#target}' }") (1)
  ReferencedObject ref;
}
    // entity
{
  "_id" : "8cfb002",
  "ref" : "9a48e32"                                        (1)
}

// referenced object
{
  "_id" : "9a48e32"
}
    1 target 定义参考值本身。
    示例 3：从文档引用中提取 `refKey` 字段以用于查找查询。
    class Entity {
  @DocumentReference(lookup = "{ '_id' : '?#{refKey}' }")  (1) (2)
  private ReferencedObject ref;
}
    @WritingConverter
class ToDocumentPointerConverter implements Converter<ReferencedObject, DocumentPointer<Document>> {
	public DocumentPointer<Document> convert(ReferencedObject source) {
		return () -> new Document("refKey", source.id);    (1)
	}
}
    // entity
{
  "_id" : "8cfb002",
  "ref" : {
    "refKey" : "9a48e32"                                   (1)
  }
}

// referenced object
{
  "_id" : "9a48e32"
}
    1. 用于获取参考值的关键字必须与写入时使用的关键字相同。 2. `refKey` 是 `target.refKey` 的简写。
    示例 4：具有多个值以形成查找查询的文档引用
    class Entity {
  @DocumentReference(lookup = "{ 'firstname' : '?#{fn}', 'lastname' : '?#{ln}' }") (1) (2)
  ReferencedObject ref;
}
    // entity
{
  "_id" : "8cfb002",
  "ref" : {
    "fn" : "Josh",           (1)
    "ln" : "Long"            (1)
  }
}

// referenced object
{
  "_id" : "9a48e32",
  "firstname" : "Josh",      (2)
  "lastname" : "Long",       (2)
}
    1 根据查找查询，从关联文档中读取或写入键 fn 和 ln。
    2 使用非 id 字段来查找目标文档。
    示例 5：从目标集合中读取文档引用
    class Entity {
  @DocumentReference(lookup = "{ '_id' : '?#{id}' }", collection = "?#{collection}") (2)
  private ReferencedObject ref;
}
    @WritingConverter
class ToDocumentPointerConverter implements Converter<ReferencedObject, DocumentPointer<Document>> {
	public DocumentPointer<Document> convert(ReferencedObject source) {
		return () -> new Document("id", source.id)                                   (1)
                           .append("collection", … );                                (2)
	}
}
    // entity
{
  "_id" : "8cfb002",
  "ref" : {
    "id" : "9a48e32",                                                                (1)
    "collection" : "…"                                                               (2)
  }
}
    1 从引用文档中读取/写入键 _id，以便在查找查询中使用它们。
    2 可以使用其键从引用文档中读取集合名称。

    我们明白，在查找查询中使用各种 MongoDB 查询操作符很有吸引力，这本身并无不妥。但以下几点值得考虑：

    • 确保建立适当的索引以支持您的查找操作。

    • 确保使用相同的数据类型：@DocumentReference(lookup="{'someRef':?#{#self._id} }") 在使用 @Id String id 和 String someRef 时很容易失败，因为 String @Id 会进行自动的 ObjectId 转换（但其他包含 ObjectId.toString() 的 String 属性则不会）。引用查找使用的是结果 Document 中的值，在这种情况下，它将使用 ObjectId 查询一个 String 字段，从而导致无结果。

    • 请注意，解析需要服务器往返通信从而引入延迟，因此请考虑采用惰性策略。

    • 使用 `$or` 运算符批量加载文档引用集合。
      内存中会尽最大努力恢复原始元素顺序。 仅在使用相等表达式时才能恢复顺序，无法在使用 MongoDB 查询运算符时恢复。 在此情况下，结果将按照从存储接收的顺序或通过提供的 `@DocumentReference(sort)` 属性指定的顺序排列。

    再补充几点一般性说明：

    • 您是否使用了循环引用？ 请自问是否需要它们。

    • 懒加载的文档引用难以调试。请确保工具不会意外触发代理解析，例如通过调用 `toString()` 的方式。
      虽然技术上可行，但应避免保存通过引用根的属性获取到的单个懒加载实体。

    • 不支持使用响应式基础设施读取文档引用。
