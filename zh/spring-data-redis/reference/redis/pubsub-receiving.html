    订阅（接收消息）

    在接收端，用户可以通过直接命名或采用模式匹配的方式订阅一个或多个频道。后一种方法非常实用，因为它不仅允许通过一条命令创建多个订阅，还可以监听在订阅时尚未创建的频道（只要它们符合指定的模式）。

    在底层，RedisConnection 提供了 subscribe 和 pSubscribe 方法，分别对应通过频道或模式订阅的 Redis 命令。请注意，这些方法可以接受多个频道或模式作为参数。若要更改连接的订阅状态或查询其是否正在监听，RedisConnection 提供了 getSubscription 和 isSubscribed 方法。

    Spring Data Redis 中的订阅命令是阻塞的。也就是说，在连接上调用 subscribe 会导致当前线程阻塞，因为它开始等待消息。只有当订阅被取消时，该线程才会被释放，而这种情况发生在另一个线程对相同的连接调用了 unsubscribe 或 pUnsubscribe 时。有关此问题的解决方案，请参阅本文档稍后部分的“消息监听器容器”。

    如前所述，订阅后连接将开始等待消息。 仅允许添加新订阅、修改现有订阅以及取消现有订阅的命令。 调用除subscribe、pSubscribe、unsubscribe或pUnsubscribe之外的任何内容都会抛出异常。

    要订阅消息，需要实现 `MessageListener` 回调接口。每当有新消息到达时，该回调就会被调用，并通过 `onMessage` 方法执行用户代码。此接口不仅提供对实际消息的访问，还提供接收消息的通道以及订阅用于匹配该通道的模式（如果有）。这些信息使得调用方不仅能根据内容区分不同的消息，还能通过检查其他详细信息来进行判断。

    消息监听器容器

    由于其阻塞特性，低级订阅并不吸引人，因为每个监听器都需要进行连接和线程管理。 为缓解这一问题，Spring Data 提供了 `RedisMessageListenerContainer`，它负责处理所有繁重的工作。 如果您熟悉 EJB 和 JMS，您会发现这些概念非常熟悉，因为该设计尽可能贴近 Spring Framework 的支持及其消息驱动 POJO（MDP）。

    RedisMessageListenerContainer 充当消息监听容器。它用于从 Redis 频道接收消息，并驱动注入到其中的 MessageListener 实例。该监听容器负责消息接收的所有线程管理以及向监听器分发消息以供处理。消息监听容器是 MDP（消息驱动进程）与消息提供者之间的中介，负责注册接收消息、资源的获取与释放、异常转换等工作。这使得应用程序开发者可以专注于编写（可能复杂的）与接收消息（并对此做出反应）相关的业务逻辑，而将冗余的 Redis 基础设施关注点委托给框架处理。

    `MessageListener` 还可以实现 `SubscriptionListener`，以便在订阅/取消订阅确认时接收通知。监听订阅通知在同步调用时非常有用。

    此外，为最小化应用占用空间，RedisMessageListenerContainer 允许多个监听器共享一个连接和一个线程，即使它们不共享订阅关系。因此，无论应用程序跟踪多少监听器或通道，其运行成本在整个生命周期中保持不变。此外，容器支持运行时配置更改，使您能够在应用程序运行时添加或删除监听器，而无需重启应用。另外，该容器采用懒订阅方式，仅在需要时才使用 RedisConnection。如果所有监听器都已取消订阅，将自动执行清理操作并释放线程。

    为了应对消息的异步特性，容器需要一个 `java.util.concurrent.Executor`（或 Spring 的 `TaskExecutor`）来分发这些消息。 根据负载情况、监听器数量或运行环境的不同，您应该调整或优化该执行器，以更好地满足您的需求。 特别是在托管环境（如应用服务器）中，强烈建议选择适当的 `TaskExecutor`，以便充分利用其运行时特性。

    MessageListenerAdapter

    `MessageListenerAdapter` 类是 Spring 异步消息支持中的最终组件。简而言之，它允许您将几乎任何类暴露为 MDP（尽管存在一些限制）。

    请考虑以下接口定义：

    public interface MessageDelegate {
  void handleMessage(String message);
  void handleMessage(Map message);
  void handleMessage(byte[] message);
  void handleMessage(Serializable message);
  // pass the channel/pattern as well
  void handleMessage(Serializable message, String channel);
 }

    请注意，尽管该接口并未扩展 `MessageListener` 接口，但通过使用 `MessageListenerAdapter` 类，它仍然可以作为 MDP 使用。 此外，请注意各种消息处理方法是根据它们能够接收和处理的各个 `Message` 类型的内容进行强类型定义的。 另外，可以向方法传递消息发送的通道或模式作为第二个类型为 `String` 的参数：

    public class DefaultMessageDelegate implements MessageDelegate {
  // implementation elided for clarity...
}
    Notice how the above implementation of the `MessageDelegate` interface (the above `DefaultMessageDelegate` class) has *no* Redis dependencies at all. It truly is a POJO that we make into an MDP with the following configuration:

    • Java

    • XML

    @Configuration
class MyConfig {

  // …

  @Bean
  DefaultMessageDelegate listener() {
    return new DefaultMessageDelegate();
  }

  @Bean
  MessageListenerAdapter messageListenerAdapter(DefaultMessageDelegate listener) {
    return new MessageListenerAdapter(listener, "handleMessage");
  }

  @Bean
  RedisMessageListenerContainer redisMessageListenerContainer(RedisConnectionFactory connectionFactory, MessageListenerAdapter listener) {

    RedisMessageListenerContainer container = new RedisMessageListenerContainer();
    container.setConnectionFactory(connectionFactory);
    container.addMessageListener(listener, ChannelTopic.of("chatroom"));
    return container;
  }
}

    监听器主题可以是频道（例如 topic="chatroom" 对应 Topic.channel("chatroom")）或模式（例如 topic="*room" 对应 Topic.pattern("*room")）。

    前面的示例使用 Redis 命名空间声明消息监听器容器，并自动将 POJO 注册为监听器。 完整的 Bean 定义如下：

    <bean id="messageListener" class="org.springframework.data.redis.listener.adapter.MessageListenerAdapter">
  <constructor-arg>
    <bean class="redisexample.DefaultMessageDelegate"/>
  </constructor-arg>
</bean>

<bean id="redisContainer" class="org.springframework.data.redis.listener.RedisMessageListenerContainer">
  <property name="connectionFactory" ref="connectionFactory"/>
  <property name="messageListeners">
    <map>
      <entry key-ref="messageListener">
        <bean class="org.springframework.data.redis.listener.ChannelTopic">
          <constructor-arg value="chatroom"/>
        </bean>
      </entry>
    </map>
  </property>
</bean>

    每次接收到消息时，适配器都会自动且透明地在低级格式与所需对象类型之间执行转换（使用配置的 RedisSerializer）。 方法调用引发的任何异常都会被容器捕获并处理（默认情况下，异常会被记录日志）。

    响应式消息监听器容器

    Spring Data 提供了 ReactiveRedisMessageListenerContainer，它负责为用户处理所有的转换和订阅状态管理繁重工作。

    消息监听器容器本身不需要外部线程资源。它使用驱动线程来发布消息。

    ReactiveRedisConnectionFactory factory = …
ReactiveRedisMessageListenerContainer container = new ReactiveRedisMessageListenerContainer(factory);

Flux<ChannelMessage<String, String>> stream = container.receive(ChannelTopic.of("my-channel"));

    要等待并确保正确订阅，您可以使用返回 `Mono<Flux<ChannelMessage>>` 的 `receiveLater` 方法。 由于已订阅给定主题，生成的 `Mono` 将完成并包含一个内部发布器。 通过拦截 `onNext` 信号，您可以同步服务器端的订阅。

    ReactiveRedisConnectionFactory factory = …
ReactiveRedisMessageListenerContainer container = new ReactiveRedisMessageListenerContainer(factory);

Mono<Flux<ChannelMessage<String, String>>> stream = container.receiveLater(ChannelTopic.of("my-channel"));

stream.doOnNext(inner -> // notification hook when Redis subscriptions are synchronized with the server)
    .flatMapMany(Function.identity())
    .…;

    通过模板 API 订阅

    如上所述，您可以直接使用ReactiveRedisTemplate来订阅频道或模式。这种方法提供了一种简单但有限的解决方案，因为您无法在初始订阅之后添加新的订阅。尽管如此，您仍然可以通过返回的Flux（例如使用take(Duration)）来控制消息流。读取完成、发生错误或取消操作时，所有绑定的资源都会被释放。

    redisTemplate.listenToChannel("channel1", "channel2").doOnNext(msg -> {
    // message processing ...
}).subscribe();
