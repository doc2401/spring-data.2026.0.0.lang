    实体建模

    本章介绍如何对实体进行建模，并解释其在 Couchbase Server 中的对应表示方式。

    对象映射基础

    本节涵盖 Spring Data 对象映射、对象创建、字段和属性访问以及可变性与不可变性的基础知识。请注意，本节仅适用于不使用底层数据存储（如 JPA）的对象映射的 Spring Data 模块。此外，请务必查阅针对特定存储器的章节，以了解特定于该存储器的对象映射内容，例如索引、自定义列或字段名称等。

    Spring Data 对象映射的核心职责是创建领域对象实例，并将存储原生的数据结构映射到这些对象上。 这意味着我们需要两个基本步骤：

    1. 通过暴露的构造函数之一创建实例。

    2. 实例化以呈现所有暴露的属性。

    对象创建

    Spring Data 会自动尝试检测持久化实体中用于实例化该类型对象的构造函数。 解析算法的工作方式如下：

    1. 如果存在一个带有@PersistenceCreator注解的单个静态工厂方法，则使用该方法。

    2. 如果只有一个构造函数，则使用它。

    3. 如果存在多个构造函数且其中恰好有一个被标注为@PersistenceCreator，则使用该构造函数。

    4. 如果类型是 Java 的Record，则使用规范构造函数。

    5. 如果有无参构造函数，则使用它。 其他构造函数将被忽略。

    值解析假设构造函数/工厂方法的参数名称与实体的属性名称相匹配，即解析过程将如同该属性正在被填充一样执行，包括所有映射自定义（如不同的数据存储列或字段名等）。此外，这还需要类文件中包含参数名称信息，或者在构造函数上存在 `@ConstructorProperties` 注解。

    可以通过使用 Spring Framework 的 `@Value` 注解配合特定于存储库的 SpEL 表达式来自定义值解析。有关更多详细信息，请参阅关于存储库特定映射的部分。

    对象创建的内部机制

    为避免反射带来的开销，Spring Data 默认使用在运行时生成的工厂类来创建对象，该工厂类将直接调用领域类的构造函数。 即对于此示例类型：

    class Person {
  Person(String firstname, String lastname) { … }
}

    我们将在运行时创建一个语义上与此工厂类等效的工厂类：

    class PersonObjectInstantiator implements ObjectInstantiator {

  Object newInstance(Object... args) {
    return new Person((String) args[0], (String) args[1]);
  }
}

    这为我们带来了比反射间接高出约 10% 的性能提升。 要使领域类符合此类优化条件，它需要遵守一组约束：

    • 它不能是私有类。

    • 它不能是非静态内部类。

    • 它不能是 CGLib 代理类。

    • Spring Data 所使用的构造函数不能是私有的。

    如果这些标准中的任何一项匹配，Spring Data 将通过反射回退到实体实例化。

    属性人口

    一旦创建了该实体实例，Spring Data 将填充该类中所有剩余的持久化属性。 除非这些属性已通过实体的构造函数（即通过其构造函数参数列表）进行填充，否则标识符属性将被首先填充，以便解析循环对象引用。 随后，对于尚未由构造函数填充的所有非瞬态属性，将在实体实例上进行设置。 为此，我们采用以下算法：

    1. 如果该属性是不可变的，但暴露了 `with…` 方法（见下文），我们使用 `with…` 方法来创建一个具有新属性值的新实体实例。

    2. 如果定义了属性访问（即通过 getter 和 setter 进行访问），我们将调用 setter 方法。

    3. 如果该属性是可变的，则直接设置该字段。

    4. 如果属性是不可变的，我们将使用构造函数（参见对象创建）来为持久化操作创建该实例的副本。

    5. 默认情况下，我们直接设置字段值。

    属性人口内部结构

    与我们在对象构建优化中采用的方式类似，我们也使用 Spring Data 运行时生成的访问器类来与实体实例进行交互。

    class Person {

  private final Long id;
  private String firstname;
  private @AccessType(Type.PROPERTY) String lastname;

  Person() {
    this.id = null;
  }

  Person(Long id, String firstname, String lastname) {
    // Field assignments
  }

  Person withId(Long id) {
    return new Person(id, this.firstname, this.lastname);
  }

  void setLastname(String lastname) {
    this.lastname = lastname;
  }
}
    生成的属性访问器
    class PersonPropertyAccessor implements PersistentPropertyAccessor {

  private static final MethodHandle firstname;              (2)

  private Person person;                                    (1)

  public void setProperty(PersistentProperty property, Object value) {

    String name = property.getName();

    if ("firstname".equals(name)) {
      firstname.invoke(person, (String) value);             (2)
    } else if ("id".equals(name)) {
      this.person = person.withId((Long) value);            (3)
    } else if ("lastname".equals(name)) {
      this.person.setLastname((String) value);              (4)
    }
  }
}
    1 PropertyAccessor 持有底层对象的可变实例，以便能够修改原本不可变的属性。
    2 默认情况下，Spring Data 使用属性访问方式来读写属性值。根据 private 字段的可见性规则，使用 MethodHandles 与字段进行交互。
    3 该类提供了一个 withId(…) 方法，用于设置标识符，例如当实例被插入数据存储且已生成标识符时。调用 withId(…) 会创建一个新的 Person 对象。随后的所有修改都将在新实例中进行，而不会改变之前的实例。
    4 使用属性访问允许直接调用方法，而无需使用 MethodHandles。

    这为我们带来了比反射间接提升约 25% 的性能。为了使领域类符合此类优化条件，它需要遵守一组约束：

    • 类型不得位于默认包或java包下。

    • 类型及其构造函数必须是public的。

    • 作为内部类的类型，必须是static的。

    • 所使用的 Java 运行时必须允许在源 ClassLoader 中声明类。Java 9 及更高版本施加了某些限制。

    默认情况下，Spring Data 尝试使用生成的属性访问器；如果检测到限制，则会回退到基于反射的访问器。

    让我们看看以下实体：

    示例实体
    class Person {

  private final @Id Long id;                                                (1)
  private final String firstname, lastname;                                 (2)
  private final LocalDate birthday;
  private final int age;                                                    (3)

  private String comment;                                                   (4)
  private @AccessType(Type.PROPERTY) String remarks;                        (5)
  private @Transient String summary;                                        (6)

  static Person of(String firstname, String lastname, LocalDate birthday) { (7)

    return new Person(null, firstname, lastname, birthday,
      Period.between(birthday, LocalDate.now()).getYears());
  }

  Person(Long id, String firstname, String lastname, LocalDate birthday, int age) { (7)

    this.id = id;
    this.firstname = firstname;
    this.lastname = lastname;
    this.birthday = birthday;
    this.age = age;
  }

  Person withId(Long id) {                                                  (1)
    return new Person(id, this.firstname, this.lastname, this.birthday, this.age);
  }

  void setRemarks(String remarks) {                                         (5)
    this.remarks = remarks;
  }
}
    1 标识符属性为 final 类型，但在构造函数中被设置为 null。该类提供了一个 withId(…) 方法用于设置标识符，例如当实例被插入数据存储且已生成标识符时。原始的 Person 实例保持不变，因为会创建一个新的实例。通常会对其他需要持久化操作但可能发生变更的存储管理属性应用相同的模式。wither 方法是可选的，因为持久化构造函数（见第 6 点）本质上是一个拷贝构造函数，设置该属性将被转换为创建一个新实例并将新的标识符值应用其中。
    2 firstname 和 lastname 属性是普通的不可变属性，可能通过 getter 方法暴露。
    3 age 属性是不可变的，但它是从 birthday 属性派生而来的。按照所示的设计，数据库值将优于默认值，因为 Spring Data 仅使用声明的构造函数。即使意图是优先采用计算结果，也重要的是该构造函数必须包含 age 作为参数（以便可能忽略它），否则属性填充步骤将尝试设置 age 字段，但由于其不可变且不存在 with… 方法而失败。
    4 comment 属性是可变的，通过直接设置其字段进行填充。
    5 remarks 属性是可变的，通过调用 setter 方法进行填充。
    6 summary 属性是瞬态的，不会被持久化，因为它被标注为 @Transient。Spring Data 不使用 Java 的 transient 关键字来排除属性的持久化，因为 transient 是 Java 序列化框架的一部分。请注意，该属性可以与持久化构造函数一起使用，但其值将默认为 null（如果属性类型是基本类型，则为其相应的基本类型初始值）。
    7 该类提供了一个工厂方法和一个用于对象创建的构造函数。这里的核心理念是使用工厂方法而不是额外的构造函数，以避免通过 @PersistenceCreator 进行构造函数消歧的需要。相反，属性的默认值处理在工厂方法内部完成。如果您希望 Spring Data 使用工厂方法进行对象实例化，请将其标注为 @PersistenceCreator。

    一般建议

    • 尽量使用不可变对象——创建不可变对象非常简单，只需调用其构造函数即可完成对象的实例化。此外，这还能避免在领域对象中散布允许客户端代码修改对象状态的 setter 方法。如果确实需要这些方法，建议将其设为包级私有（package protected），以便仅由有限的同包类型调用。仅通过构造函数进行对象实例化的速度比通过属性赋值快高达 30%。

    • 提供一个全参构造函数——即使您无法或不愿将实体建模为不可变值，提供接受实体所有属性（包括可变属性）作为参数的构造函数仍然具有价值，因为这允许对象映射跳过属性填充过程，从而实现最佳性能。

    • 使用工厂方法而非重载构造函数，以避免使用 @PersistenceCreator——由于全参构造函数对于最佳性能是必需的，我们通常希望暴露更多针对特定应用程序用例的构造函数，这些构造函数会省略诸如自动生成的标识符等内容。 采用静态工厂方法来暴露全参构造函数的各种变体，是一种成熟的模式。

    • 确保遵守相关约束，以便生成的实例化器和属性访问器类能够被使用。

    • 若要生成标识符，仍需使用最终字段结合全参数持久化构造函数（首选）或 with… 方法 —

    • 使用 Lombok 避免样板代码——由于持久化操作通常需要包含所有参数的构造函数，其声明往往沦为繁琐的样板式参数到字段赋值重复工作，而使用 Lombok 的 @AllArgsConstructor 可最佳地避免此类问题。

    覆盖属性

    Java 允许对领域类进行灵活设计，子类可以定义一个与其父类中已声明的同名属性。 考虑以下示例：

    public class SuperType {

   private CharSequence field;

   public SuperType(CharSequence field) {
      this.field = field;
   }

   public CharSequence getField() {
      return this.field;
   }

   public void setField(CharSequence field) {
      this.field = field;
   }
}

public class SubType extends SuperType {

   private String field;

   public SubType(String field) {
      super(field);
      this.field = field;
   }

   @Override
   public String getField() {
      return this.field;
   }

   public void setField(String field) {
      this.field = field;

      // optional
      super.setField(field);
   }
}

    两个类都使用可赋值类型定义了 field。然而，SubType 会遮蔽 SuperType.field。 根据类的设计，使用构造函数可能是设置 SuperType.field 的唯一默认方式。 或者，在 setter 中调用 super.setField(…) 也可以设置 SuperType 中的 field。 所有这些机制在某种程度上都会产生冲突，因为属性名称相同，但可能代表两个不同的值。 如果类型不可赋值，Spring Data 会跳过超类型的属性。 也就是说，被覆盖属性的类型必须可赋值于其超类型属性类型才能注册为覆盖属性；否则，超类型属性将被视为瞬态。 我们通常建议使用不同的属性名称。

    Spring Data 模块通常支持覆盖属性以持有不同的值。从编程模型的角度来看，有几点需要考虑：

    1. 应持久化哪些属性（默认为所有声明的属性）？ 您可以通过使用 @Transient 注解来排除某些属性。

    2. 如何在数据存储中表示属性？ 使用相同的字段/列名存储不同的值通常会导致数据损坏，因此您应该至少为其中一个属性显式指定字段/列名。

    3. 使用@AccessType(PROPERTY)不可行，因为无法在不对 setter 实现做出任何额外假设的情况下设置超属性。

    Kotlin 支持

    Spring Data 适配了 Kotlin 的具体特性，以支持对象的创建和修改。

    Kotlin 对象创建

    支持实例化 Kotlin 类，所有类默认不可变，且需要显式声明属性以定义可变属性。

    Spring Data 会自动尝试检测持久化实体中用于实例化该类型对象的构造函数。 解析算法的工作方式如下：

    1. 如果存在一个带有@PersistenceCreator注解的构造函数，则使用它。

    2. 如果类型是Kotlin 数据类，则使用主构造函数。

    3. 如果存在一个带有@PersistenceCreator注解的单个静态工厂方法，则使用该方法。

    4. 如果只有一个构造函数，则使用它。

    5. 如果存在多个构造函数且其中恰好有一个被标注为@PersistenceCreator，则使用该构造函数。

    6. 如果类型是 Java 的Record，则使用规范构造函数。

    7. 如果有无参构造函数，则使用它。 其他构造函数将被忽略。

    考虑以下 `data` 类 `Person`：

    data class Person(val id: String, val name: String)

    上述类编译为具有显式构造函数的典型类。我们可以通过添加另一个构造函数并用@PersistenceCreator注解它来指定构造函数偏好，从而自定义该类：

    data class Person(var id: String, val name: String) {

    @PersistenceCreator
    constructor(id: String) : this(id, "unknown")
}

    Kotlin 支持通过为参数提供默认值来实现参数的可选性。当 Spring Data 检测到具有参数默认值的构造函数时，如果数据存储未提供相应值（或简单地返回 `null`），它会将这些参数留空，以便 Kotlin 应用参数默认值机制。考虑以下对 `name` 应用参数默认值的类：

    data class Person(var id: String, val name: String = "unknown")

    每次 `name` 参数不在结果中或其值为 `null` 时，`name` 将默认为 `unknown`。

    Spring Data 不支持委派属性。对于 Kotlin 数据类，映射元数据会过滤掉委派属性。 在其他所有情况下，您可以通过使用 @Transient 注解来排除委派属性的合成字段。

    Kotlin 数据类的属性填充

    在 Kotlin 中，所有类默认都是不可变的，若要定义可变属性，则需显式声明。 考虑以下 data 类 Person：

    data class Person(val id: String, val name: String)

    该类实际上是不可变的。它允许创建新实例，因为 Kotlin 会生成一个 `copy(…)` 方法，该方法通过复制现有对象的所有属性值，并将作为参数提供的属性值应用其中，来创建新的对象实例。

    Kotlin 属性重写

    Kotlin 允许声明属性重写，以在子类中修改属性。

    open class SuperType(open var field: Int)

class SubType(override var field: Int = 1) :
	SuperType(field) {
}

    这种安排会导致两个名为 `field` 的属性。 Kotlin 会为每个类中的每个属性生成访问器（getter 和 setter）。 实际上，代码看起来如下所示：

    public class SuperType {

   private int field;

   public SuperType(int field) {
      this.field = field;
   }

   public int getField() {
      return this.field;
   }

   public void setField(int field) {
      this.field = field;
   }
}

public final class SubType extends SuperType {

   private int field;

   public SubType(int field) {
      super(field);
      this.field = field;
   }

   public int getField() {
      return this.field;
   }

   public void setField(int field) {
      this.field = field;
   }
}

    SubType 上的 getter 和 setter 仅设置 SubType.field，而不会设置 SuperType.field。 在这种安排下，使用构造函数是设置 SuperType.field 的唯一默认方法。 虽然可以通过在 SubType 中添加一个方法来通过 this.SuperType.field = … 设置 SuperType.field，但这不符合支持的习惯用法。 属性重写会在一定程度上产生冲突，因为这些属性具有相同的名称，但可能代表两个不同的值。 我们通常建议使用不同的属性名称。

    Spring Data 模块通常支持覆盖属性以持有不同的值。从编程模型的角度来看，有几点需要考虑：

    1. 应持久化哪些属性（默认为所有声明的属性）？ 您可以通过使用 @Transient 注解来排除某些属性。

    2. 如何在数据存储中表示属性？ 使用相同的字段/列名存储不同的值通常会导致数据损坏，因此您应该至少为其中一个属性显式指定字段/列名。

    3. 使用@AccessType(PROPERTY)时，无法将其用作超属性，因为该属性不可设置。

    Kotlin 值类

    Kotlin 值类旨在构建更具表现力的领域模型，使底层概念更加明确。 Spring Data 可以读取和写入使用值类定义属性的类型。

    考虑以下领域模型：

    @JvmInline
value class EmailAddress(val theAddress: String)                                    (1)

data class Contact(val id: String, val name:String, val emailAddress: EmailAddress) (2)
    1 一个具有非空值类型的简单值类。
    2 使用 EmailAddress 值类定义属性的数据类。
    使用非原始值类型的不可空属性在编译后的类中会被扁平化为值类型。 可空的原始值类型或可空的值 - 值类型将以其包装类型表示，这会影响值类型在数据库中的表示方式。

    文档与字段

    所有实体都应使用@Document注解进行标注，但这并非强制要求。

    此外，实体中的每个字段都应使用 @Field 注解进行标注。虽然从严格意义上讲这是可选的，但它有助于减少边缘情况，并清晰地展示实体的意图和设计。同时，它还可用于以不同的名称存储字段。

    此外，还有一个特殊的 `@Id` 注解必须始终存在。最佳实践是将该属性命名为`id`。

    这是一个非常简单的 `User` 实体：

    示例 1. 包含字段的简单文档
    import org.springframework.data.annotation.Id;
import org.springframework.data.couchbase.core.mapping.Field;
import org.springframework.data.couchbase.core.mapping.Document;

@Document
public class User {

    @Id
    private String id;

    @Field
    private String firstname;

    @Field
    private String lastname;

    public User(String id, String firstname, String lastname) {
        this.id = id;
        this.firstname = firstname;
        this.lastname = lastname;
    }

    public String getId() {
        return id;
    }

    public String getFirstname() {
        return firstname;
    }

    public String getLastname() {
        return lastname;
    }
}

    Couchbase Server 支持文档的自动过期功能。该库通过 `@Document` 注解实现了对此功能的支持。您可以设置一个 `expiry` 值，该值表示文档被自动移除前的秒数。如果您希望文档在突变后 10 秒内过期，可以将其设置为 `@Document(expiry = 10)`。或者，您可以使用 Spring 的属性支持以及 `expiryExpression` 参数来配置过期时间，以便动态更改过期值。例如：@Document(expiryExpression = "${valid.document.expiry}")。该属性必须可解析为整数值，且这两种方法不能混用。

    如果您希望在文档中的字段名与实体中使用的字段名不同，可以在 `@Field` 注解上设置不同的名称。例如，如果您希望保持文档的体积较小，可以将 `firstname` 字段设置为 `@Field("fname")`。在 JSON 文档中，您将看到 `{"fname": ".."}` 而不是 `{"firstname": ".."}`。

    由于每个 Couchbase 文档都需要一个唯一键，因此必须包含 @Id 注解。 该键可以是任何字符串，最大长度为 250 个字符。 请根据您的具体用例自由选择，例如使用 UUID、电子邮件地址或其他内容。

    写入 Couchbase Server 桶时，可以可选地指定持久性要求；该要求指示 Couchbase Server 在将写入视为已提交之前，先在集群中多个节点的内存和/或磁盘位置更新指定的文档。 默认持久性要求也可以通过 `@Document` 或 `@Durability` 注解进行配置。 例如：`@Document(durabilityLevel = DurabilityLevel.MAJORITY)` 会强制将变更复制到多数数据服务节点。这两个注解均支持通过 `durabilityExpression` 属性基于表达式分配持久性级别（注意不支持 SPEL）。

    通常情况下，您还需要存储一个时间值，例如 Date。 由于无法直接在 JSON 中存储该类型，因此需要进行转换。 该库为 Date、Calendar 以及 JodaTime 类型（如果位于类路径中）实现了默认转换器。 在文档中，这些类型默认均以 Unix 时间戳（数字）形式表示。 您始终可以通过自定义转换器覆盖默认行为，如下所示：

    示例 6：带有日期和日历的文档
    @Document
public class BlogPost {

    @Id
    private String id;

    @Field
    private Date created;

    @Field
    private Calendar updated;

    @Field
    private String title;

    public BlogPost(String id, Date created, Calendar updated, String title) {
        this.id = id;
        this.created = created;
        this.updated = updated;
        this.title = title;
    }

}

    示例 7。带有日期和日历的文档 - JSON

    可选地，通过将系统属性 `org.springframework.data.couchbase.useISOStringConverterForDate` 设置为 true，可以将 Date 转换为符合 ISO-8601 标准的字符串，或从此类字符串转换回 Date。 如果您希望覆盖转换器或实现自己的转换器，这也是可行的。 该库实现了通用的 Spring Converter 模式。 您可以在配置中的 Bean 创建时插入自定义转换器。 以下是如何在您重写的 `AbstractCouchbaseConfiguration` 中进行配置的方法：

    示例 8：自定义转换器
    @Override
public CustomConversions customConversions() {
    return new CustomConversions(Arrays.asList(FooToBarConverter.INSTANCE, BarToFooConverter.INSTANCE));
}

@WritingConverter
public static enum FooToBarConverter implements Converter<Foo, Bar> {
    INSTANCE;

    @Override
    public Bar convert(Foo source) {
        return /* do your conversion here */;
    }

}

@ReadingConverter
public static enum BarToFooConverter implements Converter<Bar, Foo> {
    INSTANCE;

    @Override
    public Foo convert(Bar source) {
        return /* do your conversion here */;
    }

}

    关于自定义转化，有几点需要注意：

    • 为消除歧义，请始终在转换器上使用@WritingConverter和@ReadingConverter注解。特别是在处理基本类型转换时，这将有助于减少可能的错误转换。

    • 如果您实现了写入转换器，请确保仅解码为基本类型、映射和列表。 如果需要更复杂的对象类型，请使用 CouchbaseDocument 和 CouchbaseList 类型，这些类型也能被底层的转换引擎识别。 最好的做法是尽可能保持转换简单。

    • 始终将更特殊的转换器置于通用转换器之前，以避免执行错误的转换器。

    • 对于日期，读取转换器应能够读取任何 `Number`（而不仅仅是 `Long`）。 这是为了支持 N1QL。

    乐观锁

    在某些情况下，您可能希望在文档上执行突变操作时，确保不会覆盖其他用户的更改。为此，您有三种选择：事务（自 Couchbase 6.5 起支持）、悲观并发控制（加锁）或乐观并发控制。

    乐观并发控制通常比悲观并发控制或事务提供更好的性能，因为它不会在数据上持有实际的锁，也不会存储有关操作的额外信息（无需事务日志）。

    为了实现乐观锁，Couchbase 采用了 CAS（比较并交换）机制。当文档发生变更时，其 CAS 值也会随之改变。CAS 对客户端是不透明的，您只需知道：只要内容或元数据发生变化，CAS 值就会更新。

    在其他数据存储中，可以通过带有递增计数器的任意版本字段来实现类似的行为。由于 Couchbase 对此提供了更好的支持，因此实现起来非常简单。如果您需要自动的乐观锁支持，只需在长整型字段上添加 `@Version` 注解即可，如下所示：

    示例 9：具有乐观锁的文档。
    @Document
public class User {

        @Version
        private long version;

        // constructor, getters, setters...
}

    通过模板或存储库加载文档时，版本字段将自动填充为当前的 CAS 值。 需要注意的是，您不应直接访问该字段，更不应自行修改它。 保存文档后，操作要么成功，要么会抛出 OptimisticLockingFailureException 异常。 如果捕获到此类异常，后续处理方式取决于您的应用目标：您可以选择重试完整的加载 - 更新 - 写入循环，或将错误向上层传播以便进行适当处理。

    Validation

    该库支持基于实体中直接注解的 JSR 303 验证。当然，您可以在服务层添加各种类型的验证，但这种方式与您的实际实体紧密耦合。

    要使该功能正常工作，您需要包含两个额外的依赖项：JSR 303 以及一个实现该规范的库（例如 Hibernate 所支持的库）：

    示例 10：验证依赖项

  <groupId>javax.validation</groupId>
  <artifactId>validation-api</artifactId>
</dependency>
<dependency>
  <groupId>org.hibernate</groupId>
  <artifactId>hibernate-validator</artifactId>
</dependency>

    Auditing

    实体可以通过 Spring Data 审计机制进行自动审计（追踪创建实体的用户、更新实体的用户以及更新时间）。

    首先，请注意，只有具有@Version注解字段的实体才能进行创建审计（否则框架会将创建操作解释为更新）。

    审计功能通过为字段添加 `@CreatedBy`、`@CreatedDate`、`@LastModifiedBy` 和 `@LastModifiedDate` 注解来实现。在持久化实体时，框架会自动向这些字段注入正确的值。 `xxxDate` 类型的注解必须应用于 `Date` 字段（或兼容类型，如 JodaTime 类），而 `xxxBy` 类型的注解可以应用于任意类型 `T` 的字段（尽管两个字段必须具有相同的类型）。

    要配置审计功能，首先需要在上下文中引入一个 AuditorAware 类型的 Bean。该 Bean 的类型必须是 AuditorAware<T>（允许生成可存储到之前提到的类型为 T 的 xxxBy 字段中的值）。其次，您必须在 @Configuration 类中使用 @EnableCouchbaseAuditing 注解来启用审计功能。

    这是一个示例：

    示例 13。样本审计主体
    @Document
public class AuditedItem {

  @Id
  private final String id;

  private String value;

  @CreatedBy
  private String creator;

  @LastModifiedBy
  private String lastModifiedBy;

  @LastModifiedDate
  private Date lastModification;

  @CreatedDate
  private Date creationDate;

  @Version
  private long version;

  //..omitted constructor/getters/setters/...
}

    注意，@CreatedBy 和 @LastModifiedBy 都放置在 String 字段上，因此我们的 AuditorAware 必须与 String 配合使用。

    示例 14：SampleAuditorAware 实现示例
    public class NaiveAuditorAware implements AuditorAware<String> {

  private String auditor = "auditor";

  @Override
  public String getCurrentAuditor() {
    return auditor;
  }

  public void setAuditor(String auditor) {
    this.auditor = auditor;
  }
}

    将所有这些内容整合起来，我们使用 Java 配置既声明一个 AuditorAware Bean，又激活审计功能：

    示例 15。样本审计配置
    @Configuration
@EnableCouchbaseAuditing //this activates auditing
public class AuditConfiguration extends AbstractCouchbaseConfiguration {

    //... a few abstract methods omitted here

    // this creates the auditor aware bean that will feed the annotations
    @Bean
    public NaiveAuditorAware testAuditorAware() {
      return new NaiveAuditorAware();
    }
