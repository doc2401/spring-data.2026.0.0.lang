    对象映射

    MappingMongoConverter 提供了丰富的映射支持。该转换器持有一个元数据模型，用于提供将领域对象映射到 MongoDB 文档的完整功能集。映射元数据模型是通过在领域对象上使用注解来填充的。然而，基础设施并不局限于仅使用注解作为元数据的唯一来源。MappingMongoConverter 还允许您通过遵循一系列约定，在不提供任何额外元数据的情况下将对象映射为文档。

    本节介绍了MappingMongoConverter的功能，包括其基础内容、如何使用约定将对象映射为文档，以及如何通过基于注解的映射元数据覆盖这些约定。

    对象映射基础

    本节涵盖 Spring Data 对象映射、对象创建、字段和属性访问以及可变性与不可变性的基础知识。请注意，本节仅适用于不使用底层数据存储（如 JPA）的对象映射的 Spring Data 模块。此外，请务必查阅针对特定存储的章节，以了解特定于该存储的对象映射内容，例如索引、自定义列或字段名称等。

    Spring Data 对象映射的核心职责是创建领域对象实例，并将存储原生的数据结构映射到这些对象上。 这意味着我们需要两个基本步骤：

    1. 通过暴露的构造函数之一创建实例。

    2. 实例化以体现所有暴露的属性。

    对象创建

    Spring Data 会自动尝试检测持久化实体中用于实例化该类型对象的构造函数。 解析算法的工作方式如下：

    1. 如果存在一个带有@PersistenceCreator注解的单个静态工厂方法，则使用该方法。

    2. 如果只有一个构造函数，则使用它。

    3. 如果存在多个构造函数且其中恰好有一个被标注为@PersistenceCreator，则使用该构造函数。

    4. 如果类型是 Java 的 `Record`，则使用规范构造函数。

    5. 如果有无参构造函数，则使用它。 其他构造函数将被忽略。

    值解析假定构造函数/工厂方法的参数名称与实体属性名称相匹配，即解析过程将如同该属性正在被填充一样执行，包括所有映射自定义（如不同的数据存储列或字段名等）。 此外，还要求类文件中提供参数名称信息，或者在构造函数上存在 `@ConstructorProperties` 注解。

    可以通过使用 Spring Framework 的 `@Value` 注解及特定于存储库的 SpEL 表达式来自定义值解析。有关更多详细信息，请参阅关于存储库特定映射的章节。

    对象创建的内部机制

    为避免反射带来的开销，Spring Data 默认使用在运行时生成的工厂类来创建对象，该工厂类将直接调用领域类的构造函数。 即对于此示例类型：

    class Person {
  Person(String firstname, String lastname) { … }
}

    我们将在运行时创建一个语义上与此工厂类等效的工厂类：

    class PersonObjectInstantiator implements ObjectInstantiator {

  Object newInstance(Object... args) {
    return new Person((String) args[0], (String) args[1]);
  }
}

    这为我们带来了比反射大约 10% 的性能提升。 要使领域类符合此类优化的条件，它需要遵守一组约束：

    • 它不能是私有类。

    • 它不能是非静态内部类。

    • 它不能是 CGLib 代理类。

    • Spring Data 所使用的构造函数不能是私有的。

    如果满足上述任一条件，Spring Data 将通过反射回退到实体实例化。

    属性人口

    一旦创建了该实体的实例，Spring Data 会填充该类中所有剩余的持久化属性。 除非这些属性已通过实体构造函数（即通过构造函数参数列表）进行填充，否则标识符属性将被首先填充，以便解析循环对象引用。 随后，所有未被构造函数填充的非瞬态属性将被设置到实体实例上。 为此，我们采用以下算法：

    1. 如果该属性是不可变的，但暴露了 `with…` 方法（见下文），我们使用 `with…` 方法来创建一个具有新属性值的新实体实例。

    2. 如果定义了属性访问（即通过 getter 和 setter 进行访问），我们将调用 setter 方法。

    3. 如果该属性是可变的，则直接设置该字段。

    4. 如果属性是不可变的，我们将使用构造函数（参见对象创建）由持久化操作来创建该实例的副本。

    5. 默认情况下，我们直接设置字段值。

    属性人口内部结构

    与我们在对象构建中的优化类似，我们也使用 Spring Data 运行时生成的访问器类来与实体实例进行交互。

    class Person {

  private final Long id;
  private String firstname;
  private @AccessType(Type.PROPERTY) String lastname;

  Person() {
    this.id = null;
  }

  Person(Long id, String firstname, String lastname) {
    // Field assignments
  }

  Person withId(Long id) {
    return new Person(id, this.firstname, this.lastname);
  }

  void setLastname(String lastname) {
    this.lastname = lastname;
  }
}
    生成的属性访问器
    class PersonPropertyAccessor implements PersistentPropertyAccessor {

  private static final MethodHandle firstname;              (2)

  private Person person;                                    (1)

  public void setProperty(PersistentProperty property, Object value) {

    String name = property.getName();

    if ("firstname".equals(name)) {
      firstname.invoke(person, (String) value);             (2)
    } else if ("id".equals(name)) {
      this.person = person.withId((Long) value);            (3)
    } else if ("lastname".equals(name)) {
      this.person.setLastname((String) value);              (4)
    }
  }
}
    1 PropertyAccessor 持有底层对象的可变实例，以便能够修改原本不可变的属性。
    2 默认情况下，Spring Data 使用属性访问方式来读写属性值。根据 private 字段的可见性规则，使用 MethodHandles 与字段进行交互。
    3 该类提供了一个 withId(…) 方法，用于设置标识符，例如当实例被插入数据存储且已生成标识符时。调用 withId(…) 会创建一个新的 Person 对象。随后的所有修改都将在新实例中进行，而不会改变之前的实例。
    4 使用属性访问允许直接调用方法，而无需使用 MethodHandles。

    这为我们带来了比反射间接提升约 25% 的性能。 要使领域类符合此类优化的条件，它需要遵守一组约束：

    • 类型不得位于默认包或java包下。

    • 类型及其构造函数必须是public的

    • 作为内部类的类型，必须是static的。

    • 所使用的 Java 运行时必须允许在源 `ClassLoader` 中声明类。Java 9 及更高版本施加了某些限制。

    默认情况下，Spring Data 会尝试使用生成的属性访问器；如果检测到限制，则回退到基于反射的访问器。

    让我们看看以下实体：

    示例实体
    class Person {

  private final @Id Long id;                                                (1)
  private final String firstname, lastname;                                 (2)
  private final LocalDate birthday;
  private final int age;                                                    (3)

  private String comment;                                                   (4)
  private @AccessType(Type.PROPERTY) String remarks;                        (5)
  private @Transient String summary;                                        (6)

  static Person of(String firstname, String lastname, LocalDate birthday) { (7)

    return new Person(null, firstname, lastname, birthday,
      Period.between(birthday, LocalDate.now()).getYears());
  }

  Person(Long id, String firstname, String lastname, LocalDate birthday, int age) { (7)

    this.id = id;
    this.firstname = firstname;
    this.lastname = lastname;
    this.birthday = birthday;
    this.age = age;
  }

  Person withId(Long id) {                                                  (1)
    return new Person(id, this.firstname, this.lastname, this.birthday, this.age);
  }

  void setRemarks(String remarks) {                                         (5)
    this.remarks = remarks;
  }
}
    1 标识符属性为 final 类型，但在构造函数中被设置为 null。该类提供了一个 withId(…) 方法用于设置标识符，例如当实例被插入数据存储且已生成标识符时。原始的 Person 实例保持不变，因为会创建一个新的实例。通常会对其他需要存储管理但可能需要更改以进行持久化操作的属性应用相同的模式。wither 方法是可选的，因为持久化构造函数（见第 6 点）本质上是一个拷贝构造函数，设置该属性将被转换为创建一个新实例，并将新的标识符值应用其中。
    2 firstname 和 lastname 属性是普通的不可变属性，可能通过 getter 方法暴露。
    3 age 属性是不可变的，但它是从 birthday 属性派生而来的。按照所示的设计，数据库值将优于默认值，因为 Spring Data 仅使用声明的构造函数。即使意图是优先采用计算结果，也重要的是该构造函数也应接受 age 作为参数（以便可能忽略它），否则属性填充步骤将尝试设置 age 字段，但由于其不可变且不存在 with… 方法而失败。
    4 comment 属性是可变的，通过直接设置其字段进行填充。
    5 remarks 属性是可变的，通过调用 setter 方法进行填充。
    6 summary 属性是瞬态的，不会被持久化，因为它被标注为 @Transient。Spring Data 不使用 Java 的 transient 关键字来排除属性不被持久化，因为 transient 是 Java 序列化框架的一部分。请注意，该属性可以与持久化构造函数一起使用，但其值将默认为 null（如果属性类型是基本类型，则为其相应的基本类型初始值）。
    7 该类提供了一个工厂方法和一个构造函数用于对象创建。这里的核心理念是使用工厂方法而不是额外的构造函数，以避免通过 @PersistenceCreator 进行构造函数消歧的需要。相反，属性的默认值处理在工厂方法内部完成。如果您希望 Spring Data 使用工厂方法进行对象实例化，请将其标注为 @PersistenceCreator。

    一般建议

    • 尽量使用不可变对象——创建不可变对象非常简单，只需调用其构造函数即可完成对象的实例化。此外，这还能避免在领域对象中散布允许客户端代码操纵对象状态的 setter 方法。如果确实需要这些方法，建议将其设为包级私有（package protected），以便仅由有限的同包类型调用。仅通过构造函数进行对象实例化的速度比属性填充快高达 30%。

    • 提供一个全参构造函数——即使您无法或不愿将实体建模为不可变值，提供接受实体所有属性（包括可变属性）作为参数的构造函数仍有价值，因为这允许对象映射跳过属性填充，从而实现最佳性能。

    • 使用工厂方法而非重载构造函数，以避免使用 @PersistenceCreator——由于全参构造函数对于最佳性能是必需的，我们通常希望暴露更多针对特定应用场景的构造函数，这些构造函数会省略诸如自动生成的标识符等内容。 采用静态工厂方法来暴露全参构造函数的各种变体，是一种成熟的模式。

    • 确保遵守相关约束，以便生成的实例化器和属性访问器类能够被使用。

    • 若要生成标识符，仍需使用最终字段配合全参数持久化构造函数（首选）或 with… 方法 —

    • 使用 Lombok 避免样板代码——由于持久化操作通常需要包含所有参数的构造函数，其声明往往变成对样板式参数到字段赋值语句的繁琐重复，而使用 Lombok 的 @AllArgsConstructor 可以最好地避免这种情况。

    覆盖属性

    Java 允许对领域类进行灵活设计，子类可以定义一个与其父类中已声明的同名属性。 考虑以下示例：

    public class SuperType {

   private CharSequence field;

   public SuperType(CharSequence field) {
      this.field = field;
   }

   public CharSequence getField() {
      return this.field;
   }

   public void setField(CharSequence field) {
      this.field = field;
   }
}

public class SubType extends SuperType {

   private String field;

   public SubType(String field) {
      super(field);
      this.field = field;
   }

   @Override
   public String getField() {
      return this.field;
   }

   public void setField(String field) {
      this.field = field;

      // optional
      super.setField(field);
   }
}

    两个类都使用可赋值类型定义了 `field`。然而，`SubType` 会遮蔽 `SuperType.field`。 根据类的设计，使用构造函数可能是设置 `SuperType.field` 的唯一默认方法。 或者，在 setter 中调用 `super.setField(…)` 也可以设置 `SuperType` 中的 `field`。 所有这些机制在某种程度上都会产生冲突，因为属性名称相同，但可能代表两个不同的值。 如果类型不可赋值，Spring Data 会跳过父类型的属性。也就是说，被覆盖属性的类型必须可赋值于其父类型属性类型才能注册为覆盖属性；否则，父类型属性将被视为瞬态。 我们通常建议使用不同的属性名称。

    Spring Data 模块通常支持覆盖属性以持有不同的值。从编程模型的角度来看，有几点需要考虑：

    1. 应持久化哪些属性（默认为所有声明的属性）？ 您可以通过使用 @Transient 注解来排除某些属性。

    2. 如何在数据存储中表示属性？ 为不同的值使用相同的字段/列名通常会导致数据损坏，因此您应该至少使用一个显式的字段/列名来标注这些属性。

    3. 使用@AccessType(PROPERTY)不可行，因为无法在不对 setter 实现做出任何额外假设的情况下设置超属性。

    Kotlin 支持

    Spring Data 适配了 Kotlin 的具体特性，以支持对象的创建和修改。

    Kotlin 对象创建

    支持实例化 Kotlin 类，所有类默认不可变，且需要显式声明属性以定义可变属性。

    Spring Data 会自动尝试检测持久化实体中用于实例化该类型对象的构造函数。 解析算法的工作方式如下：

    1. 如果存在一个带有@PersistenceCreator注解的构造函数，则使用该构造函数。

    2. 如果类型是Kotlin 数据类，则使用主构造函数。

    3. 如果存在一个带有@PersistenceCreator注解的单个静态工厂方法，则使用该方法。

    4. 如果只有一个构造函数，则使用它。

    5. 如果存在多个构造函数且其中恰好有一个被标注为@PersistenceCreator，则使用该构造函数。

    6. 如果类型是 Java 的 `Record`，则使用规范构造函数。

    7. 如果有无参构造函数，则使用它。 其他构造函数将被忽略。

    考虑以下 `data` 类 `Person`：

    data class Person(val id: String, val name: String)

    上述类编译为具有显式构造函数的典型类。我们可以通过添加另一个构造函数并用 `@PersistenceCreator` 注解它来指定构造函数偏好，从而自定义该类：

    data class Person(var id: String, val name: String) {

    @PersistenceCreator
    constructor(id: String) : this(id, "unknown")
}

    Kotlin 支持通过为参数提供默认值来实现参数的可选性。当 Spring Data 检测到具有参数默认值的构造函数时，如果数据存储未提供相应值（或简单地返回 null），它会将这些参数留空，以便 Kotlin 应用参数默认值机制。考虑以下对 name 参数应用默认值的类：

    data class Person(var id: String, val name: String = "unknown")

    每次 `name` 参数不在结果中或其值为 `null` 时，`name` 将默认为 `unknown`。

    Spring Data 不支持委派属性。对于 Kotlin 数据类，映射元数据会过滤掉委派属性。 在其他所有情况下，您可以通过使用 @Transient 注解标记该属性来排除委派属性的合成字段。

    Kotlin 数据类的属性填充

    在 Kotlin 中，所有类默认都是不可变的，若要定义可变属性，则需显式声明。 考虑以下 data 类 Person：

    data class Person(val id: String, val name: String)

    该类实际上是不可变的。它允许创建新实例，因为 Kotlin 会生成一个 `copy(…)` 方法，该方法通过复制现有对象的所有属性值，并将作为参数提供的属性值应用过来，从而创建新的对象实例。

    Kotlin 属性重写

    Kotlin 允许声明属性重写，以在子类中修改属性。

    open class SuperType(open var field: Int)

class SubType(override var field: Int = 1) :
	SuperType(field) {
}

    这样的安排会导致两个名为 `field` 的属性。 Kotlin 会为每个类中的每个属性生成访问器（getter 和 setter）。 实际上，代码看起来如下所示：

    public class SuperType {

   private int field;

   public SuperType(int field) {
      this.field = field;
   }

   public int getField() {
      return this.field;
   }

   public void setField(int field) {
      this.field = field;
   }
}

public final class SubType extends SuperType {

   private int field;

   public SubType(int field) {
      super(field);
      this.field = field;
   }

   public int getField() {
      return this.field;
   }

   public void setField(int field) {
      this.field = field;
   }
}

    SubType 上的 getter 和 setter 仅设置 SubType.field，而不会设置 SuperType.field。 在这种安排下，使用构造函数是设置 SuperType.field 的唯一默认方法。 虽然在 SubType 中添加一个通过 this.SuperType.field = … 来设置 SuperType.field 的方法是可行的，但这不符合支持的标准约定。 属性重写会在一定程度上产生冲突，因为这些属性具有相同的名称，但可能代表两个不同的值。 我们通常建议使用不同的属性名称。

    Spring Data 模块通常支持覆盖属性以持有不同的值。从编程模型的角度来看，有几点需要考虑：

    1. 应持久化哪些属性（默认为所有声明的属性）？ 您可以通过使用 @Transient 注解来排除某些属性。

    2. 如何在数据存储中表示属性？ 为不同的值使用相同的字段/列名通常会导致数据损坏，因此您应该至少使用一个显式的字段/列名来标注这些属性。

    3. 使用@AccessType(PROPERTY)时，由于无法设置父属性，因此不能使用。

    基于约定的映射

    当未提供额外的映射元数据时，MappingMongoConverter 在将对象映射为文档时遵循一些约定。这些约定包括：

    • 短类名与集合名的映射方式如下。 类com.bigbank.SavingsAccount映射到集合名savingsAccount。

    • 所有嵌套对象均以嵌套对象的形式存储在文档中，而非以 DBRef 形式存储。

    • 转换器使用与其注册的任何 Spring 转换器来覆盖对象属性到文档字段和值的默认映射。

    • 对象的字段用于与文档中的字段进行转换。 不使用公共的 `JavaBean` 属性。

    • 如果存在一个具有单个非零参数的构造函数，且该构造函数的参数名称与文档的顶层字段名称匹配，则使用该构造函数；否则，使用无参构造函数。如果存在多个具有非零参数的构造函数，将抛出异常。

    映射层中如何处理 _id 字段。

    MongoDB 要求所有文档都必须包含一个 `_id` 字段。如果您未提供该字段，驱动程序将分配一个具有生成值的 ObjectId。_id 字段的类型可以是除数组以外的任何类型，只要其值是唯一的即可。驱动程序天然支持所有基本类型和日期。在使用 `MappingMongoConverter` 时，有一些规则决定了如何将 Java 类的属性映射到 `_id` 字段。

    以下字段将被映射到文档的 `_id` 字段：

    • 使用 @Id（org.springframework.data.annotation.Id）注解的字段将映射到 _id 字段。
      此外，可以通过 @Field 注解自定义文档字段的名称，在这种情况下，文档中将不包含 _id 字段。

    • 没有注解但命名为id的字段将被映射到_id字段。

    以下说明了将映射到 `_id` 文档字段的属性所执行的类型转换（如有）。

    • 如果 Java 类中声明的字段名为id，且其类型为 String 或 BigInteger，则只要可能，该值将被转换为 ObjectId 并存储。ObjectId 作为字段类型也是有效的。如果在应用程序中为id指定了值，MongoDB 驱动程序会负责将其转换为 ObjectId。如果指定的id值无法转换为 ObjectId，则该值将原样存储在文档的_id字段中。此规则同样适用于使用@Id注解标记的字段。

    • 如果 Java 类中的字段使用 @MongoId 注解，该字段将以其实际类型进行转换并存储。 除非 @MongoId 声明了期望的字段类型，否则不会进行进一步的转换。 如果未为 id 字段提供值，将创建一个新的 ObjectId 并将其转换为属性类型。

    • 如果 Java 类中的字段使用 @MongoId(FieldType.…) 进行注解，系统将尝试将该字段的值转换为声明的 FieldType。 如果未为 id 字段提供值，将创建一个新的 ObjectId 并将其转换为声明的类型。

    • 如果 Java 类中的字段未声明为 String、BigInteger 或 ObjectID，则应在应用程序中为其赋值，以便将其“原样”存储到文档的 `_id` 字段中。

    • 如果 Java 类中没有名为 id 的字段，则驱动程序会生成一个隐式的 _id 文件，但该文件不会映射到 Java 类的任何属性或字段。

    当查询和更新时，MongoTemplate 会使用转换器来处理与上述保存文档规则相对应的 Query 和 Update 对象的转换，因此您在查询中使用的字段名称和类型将能够与您的领域类中的内容相匹配。

    藏品管理

    集合的处理取决于 MongoDB 返回的实际值。

    • 如果文档中不包含映射到集合的字段，则映射不会更新该属性。这意味着该值将保持为null、Java 默认值或在对象创建期间设置的任何值。

    • 如果文档中包含一个需要映射的字段，但该字段的值为null（例如：{ 'list' : null }），则属性值将被设置为null。

    • 如果文档中包含一个映射到集合的字段，且该集合不为null（例如：{ 'list' : [ … ] }），则该集合将被填充为映射后的值。

    通常，如果使用构造函数创建，则可以获取要设置的值。如果查询响应未提供属性值，则属性填充可以使用默认初始化值。

    基于元数据的映射

    要充分利用 Spring Data MongoDB 支持中的对象映射功能，您应该使用 @Document 注解来标注您的映射对象。 虽然映射框架并不强制需要此注解（即使没有任何注解，您的 POJO 也能正确映射），但该注解允许类路径扫描器发现并预处理您的领域对象，以提取必要的元数据。 如果您不使用此注解，在首次存储领域对象时，应用程序的性能会略有下降，因为映射框架需要构建其内部元数据模型，以便了解您领域对象的属性以及如何持久化它们。 以下示例展示了一个领域对象：

    示例 1。示例领域对象
    @Document
public class Person {

  @Id
  private ObjectId id;

  @Indexed
  private Integer ssn;

  private String firstName;

  @Indexed
  private String lastName;
}
    @Id 注解告诉 Mapper 您希望使用哪个属性作为 MongoDB 的 _id 属性，而 @Indexed 注解则指示映射框架在该文档的属性上调用 createIndex(…)，从而加快搜索速度。 仅对带有 @Document 注解的类型执行自动索引创建。
    自动创建索引默认处于禁用状态，需要通过配置启用（参见 索引创建）。

    映射注解概述

    MappingMongoConverter 可以使用元数据来驱动对象到文档的映射。 可用的注解如下：

    • @Id：应用于字段级别，用于标记用于标识目的的字段。

    • @MongoId：在字段级别应用，用于标记用于身份识别的字段。 接受可选的 FieldType 以自定义 ID 转换。

    • @Document：在类级别应用，表示该类是数据库映射的候选者。 您可以指定存储数据的集合名称。

    • @DBRef：应用于字段，指示该字段将使用 com.mongodb.DBRef 进行存储。

    • @DocumentReference：应用于字段，表示该字段应存储为指向另一个文档的指针。 这可以是一个单值（默认为 id），或者通过转换器提供的 Document 对象。

    • @Indexed：应用于字段级别，用于描述如何对该字段进行索引。

    • @CompoundIndex（可重复）：在类型级别应用，用于声明复合索引。

    • @GeoSpatialIndexed：在字段级别应用，用于描述如何对该字段进行地理空间索引。

    • @TextIndexed：应用于字段级别，用于标记该字段应包含在文本索引中。

    • @HashIndexed：在字段级别应用，用于哈希索引中，以便在分片集群中划分数据。

    • @Language：应用于字段级别，用于设置文本索引的语言覆盖属性。

    • @Transient：默认情况下，所有字段都会映射到文档中。此注解会排除应用该注解的字段，使其不被存储到数据库中。瞬态属性不能在持久化构造函数中使用，因为转换器无法为构造函数参数生成值。

    • @PersistenceCreator：标记一个构造函数或静态工厂方法（即使是包级私有的），以便在从数据库实例化对象时使用该方法。构造函数的参数将按名称映射到检索到的文档中的键值。

    • @Value：此注解属于 Spring 框架。在映射框架中，它可以应用于构造函数参数。 这使得您能够使用 Spring 表达式语言语句，在利用从数据库检索到的键值构建领域对象之前对其进行转换。 若要引用给定文档的某个属性，则需使用类似 @Value("#root.myProperty") 的表达式，其中 root 指代该给定文档的根节点。

    • @Field：应用于字段级别，它允许描述该字段在 MongoDB BSON 文档中的名称和类型，从而使字段的名称和类型可以与类的字段名以及属性类型不同。

    • @Version：在字段级别应用，用于乐观锁，并在保存操作时检查修改。初始值为零（基本类型为 1），每次更新时自动递增。

    映射元数据基础设施定义在一个独立的、与具体技术无关的 spring-data-commons 项目中。 MongoDB 支持模块使用了特定的子类来实现基于注解的元数据功能。 如果存在需求，也可以实施其他策略。

    这是一个更复杂映射的示例。

  @AsString
  private BigDecimal value;

  // ...
}

    特殊字段名称

    一般来说，MongoDB 使用点号（.）作为嵌套文档或数组的路径分隔符。这意味着在查询（或更新语句）中，类似 a.b.c 的键将指向如下所示的对象结构：

    {
    'a' : {
        'b' : {
            'c' : …
        }
    }
}

    因此，在 MongoDB 5.0 之前，字段名称不能包含点号（.）。 通过使用 MappingMongoConverter#setMapKeyDotReplacement，可以在写入时将点号替换为其他字符，从而规避存储 Map 结构时的一些限制。

    converter.setMapKeyDotReplacement("-");
// ...

source.map = Map.of("key.with.dot", "value")
converter.write(source,...) // -> map : { 'key-with-dot', 'value' }

    随着 MongoDB 5.0 的发布，对包含特殊字符的 `Document` 字段名的限制已被解除。我们强烈建议阅读更多关于在字段名中使用点号的限制的详细信息，请参阅 MongoDB 参考文档。
    若要在 `Map` 结构中包含点号，请在 `MappingMongoConverter` 上设置 `preserveMapKeys`。

    使用@Field允许以两种方式自定义字段名以考虑点号。

    1. @Field(name = "a.b")：名称被视为路径。操作期望嵌套对象的结构，例如 { a : { b : … } }。

    2. @Field(name = "a.b", fieldNameType = KEY)：名称被视为原样。操作期望一个具有给定值的字段，即 { 'a.b' : ….. }。

    由于 MongoDB 查询和更新语句中点字符的特殊性，包含点的字段名无法被直接定位，因此被排除在派生查询方法的使用范围之外。 考虑以下具有categoryId属性的Item，该属性映射到名为cat.id的字段。

    public class Item {

	@Field(name = "cat.id", fieldNameType = KEY)
	String categoryId;

	// ...
}

    其原始表现形式将如下所示

    {
    'cat.id' : "5b28b5e7-52c2",
    ...
}

    由于无法直接针对cat.id字段进行查询（因为这会被解释为路径），我们需要借助聚合框架的帮助。

    查询名称中包含点的字段
    template.query(Item.class)
    // $expr : { $eq : [ { $getField : { input : '$$CURRENT', 'cat.id' }, '5b28b5e7-52c2' ] }
    .matching(expr(ComparisonOperators.valueOf(ObjectOperators.getValueOf("value")).equalToValue("5b28b5e7-52c2"))) (1)
    .all();
    1 映射层负责将属性名 value 转换为实际的字段名。在这里使用目标字段名也是完全有效的。
    更新名称中包含点的字段
    template.update(Item.class)
    .matching(where("id").is("r2d2"))
    // $replaceWith: { $setField : { input: '$$CURRENT', field : 'cat.id', value : 'af29-f87f4e933f97' } }
    .apply(AggregationUpdate.newUpdate(ReplaceWithOperation.replaceWithValue(ObjectOperators.setValueTo("value", "af29-f87f4e933f97")))) (1)
    .first();
    1 映射层负责将属性名 value 转换为实际的字段名。在这里使用目标字段名也是完全有效的。

    上图展示了一个简单示例，其中特殊字段位于顶层文档。嵌套层级的增加会提高与字段交互所需的聚合表达式的复杂度。

    自定义对象构建

    映射子系统允许通过用@PersistenceCreator注解构造函数来自定义对象构建。 用于解析构造函数参数的值的方式如下：

    • 如果参数被标注了 `@Value` 注解，则会对给定的表达式进行求值，并将结果用作该参数的值。

    • 如果 Java 类型中存在一个属性，其名称与输入文档中的给定字段匹配，则使用该属性的信息来选择适当的构造函数参数，以便将输入字段的值传递给它。 此方法仅在 java .class 文件中包含参数名信息时才有效，这可以通过使用调试信息编译源代码，或在 Java 8 中使用新的 -parameters 命令行开关来实现。

    • 否则，将抛出 `MappingException` 异常，表示无法绑定给定的构造函数参数。

    class OrderItem {

  private @Id String id;
  private int quantity;
  private double unitPrice;

  OrderItem(String id, @Value("#root.qty ?: 0") int quantity, double unitPrice) {
    this.id = id;
    this.quantity = quantity;
    this.unitPrice = unitPrice;
  }

  // getters/setters omitted
}

Document input = new Document("id", "4711");
input.put("unitPrice", 2.5);
input.put("qty",5);
OrderItem item = converter.read(OrderItem.class, input);
    如果无法解析 @Value 注解中 quantity 参数的 SpEL 表达式指定的属性路径，则该表达式将回退到值 0。

    使用 @PersistenceCreator 注解的更多示例可以在 MappingMongoConverterUnitTests 测试套件中找到。
