    唯一标识符的处理与配置

    使用内部 Neo4j ID

    为域类提供唯一标识符的最简单方法是在类型为 String 或 Long（首选对象类型而非标量 long，因为字面量 null 是判断实例是否为新实例的更好指标）的字段上使用 @Id 和 @GeneratedValue 的组合：

    示例 1：具有内部 Neo4j ID 的可变 Movie 实体
    @Node("Movie")
public class MovieEntity {

	@Id @GeneratedValue
	private Long id;

	private String name;

	public MovieEntity(String name) {
		this.name = name;
	}
}

    您无需为该字段提供 setter，SDN 将使用反射来赋值该字段，但如果存在 setter，则优先使用 setter。 如果您想创建一个具有内部生成 ID 的不可变实体，则必须提供一个wither。

    示例 2：具有内部 Neo4j ID 的不可变 Movie 实体
    @Node("Movie")
public class MovieEntity {

	@Id @GeneratedValue
	private final Long id; (1)

	private String name;

	public MovieEntity(String name) { (2)
		this(null, name);
	}

	private MovieEntity(Long id, String name) { (3)
		this.id = id;
		this.name = name;
	}

	public MovieEntity withId(Long id) { (4)
		if (this.id.equals(id)) {
			return this;
		} else {
			return new MovieEntity(id, this.title);
		}
	}
}
    1 表示生成值的不可变 final id 字段
    2 公共构造函数，由应用程序和 Spring Data 使用
    3 内部使用的构造函数
    4 这是一个针对 id 属性的所谓 wither。它创建一个新的实体并相应地设置该字段，而不会修改原始实体，从而使其具有不可变性。

    要么必须为 id 属性提供 setter，或者类似 `wither` 的机制，如果您想要拥有

    • 优势：很明显，id 属性是代理业务键，使用它无需额外努力或配置。

    • 缺点：它依赖于 Neo4j 的内部数据库 ID，该 ID 在整个数据库生命周期内并非仅针对我们的应用实体而唯一。

    • 缺点：创建不可变实体需要付出更多努力。

    使用外部提供的代理键

    @GeneratedValue 注解可以接受一个实现 org.springframework.data.neo4j.core.schema.IdGenerator 的类作为参数。 SDN 默认提供了 InternalIdGenerator 和 UUIDStringGenerator。 后者为每个实体生成新的 UUID，并将其返回为 java.lang.String 类型。 使用此类的应用程序实体将如下所示：

    示例 3：具有外部生成代理键的可变 Movie 实体
    @Node("Movie")
public class MovieEntity {

	@Id @GeneratedValue(UUIDStringGenerator.class)
	private String id;

	private String name;
}

    我们需要就优缺点讨论两个独立的问题：任务本身以及 UUID 策略。 通用唯一标识符（UUID）旨在在实际应用中具有唯一性。 正如维基百科所述： “因此，任何人都可以创建一个 UUID，并几乎确定该标识符不会与已创建或将要创建的用于标识其他事物的标识符重复。”我们的策略采用 Java 内部的 UUID 机制，并使用密码学安全的伪随机数生成器。 在大多数情况下，这应该能正常工作，但具体情况可能因人而异。

    这便将任务本身留了下来：

    • 优势：应用程序拥有完全控制权，能够生成恰好满足应用需求的唯一密钥。生成的值将保持稳定，无需后续更改。

    • 缺点：生成的策略是在应用层实施的。 在那个年代，大多数应用程序会部署多个实例以实现良好的扩展性。 如果您的策略容易生成重复项，则插入操作将会失败，因为这将违反主键的唯一性约束。 因此，虽然在这种情况下您无需考虑唯一的业务键，但您需要更多地思考应该生成什么内容。

    您有多种方式来实现自己的 ID 生成器。其中一种是实现一个 POJO（普通 Java 对象）来充当生成器：

    示例 4：朴素序列生成器
    import java.util.concurrent.atomic.AtomicInteger;

import org.springframework.data.neo4j.core.schema.IdGenerator;
import org.springframework.util.StringUtils;

public class TestSequenceGenerator implements IdGenerator<String> {

	private final AtomicInteger sequence = new AtomicInteger(0);

	@Override
	public String generateId(String primaryLabel, Object entity) {
		return StringUtils.uncapitalize(primaryLabel) +
			"-" + sequence.incrementAndGet();
	}
}

    另一种选择是提供如下所示的额外 Spring Bean：

    示例 5：基于 Neo4jClient 的 ID 生成器
    @Component
class MyIdGenerator implements IdGenerator<String> {

	private final Neo4jClient neo4jClient;

	public MyIdGenerator(Neo4jClient neo4jClient) {
		this.neo4jClient = neo4jClient;
	}

	@Override
	public String generateId(String primaryLabel, Object entity) {
		return neo4jClient.query("YOUR CYPHER QUERY FOR THE NEXT ID") (1)
			.fetchAs(String.class).one().get();
	}
}
    1 使用您所需的精确查询或逻辑。

    上面的生成器将像这样配置为 Bean 引用：

    示例 6：使用 Spring Bean 作为 ID 生成器的可变 MovieEntity
    @Node("Movie")
public class MovieEntity {

	@Id @GeneratedValue(generatorRef = "myIdGenerator")
	private String id;

	private String name;
}

    使用业务键

    我们在完整示例的 MovieEntity 和 PersonEntity 中使用了业务主键。人员的姓名在构造时即被赋值，既由您的应用程序设置，也在使用 Spring Data 加载时进行设置。

    这只有在找到稳定且唯一的业务键时才可行，但它能创建出优秀的不可变领域对象。

    • 优势：使用业务键或自然键作为主键是合乎自然的。 该实体被明确标识，在后续领域建模中，它大多数情况下都显得恰到好处。

    • 缺点：一旦您发现所选的业务键并不像预期那样稳定，将其作为主键将难以更新。 很多时候，即使对方承诺不会变更，该键仍可能发生变化。 此外，找到真正具有唯一性的标识符本身也是一项难题。

    请注意，Spring Data Neo4j 在处理域实体之前，会始终为其设置业务键。这意味着它无法判断该实体是新创建的还是已存在的（除非同时提供了@Version字段），否则它将始终假设该实体是新的。
