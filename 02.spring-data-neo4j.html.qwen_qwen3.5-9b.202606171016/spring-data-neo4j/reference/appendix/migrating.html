    从 SDN+OGM 迁移到 SDN

    以往 SDN+OGM 迁移中存在的已知问题

    SDN+OGM 多年来经历了一段不平凡的发展历程，我们深知迁移大型应用系统既非易事，也无法立即带来收益。 在将旧版本的 Spring Data Neo4j 迁移到新版本时，我们观察到的主要问题大致如下：

    已跳过一次以上重大升级

    虽然 Neo4j-OGM 可以独立使用，但 Spring Data Neo4j 则不行。它很大程度上依赖于 Spring Data，进而依赖于 Spring Framework 本身，这最终会影响您应用程序的大部分组件。根据应用程序的结构方式——即有多少框架部分泄露到了业务代码中——您需要对应用程序进行相应调整的程度也会有所不同。如果您的应用程序中包含多个 Spring Data 模块，并且在同一服务层中同时访问关系型数据库和图数据库，情况会更加糟糕。更新两个对象映射框架绝非易事。

    依托通过 Spring Data 自身配置的嵌入式数据库

    在 SDN+OGM 项目中，嵌入式数据库由 Neo4j-OGM 进行配置。 如果您希望将 Neo4j 从 3.0 版本升级到 3.5 版本，则必须对整个应用程序进行升级，无法单独完成此操作。 这是为什么呢？ 由于您选择将数据库嵌入到应用程序中，因此您的应用与配置该嵌入式数据库的模块紧密耦合。 若要使用另一个版本的嵌入式数据库，就必须升级配置它的模块，因为旧版本模块不支持新版本的数据库。 由于始终存在与 Neo4j-OGM 相对应的 Spring Data 版本，因此您也必须对其进行升级。 然而，Spring Data 依赖于 Spring Framework，此时第一点中提到的限制条件同样适用。

    不确定应包含哪些构建模块

    要准确掌握这些术语并不容易。 我们在 这里 编写了 SDN+OGM 环境下的构建模块。 有可能所有这些依赖都是巧合地添加的，导致你面临大量相互冲突的依赖项。

    基于上述观察，我们建议在从 SDN+OGM 迁移到 SDN 之前，确保您的当前应用程序仅使用 Bolt 或 http 传输。 这样一来，您的应用程序及其访问层在很大程度上将独立于数据库的版本。 在此状态下，可以考虑从 SDN+OGM 迁移到 SDN。

    准备从 SDN+OGM Lovelace 或 SDN+OGM Moore 迁移到 SDN。

    Lovelace 发布系列对应 SDN 5.1.x 和 OGM 3.1.x，而Moore则对应 SDN 5.2.x 和 OGM 3.2.x。

    首先，您必须确保您的应用程序通过 Bolt 协议在服务器模式下与 Neo4j 交互，这意味着您需要满足以下三种情况中的两种：

    您已处于嵌入式环境中。

    您已在项目中添加了 org.neo4j:neo4j-ogm-embedded-driver 和 org.neo4j:neo4j，并通过 OGM 设施启动了数据库。 此方式已不再受支持，您需要配置标准的 Neo4j 服务器（同时支持独立部署和集群模式）。

    必须移除上述依赖项。

    从嵌入式解决方案迁移可能是最具挑战性的迁移，因为您还需要搭建服务器。 然而，这也是能为您带来最大价值的一种方案： 未来，您将能够独立升级数据库本身，而无需考虑您的应用程序框架以及数据访问框架。

    您正在使用 HTTP 传输

    您已添加 `org.neo4j:neo4j-ogm-http-driver` 并配置了类似 `user:password@localhost:7474` 的 URL。 该依赖需要替换为 `org.neo4j:neo4j-ogm-bolt-driver`，并且您需要配置一个 Bolt URL，例如 `bolt://localhost:7687`，或使用新的 `neo4j://` 方案，后者也能自动处理路由。

    您已经在间接使用 Bolt 了

    默认 SDN+OGM 项目使用 `org.neo4j:neo4j-ogm-bolt-driver`，因此间接使用了纯 Java 驱动。您可以保留现有的 URL。

    Migrating

    一旦确认您的 SDN+OGM 应用程序通过 Bolt 按预期运行，即可开始迁移至 SDN。

    • 移除所有 `org.neo4j:neo4j-ogm-*` 依赖项

    • 通过 `org.neo4j.ogm.config.Configuration` Bean 配置 SDN 不再受支持，所有驱动器的配置现在都需通过我们的新 Java 驱动器启动器进行。您尤其需要调整 URL 和身份验证相关的属性，请参阅旧属性与新属性的对比。

    无法通过 XML 配置 SDN。 如果您曾使用 SDN+OGM 应用程序进行此操作，请确保您已了解 Spring 应用程序的注解驱动或功能式配置方式。 目前最简便的选择是 Spring Boot。 借助我们的启动器，除了连接 URL 和认证信息外，所有必要的配置均已为您设置完毕。
    新旧房产对比
    # Old
spring.data.neo4j.embedded.enabled=false # No longer supported
spring.data.neo4j.uri=bolt://localhost:7687
spring.data.neo4j.username=neo4j
spring.data.neo4j.password=secret

# New
spring.neo4j.uri=bolt://localhost:7687
spring.neo4j.authentication.username=neo4j
spring.neo4j.authentication.password=secret
    这些新属性在未来可能会再次发生变化，届时 SDN 和驱动程序将最终完全取代旧版配置。

    最后，添加新的依赖项，有关 Gradle 和 Maven 的详细信息，请参阅入门指南。

    此时，您已准备好替换注释：

    Old New

    org.neo4j.ogm.annotation.NodeEntity

    org.springframework.data.neo4j.core.schema.Node

    org.neo4j.ogm.annotation.GeneratedValue

    org.springframework.data.neo4j.core.schema.GeneratedValue

    org.neo4j.ogm.annotation.Id

    org.springframework.data.neo4j.core.schema.Id

    org.neo4j.ogm.annotation.Property

    org.springframework.data.neo4j.core.schema.Property

    org.neo4j.ogm.annotation.Relationship

    org.springframework.data.neo4j.core.schema.Relationship

    org.springframework.data.neo4j.annotation.EnableBookmarkManagement

    无需替换，不必需要。

    org.springframework.data.neo4j.annotation.UseBookmark

    无需替换，不必需要。

    org.springframework.data.neo4j.annotation.QueryResult

    使用投影；不再支持任意结果映射。
    Several Neo4j-OGM annotations do not yet have a corresponding annotation in SDN, and some will never have one. We will add to the list above as we support additional features.

    书签管理

    @EnableBookmarkManagement 和 @UseBookmark，以及 org.springframework.data.neo4j.bookmark.BookmarkManager 接口及其唯一实现类 org.springframework.data.neo4j.bookmark.CaffeineBookmarkManager 已被移除且不再需要。

    SDN 无需配置即可为所有事务使用书签。您可以移除 `CaffeineBookmarkManager` 的 Bean 声明以及其对 `com.github.ben-manes.caffeine:caffeine` 的依赖。

    如果确实必须，您可以通过这些说明来禁用自动书签管理。

    约束和索引的自动创建

    SDN 5.3 及更早版本提供了来自 Neo4j-OGM 的“自动索引管理器”。

    @Index、@CompositeIndex 和 @Required 已被移除且无替代方案。 原因何在？ 我们认为，即使对于无模式数据库，构建模式也不属于领域建模的范畴。 有人可能会争辩说 SDN 模型本身就是模式，但我们的回答是：我们甚至更倾向于采用命令 - 查询分离原则， 这意味着我们更愿意定义独立的读写模型。 这些模型在编写“枯燥”的操作以及读取图形化结果时非常实用。

    除此之外，部分注解及其值与特定的 Neo4j 版本或发行版绑定，这使得维护变得困难。

    然而，最好的论证在于生产环境：虽然所有生成模式的工具在开发阶段确实很有用，尤其是对于强制严格模式的数据库而言，但在生产环境中它们往往并不那么友好：当不同版本的应用程序同时运行时该如何处理？例如，版本 A 断言由更新版本 B 创建的索引是否存在？

    我们认为，最好从一开始就掌控局面，并推荐使用受控的数据库迁移工具，例如 Liquigraph 或 Neo4j 迁移。后者已在 JHipster 项目中与 SDN 配合使用过。这两个项目的共同之处在于，它们都将当前模式的版本存储在数据库中，并在执行更新之前确保模式符合预期。

    从之前的 Neo4j-OGM 注解迁移会影响 `@Index`、`@CompositeIndex` 和 `@Required`，这些注解的使用示例在此给出：一个使用 Neo4j-OGM 自动索引管理器的类：

    一个使用 Neo4j-OGM 自动索引管理器的类
    import org.neo4j.ogm.annotation.CompositeIndex;
import org.neo4j.ogm.annotation.GeneratedValue;
import org.neo4j.ogm.annotation.Id;
import org.neo4j.ogm.annotation.Index;
import org.neo4j.ogm.annotation.Required;

@CompositeIndex(properties = {"tagline", "released"})
public class Movie {

    @Id @GeneratedValue Long id;

    @Index(unique = true)
    private String title;

    private String description;

    private String tagline;

    @Required
    private Integer released;
}

    其注释等效于以下 Cypher 方案（截至 Neo4j 4.2）：

    基于 Cypher 的迁移示例
    CREATE CONSTRAINT movies_unique_title ON (m:Movie) ASSERT m.title IS UNIQUE;
CREATE CONSTRAINT movies_released_exists ON (m:Movie) ASSERT EXISTS (m.released);
CREATE INDEX movies_tagline_released_idx FOR (m:Movie) ON (m.tagline, m.released);

    使用@Index而不设置unique = true等同于执行CREATE INDEX movie_title_index FOR (m:Movie) ON (m.title)。 请注意，唯一索引本身就隐含了普通索引。
