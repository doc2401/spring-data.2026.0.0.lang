    Couchbase 仓库

    Spring Data 仓储抽象的目标是显著减少为各种持久化存储实现数据访问层所需的样板代码量。

    默认情况下，如果操作是单文档操作且已知 ID，则使用键值对进行存储。对于其他所有操作，默认会生成 N1QL 查询，因此必须创建适当的索引以实现高效的数据访问。

    请注意，您可以为查询调整所需的最终一致性级别（参见使用一致性进行查询），并且可以配置由不同桶支持的不同存储库（参见[couchbase.repository.multibucket]）。

    Configuration

    虽然对仓库的支持始终存在，但您需要启用通用支持或针对特定命名空间进行启用。 如果您扩展了 `AbstractCouchbaseConfiguration`，只需使用 `@EnableCouchbaseRepositories` 注解即可。 它提供了许多选项来缩小或自定义搜索路径，其中最常用的选项之一是 `basePackages`。

    此外，请注意，如果您在 Spring Boot 内部运行，自动配置支持已为您设置好该注解，因此仅在需要覆盖默认值时才需要使用它。

    示例 1：基于注解的仓库配置
    @Configuration
@EnableCouchbaseRepositories(basePackages = {"com.couchbase.example.repos"})
public class Config extends AbstractCouchbaseConfiguration {
    //...
}

    高级用法在[couchbase.repository.multibucket]中描述。

    Usage

    在最简单的情况下，您的仓库将扩展 `CrudRepository`，其中 T 是您希望暴露的实体。 让我们看看一个用于 UserInfo 的仓库：

    示例 4。UserInfo 仓储
    import org.springframework.data.repository.CrudRepository;

public interface UserRepository extends CrudRepository<UserInfo, String> {
}

    请注意，这只是一个接口，而非实际的类。 在后台，当您的上下文初始化时，会创建您仓库描述的实际实现，您可以通过常规 Bean 访问它们。 这意味着您可以节省大量样板代码，同时仍向服务层和应用程序暴露完整的 CRUD 语义。

    现在，让我们想象一下，我们将 @Autowire 注解注入到使用它的类中。 我们有哪些可用的方法？

    表 1。UserRepository 中暴露的方法
    Method Description

    UserInfo 保存 (UserInfo 实体)

    保存给定实体。

    Iterable<UserInfo> save(Iterable<UserInfo> entity)

    保存实体列表。

    UserInfo findOne(String id)

    根据唯一 ID 查找实体。

    boolean exists(String id)

    根据唯一 ID 检查给定实体是否存在。

    Iterable<UserInfo> findAll()

    在该存储桶中查找所有此类型的实体。

    Iterable<UserInfo> findAll(Iterable<String> ids)

    根据此类型及给定的 ID 列表查找所有实体。

    长计数()

    统计桶中的实体数量。

    void delete(String id)

    根据 ID 删除实体。

    void 删除 (UserInfo 实体)

    删除该实体。

    void delete(Iterable entities)

    删除所有给定实体。

    void deleteAll()

    删除桶中所有指定类型的实体。

    太棒了！ 只需定义一个接口，即可在托管实体之上获得完整的 CRUD 功能。

    虽然暴露的方法为您提供了多种访问模式，但您经常需要定义自定义的模式。您可以通过向接口添加方法声明来实现这一点，这些声明将在后台自动解析为请求，我们将在接下来的章节中看到。

    存储库与查询

    基于 N1QL 的查询

    前提是在将实体存储的桶上已创建主索引。

    这是一个示例：

    示例 5：带有 N1QL 查询的扩展 UserInfo 存储库
    public interface UserRepository extends CrudRepository<UserInfo, String> {

    @Query("#{#n1ql.selectEntity} WHERE role = 'admin' AND #{#n1ql.filter}")
    List<UserInfo> findAllAdmins();

    List<UserInfo> findByFirstname(String fname);
}

    这里展示了两种基于 N1QL 的查询方式。

    第一种方法使用 `Query` 注解内联提供 N1QL 语句。 SpEL（Spring 表达式语言）支持在 `#{` 和 `}` 之间的 SpEL 表达式块中编写。 通过 SpEL 提供了几个 N1QL 特定的值：

    • #n1ql.selectEntity 可轻松确保语句将选择构建完整实体所需的所有字段（包括文档 ID 和 CAS 值）。

    • WHERE 子句中的 #n1ql.filter 添加了一个条件，用于匹配实体类型以及 Spring Data 用来存储类型信息的字段。

    • #n1ql.bucket 将被替换为存储该实体的桶的名称，并用反引号进行转义。

    • #n1ql.scope 将被替换为存储该实体的作用域名称，并用反引号进行转义。

    • #n1ql.collection 将被替换为存储该实体的集合名称，并用反引号进行转义。

    • #n1ql.fields 将被替换为重建该实体所需的字段列表（例如，用于 SELECT 子句）。

    • #n1ql.delete 将被替换为 delete from 语句。

    • #n1ql.returning 将被替换为重建实体所需的 RETURNING 子句。

    我们建议您始终使用 selectEntity SpEL 以及带有 filter SpEL 的 WHERE 子句（否则，您的查询可能会受到其他存储库中实体的影响）。

    基于字符串的查询支持参数化查询。您可以使用位置占位符（如"$1"），此时每个方法参数将按顺序映射到$1、$2、$3…；或者，您可以使用"$someString"语法来使用命名占位符。 方法参数将通过参数名称与其对应的占位符进行匹配。您可以通过为每个参数（除Pageable或Sort外）添加@Param注解来覆盖该名称（例如@Param("someString")）。 您不能在查询中混合使用这两种方法，否则将抛出IllegalArgumentException异常。

    请注意，您可以混合使用 N1QL 占位符和 SpEL。N1QL 占位符仍会考虑所有方法参数，因此请确保像下面的示例一样使用正确的索引：

    示例 6：混合使用 SpEL 和 N1QL 占位符的联行查询
    @Query("#{#n1ql.selectEntity} WHERE #{#n1ql.filter} AND #{[0]} = $2")
public List<User> findUsersByDynamicCriteria(String criteriaField, Object criteriaValue)

    这使得您只需声明一个方法，即可生成类似于 `AND name = "someName"` 或 `AND age = 3` 的查询。

    在 N1QL 查询中，您也可以执行单列投影（前提是仅选择一个字段并返回单个结果，通常是聚合函数如 COUNT、AVG、MAX…）。 此类投影具有简单的返回类型，例如 long、boolean 或 String。 此功能不适用于将结果投影到 DTO（数据传输对象）。

    另一个示例：
    #{#n1ql.selectEntity} WHERE #{#n1ql.filter} AND test = $1
    等同于
    SELECT #{#n1ql.fields} FROM #{#n1ql.collection} WHERE #{#n1ql.filter} AND test = $1

    Spring Security 中 SpEL 的实际应用

    当需要根据其他 Spring 组件（如 Spring Security）注入的数据执行查询时，SpEL 会非常有用。以下是扩展 SpEL 上下文以访问此类外部数据所需的操作步骤。

    首先，您需要实现一个EvaluationContextExtension（使用如下支持类）：

    class SecurityEvaluationContextExtension extends EvaluationContextExtensionSupport {

  @Override
  public String getExtensionId() {
    return "security";
  }

  @Override
  public SecurityExpressionRoot getRootObject() {
    Authentication authentication = SecurityContextHolder.getContext().getAuthentication();
    return new SecurityExpressionRoot(authentication) {};
  }
}

    只需在配置中声明相应的 Bean，Spring Data Couchbase 即可访问关联的 SpEL 值：

    @Bean
EvaluationContextExtension securityExtension() {
    return new SecurityEvaluationContextExtension();
}

    这可用于根据连接用户的角色来构建查询，例如：

    @Query("#{#n1ql.selectEntity} WHERE #{#n1ql.filter} AND " +
"role = '?#{hasRole('ROLE_ADMIN') ? 'public_admin' : 'admin'}'")
List<UserInfo> findAllAdmins(); //only ROLE_ADMIN users will see hidden admins

    删除查询示例：

    @Query("#{#n1ql.delete} WHERE #{#n1ql.filter} AND " +
"username = $1 #{#n1ql.returning}")
UserInfo removeUser(String username);

    第二种方法利用 Spring Data 的查询推导机制，根据方法名和参数构建 N1QL 查询。这将生成如下形式的查询：SELECT … FROM … WHERE firstName = "valueOfFnameAtRuntime"。您可以组合这些条件，甚至可以使用类似 countByFirstname 的名称进行计数，或使用类似 findFirst3ByLastname 的名称设置限制……

    实际上，生成的 N1QL 查询还会包含额外的 N1QL 条件，以确保仅选择与存储库实体类匹配的文档。

    您可以结合计数查询和[repositories.limit-query-result]功能使用此方法。

    使用 N1QL，存储库的另一种可能接口是 `PagingAndSortingRepository`（它扩展了 `CrudRepository`）。 它添加了两个方法：

    表 2。PagingAndSortingRepository 中暴露的方法
    Method Description

    Iterable findAll(Sort sort);

    支持根据实体的某个属性进行排序，同时检索所有相关实体。

    findAll(Pageable pageable);

    支持分页检索实体。返回的 Page 对象可方便地获取下一页的 Pageable 以及项目列表。首次调用时，请使用 new PageRequest(0, pageSize) 作为 Pageable。
    在使用基于 N1QL 的存储库时，您也可以将 Page 和 Slice 用作方法返回类型。
    如果内联查询中使用了分页和排序参数，则内联查询本身不应包含 ORDER BY、LIMIT 或 OFFSET 子句，否则服务器会因查询格式错误而拒绝该查询。

    自动索引管理

    默认情况下，预期用户会为其查询创建和管理最优索引。特别是在开发初期，自动创建索引以便快速启动可能会非常有用。

    对于 N1QL，提供以下注解，需要将其附加到实体（类或字段）上：

    • @QueryIndexed：置于字段上，表示该字段应包含在索引中。

    • @CompositeQueryIndex：标注在类上，表示应创建一个针对多个字段（复合）的索引。

    • @CompositeQueryIndexes：如果需要创建多个CompositeQueryIndex，此注解将接收一个包含它们的列表。

    例如，在实体上定义复合索引的方式如下：

    示例 7：对两个字段创建复合索引并指定排序顺序
    @Document
@CompositeQueryIndex(fields = {"id", "name desc"})
public class Airline {
   @Id
   String id;

	@QueryIndexed
	String name;

	@PersistenceConstructor
	public Airline(String id, String name) {
		this.id = id;
	}

	public String getId() {
		return id;
	}

	public String getName() {
		return name;
	}

}

    默认情况下，索引创建功能处于禁用状态。若需启用该功能，需在配置中覆盖此设置：

    示例 8：启用自动索引创建
    @Override
protected boolean autoIndexCreation() {
 return true;
}

    一致性查询

    默认情况下，使用 N1QL 的存储库查询采用NOT_BOUNDED扫描一致性。这意味着结果返回迅速，但索引中的数据可能尚未包含先前写入操作的数据（称为最终一致性）。如果您需要为查询实现“自己准备写入”的语义，则必须使用@ScanConsistency注解。示例如下：

    示例 9：使用不同的扫描一致性
    @Repository
public interface AirportRepository extends PagingAndSortingRepository<Airport, String> {

	@Override
	@ScanConsistency(query = QueryScanConsistency.REQUEST_PLUS)
	Iterable<Airport> findAll();

}

    DTO 投影

    通常情况下，Spring Data 存储库在使用查询方法时会返回领域模型。 然而，出于各种考虑，有时您可能需要对该模型的视图进行调整。 在本节中，您将学习如何定义投影，以提供资源的简化视图和精简视图。

    请查看以下领域模型：

    @Entity
public class Person {

  @Id @GeneratedValue
  private Long id;
  private String firstName, lastName;

  @OneToOne
  private Address address;
  …
}

@Entity
public class Address {

  @Id @GeneratedValue
  private Long id;
  private String street, state, country;

  …
}

    此Person具有多个属性：

    • `id` 为主键

    • firstName 和 lastName 是数据属性。

    • address 是另一个域对象的链接。

    现在假设我们创建一个相应的仓库，如下所示：

    interface PersonRepository extends CrudRepository<Person, Long> {

  Person findPersonByFirstName(String firstName);
}

    Spring Data 将返回包含所有属性的领域对象。 若要仅检索 `address` 属性，有两种选择。 其中一种是为 `Address` 对象定义一个仓库，如下所示：

    interface AddressRepository extends CrudRepository<Address, Long> {}

    在这种情况下，使用 PersonRepository 仍将返回完整的 Person 对象。 使用 AddressRepository 则仅返回 Address。

    但是，如果您完全不想暴露 `address` 详细信息该怎么办？您可以通过定义一个或多个投影来为您的仓储服务消费者提供替代方案。

    示例 10。简单投影
    interface NoAddresses {  (1)

  String getFirstName(); (2)

  String getLastName();  (3)
}

    该预测包含以下详细信息：

    1 一个普通的 Java 接口，使其具有声明性。
    2 导出 firstName。
    3 导出 lastName。

    `NoAddresses` 投影仅包含 `firstName` 和 `lastName` 的 getter，因此不会提供任何地址信息。 在这种情况下，查询方法定义返回的是 `NoAdresses`，而不是 `Person`。

    interface PersonRepository extends CrudRepository<Person, Long> {

  NoAddresses findByFirstName(String firstName);
}

    投影声明了基础类型与所暴露属性相关的方法签名之间的契约。因此，必须根据基础类型的属性名称来命名 getter 方法。如果基础属性的名称为firstName，则 getter 方法的名称必须是getFirstName；否则，Spring Data 将无法查找源属性。
