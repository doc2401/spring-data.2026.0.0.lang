    带标题的条件操作

    本节展示了 Spring Data REST 如何利用标准 HTTP 头来提升性能、实现操作的有条件执行，并为构建更复杂的前端提供支持。

    ETag, If-Match, and If-None-Match Headers

    ETag 响应头提供了一种对资源进行标记的方法。这不仅可以防止客户端之间相互覆盖，还可以减少不必要的请求。

    考虑以下示例：

    示例 1：带有版本号的可普通 Java 对象（POJO）
    class Sample {

	@Version Long version; (1)

	Sample(Long version) {
		this.version = version;
	}
}
    1 @Version 注解（如果您使用的是 Spring Data JPA，则为 JPA 的注解；对于其他模块，则为 Spring Data 的 org.springframework.data.annotation.Version）将该字段标记为版本标识符。

    在前面的示例中，当该 POJO 由 Spring Data REST 作为 REST 资源提供时，其 `ETag` 头的值即为版本字段的值。

    如果提供如下所示的 `If-Match` 头，我们可以条件性地对该资源执行 `PUT`、`PATCH` 或 `DELETE` 操作：

    curl -v -X PATCH -H 'If-Match: <value of previous ETag>' ...

    仅当资源的当前 `ETag` 状态与 `If-Match` 请求头匹配时，才会执行该操作。此保护机制可防止客户端之间相互覆盖。两个不同的客户端可以获取同一资源并获得相同的 `ETag`。如果其中一个客户端更新了该资源，响应中将返回一个新的 `ETag`。但第一个客户端仍持有旧的请求头。若该客户端尝试使用 `If-Match` 请求头进行更新，由于两者不再匹配，更新将失败；此时服务器会返回 HTTP `412 Precondition Failed` 消息。随后，该客户端可根据需要重新同步数据。

    “版本”一词在不同数据存储中可能具有不同的语义，甚至在同一应用程序内部也可能存在不同的含义。Spring Data REST 会委托给数据存储的元模型来判断某个字段是否已启用版本控制；如果是，则仅在 ETag 元素匹配时才允许执行列出的更新操作。

    If-None-Match 请求头提供了一种替代方案。与条件更新不同，If-None-Match 允许进行条件查询。考虑以下示例：

    curl -v -H 'If-None-Match: <value of previous etag>' ...

    上一条命令（默认情况下）执行一个 `GET` 请求。Spring Data REST 在执行 `GET` 时会检查 `If-None-Match` 请求头。如果该头的值与 ETag 匹配，则判定资源未发生变化，因此不会返回资源的副本，而是返回 HTTP `304 Not Modified` 状态码。从语义上讲，这意味着：“如果提供的头值与服务器端版本不匹配，则发送整个资源；否则，不发送任何内容。”

    此 POJO 源自基于 ETag 的单元测试，因此正如应用程序代码中预期的那样，它没有 @Entity（JPA）或 @Document（MongoDB）注解。它仅专注于带有 @Version 的字段如何导致生成 ETag 响应头。

    If-Modified-Since header

    `If-Modified-Since` 请求头提供了一种检查资源自上次请求以来是否已更新的方法，从而让应用程序避免重复发送相同的数据。考虑以下示例：

    示例 2。域类型中捕获的最后修改日期。
    @Document
public class Receipt {

	public @Id String id;
	public @Version Long version;
	public @LastModifiedDate Date date;  (1)

	public String saleItem;
	public BigDecimal amount;

}
    1 Spring Data Commons 的 @LastModifiedDate 注解支持以多种格式捕获此信息（包括 JodaTime 的 DateTime、旧版 Java 的 Date 和 Calendar、JDK8 日期/时间类型，以及 long/Long）。

    在上面的示例中，带有日期字段时，Spring Data REST 会返回一个类似于以下的 `Last-Modified` 响应头：

    Last-Modified: Wed, 24 Jun 2015 20:28:15 GMT

    该值可被捕获并用于后续查询，以避免在未更新的情况下重复获取相同数据，如下例所示：

    curl -H "If-Modified-Since: Wed, 24 Jun 2015 20:28:15 GMT" ...

    通过上述命令，您要求仅在资源自指定时间以来发生变化时才获取该资源。如果是这样，您将收到一个修订后的 `Last-Modified` 响应头，用于更新客户端；否则，您将收到 HTTP `304 Not Modified` 状态码。

    标题格式完美，以便将来查询时返回使用。

    请勿将不同的查询与响应头值混用，否则可能导致灾难性后果。仅在请求完全相同的 URI 和参数时，才使用响应头值。

    构建更高效的前端架构

    ETag 元素结合 If-Match 和 If-None-Match 请求头，可构建出更友好于用户数据计划和移动电池续航的前端。为此：

    1. 确定需要加锁的实体，并添加版本属性。

      HTML5 很好地支持 `data-*` 属性，因此可以将版本信息存储在 DOM 中（例如放在一个 `data-etag` 属性里）。

    2. 识别那些需要跟踪最新更新的条目。在获取这些资源时，将 `Last-Modified` 值存储到 DOM 中（例如使用 `data-last-modified`）。

    3. 在获取资源时，也请将 `self` URI 嵌入到您的 DOM 节点中（例如使用 `data-uri` 或 `data-self`），以便轻松返回到该资源。

    4. 调整PUT/PATCH/DELETE操作以使用If-Match，并处理HTTP412 Precondition Failed状态码。

    5. 调整GET操作以使用If-None-Match和If-Modified-Since，并处理HTTP304 Not Modified状态码。

    通过在您的 DOM（或原生移动应用的其它位置）中嵌入 `ETag` 元素和 `Last-Modified` 值，您可以减少数据消耗和电池电量消耗，避免重复获取相同内容。此外，您还可以避免与其他客户端发生冲突，并在需要协调差异时收到通知。

    通过这种方式，只需对前端稍作调整并进行一些实体级别的编辑，后端即可提供具有时效性的详细信息，助您在构建用户友好的客户端时充分利用这些资源。
