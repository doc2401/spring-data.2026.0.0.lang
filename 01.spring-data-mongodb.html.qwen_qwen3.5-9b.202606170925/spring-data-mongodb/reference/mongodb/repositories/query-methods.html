    MongoDB 专用查询方法

    您在存储库上通常触发的绝大多数数据访问操作都会导致在 MongoDB 数据库中执行查询。定义此类查询只需在存储库接口上声明一个方法，如下例所示：

    带有查询方法的 PersonRepository

    • Imperative

    • Reactive

    public interface PersonRepository extends PagingAndSortingRepository<Person, String> {

    List<Person> findByLastname(String lastname);                      (1)

    Page<Person> findByFirstname(String firstname, Pageable pageable); (2)

    Person findByShippingAddresses(Address address);                   (3)

    Person findFirstByLastname(String lastname);                       (4)

    Stream<Person> findAllBy();                                        (5)
}
    1 findByLastname 方法展示了查询所有具有给定姓氏的人的示例。该查询是通过解析方法名中的约束条件并拼接 And 和 Or 生成的。因此，该方法名会生成一个查询表达式 {"lastname" : lastname}。
    2 对查询应用分页功能。您可以在方法签名中添加一个 Pageable 参数，并让方法返回一个 Page 实例，Spring Data 会自动根据该参数对查询进行分页。
    3 展示了可以基于非基本类型属性进行查询。如果找到多个匹配项，将抛出 IncorrectResultSizeDataAccessException 异常。
    4 使用 First 关键字将查询限制为仅返回第一个结果。与 <3> 不同，如果找到多个匹配项，此方法不会抛出异常。
    5 使用 Java 8 Stream，在遍历流的过程中读取并转换单个元素。 
    public interface ReactivePersonRepository extends ReactiveSortingRepository<Person, String> {

    Flux<Person> findByFirstname(String firstname);                                   (1)

    Flux<Person> findByFirstname(Publisher<String> firstname);                        (2)

    Flux<Person> findByFirstnameOrderByLastname(String firstname, Pageable pageable); (3)

    Mono<Person> findByFirstnameAndLastname(String firstname, String lastname);       (4)

    Mono<Person> findFirstByLastname(String lastname);                                (5)
}
    1 该方法展示了查询所有具有给定 lastname 的人。该查询是通过解析方法名中的约束条件并拼接 And 和 Or 生成的。因此，方法名会生成一个查询表达式 {"lastname" : lastname}。
    2 该方法展示了在给定 Publisher 发出具有给定 firstname 的消息后，查询所有具有该 firstname 的人。
    3 使用 Pageable 将偏移量和排序参数传递给数据库。
    4 根据给定条件查找单个实体。如果结果不唯一，该方法将以 IncorrectResultSizeDataAccessException 异常结束。
    5 除非如第 4 点所述，否则即使查询返回更多结果文档，也会始终发出第一个实体。
    响应式仓库不支持 Page 返回类型（例如 Mono<Page>）。

    可以在派生查询方法中使用Pageable，将sort、limit和offset参数传递给查询，从而减少负载和网络流量。返回的Flux仅会在声明的范围内发射数据。

    Pageable page = PageRequest.of(1, 10, Sort.by("lastname"));
Flux<Person> persons = repository.findByFirstnameOrderByLastname("luke", page);
    不支持在领域类中引用映射为 DBRef 的参数。

    地理空间查询

    如前文关键词表所示，少数关键词可在 MongoDB 查询中触发地理空间操作。 Near 和 Within 这两个关键词允许进行进一步的修改，如下面的示例所示。

    下面的示例展示了如何使用不同的形状定义一个查找所有人员的near/within查询：

    Advanced Near queries

    • Imperative

    • Reactive

    public interface PersonRepository extends MongoRepository<Person, String> {

    // { 'location' : { '$near' : [point.x, point.y], '$maxDistance' : distance } }
    List<Person> findByLocationNear(Point location, Distance distance);

    // { 'location' : { $geoWithin: { $center: [ [ circle.center.x, circle.center.y ], circle.radius ] } } }
    List<Person> findByLocationWithin(Circle circle);

    // { 'location' : { $geoWithin: { $box: [ [ box.first.x, box.first.y ], [ box.second.x, box.second.y ] ] } } }
    List<Person> findByLocationWithin(Box box);

    // { 'location' : { $geoWithin: { $polygon: [ [ polygon.x1, polygon.y1 ], [ polygon.x2, polygon.y2 ], ... ] } } }
    List<Person> findByLocationWithin(Polygon polygon);

    // { 'location' : { $geoWithin: { $geometry: { $type : 'polygon', coordinates: [[ polygon.x1, polygon.y1 ], [ polygon.x2, polygon.y2 ], ... ] } } } }
    List<Person> findByLocationWithin(GeoJsonPolygon polygon);
}
    interface PersonRepository extends ReactiveMongoRepository<Person, String> {

    // { 'location' : { '$near' : [point.x, point.y], '$maxDistance' : distance } }
    Flux<Person> findByLocationNear(Point location, Distance distance);

    // { 'location' : { $geoWithin: { $center: [ [ circle.center.x, circle.center.y ], circle.radius ] } } }
    Flux<Person> findByLocationWithin(Circle circle);

    // { 'location' : { $geoWithin: { $box: [ [ box.first.x, box.first.y ], [ box.second.x, box.second.y ] ] } } }
    Flux<Person> findByLocationWithin(Box box);

    // { 'location' : { $geoWithin: { $polygon: [ [ polygon.x1, polygon.y1 ], [ polygon.x2, polygon.y2 ], ... ] } } }
    Flux<Person> findByLocationWithin(Polygon polygon);

    // { 'location' : { $geoWithin: { $geometry: { $type : 'polygon', coordinates: [[ polygon.x1, polygon.y1 ], [ polygon.x2, polygon.y2 ], ... ] } } } }
    Flux<Person> findByLocationWithin(GeoJsonPolygon polygon);
}

    在查询方法中添加Distance参数，可以限制结果仅包含给定距离内的数据。 如果Distance中设置了Metric，我们将透明地使用$nearSphere而非$geoWithin，如下例所示：

    示例 1. 使用Distance与Metrics
    Point point = new Point(43.7, 48.8);
Distance distance = new Distance(200, Metrics.KILOMETERS);
… = repository.findByLocationNear(point, distance);
// {'location' : {'$nearSphere' : [43.7, 48.8], '$maxDistance' : 0.03135711885774796}}
    响应式地理空间存储库查询支持域类型和 GeoResult<T> 结果，这些结果封装在响应式包装类型中。GeoPage 和 GeoResults 不被支持，因为它们与预先计算平均距离的延迟结果方法相矛盾。不过，您仍然可以传入一个 Pageable 参数来自行分页结果。

    使用带有Metric的Distance会导致添加$nearSphere子句（而不是普通的$near）。此外，实际距离将根据所使用的Metrics进行计算。

    请注意，Metric 并不指代公制单位。它可能是英里而非公里。相反，metric 指的是测量系统的概念，无论您使用哪种系统。

    在目标属性上使用 @GeoSpatialIndexed(type = GeoSpatialIndexType.GEO_2DSPHERE) 会强制使用 $nearSphere 操作符。

    • Imperative

    • Reactive

    public interface PersonRepository extends MongoRepository<Person, String> {

    // {'geoNear' : 'location', 'near' : [x, y] }
    GeoResults<Person> findByLocationNear(Point location);

    // No metric: {'geoNear' : 'person', 'near' : [x, y], maxDistance : distance }
    // Metric: {'geoNear' : 'person', 'near' : [x, y], 'maxDistance' : distance,
    //          'distanceMultiplier' : metric.multiplier, 'spherical' : true }
    GeoResults<Person> findByLocationNear(Point location, Distance distance);

    // Metric: {'geoNear' : 'person', 'near' : [x, y], 'minDistance' : min,
    //          'maxDistance' : max, 'distanceMultiplier' : metric.multiplier,
    //          'spherical' : true }
    GeoResults<Person> findByLocationNear(Point location, Distance min, Distance max);

    // {'geoNear' : 'location', 'near' : [x, y] }
    GeoResults<Person> findByLocationNear(Point location);
}
    interface PersonRepository extends ReactiveMongoRepository<Person, String>  {

    // {'geoNear' : 'location', 'near' : [x, y] }
    Flux<GeoResult<Person>> findByLocationNear(Point location);

    // No metric: {'geoNear' : 'person', 'near' : [x, y], maxDistance : distance }
    // Metric: {'geoNear' : 'person', 'near' : [x, y], 'maxDistance' : distance,
    //          'distanceMultiplier' : metric.multiplier, 'spherical' : true }
    Flux<GeoResult<Person>> findByLocationNear(Point location, Distance distance);

    // Metric: {'geoNear' : 'person', 'near' : [x, y], 'minDistance' : min,
    //          'maxDistance' : max, 'distanceMultiplier' : metric.multiplier,
    //          'spherical' : true }
    Flux<GeoResult<Person>> findByLocationNear(Point location, Distance min, Distance max);

    // {'geoNear' : 'location', 'near' : [x, y] }
    Flux<GeoResult<Person>> findByLocationNear(Point location);
}

    基于 JSON 的查询方法和字段限制

    通过在您的存储库查询方法上添加 `org.springframework.data.mongodb.repository.Query` 注解，您可以指定一个用于替代从方法名派生的 MongoDB JSON 查询字符串，如下例所示：

    • Imperative

    • Reactive

    public interface PersonRepository extends MongoRepository<Person, String> {

    @Query("{ 'firstname' : ?0 }")
    List<Person> findByThePersonsFirstname(String firstname);

}
    public interface PersonRepository extends ReactiveMongoRepository<Person, String> {

    @Query("{ 'firstname' : ?0 }")
    Flux<Person> findByThePersonsFirstname(String firstname);

}

    ?0 占位符允许您将方法参数中的值替换到 JSON 查询字符串中。

    String 参数值在绑定过程中会被转义，这意味着无法通过该参数添加 MongoDB 特定的操作符。

    此外，您还可以使用 filter 属性来限制映射到 Java 对象的属性集，如下例所示：

    • Imperative

    • Reactive

    public interface PersonRepository extends MongoRepository<Person, String> {

    @Query(value="{ 'firstname' : ?0 }", fields="{ 'firstname' : 1, 'lastname' : 1}")
    List<Person> findByThePersonsFirstname(String firstname);

}
    public interface PersonRepository extends ReactiveMongoRepository<Person, String> {

    @Query(value="{ 'firstname' : ?0 }", fields="{ 'firstname' : 1, 'lastname' : 1}")
    Flux<Person> findByThePersonsFirstname(String firstname);

}

    前面的示例中的查询仅返回 Person 对象的 firstname、lastname 和 Id 属性。 age 属性是一个 java.lang.Integer，未被设置，因此其值为 null。

    基于 JSON 的查询与 SpEL 表达式

    查询字符串和字段定义可与 SpEL 表达式结合使用，以在运行时创建动态查询。 SpEL 表达式可提供谓词值，并可用于通过子文档扩展谓词。

    表达式通过一个包含所有参数的数组来暴露方法参数。 以下查询使用 `[0]` 来声明 `lastname` 的谓词值（这与 `?0` 参数绑定等效）：

    • Imperative

    • Reactive

    public interface PersonRepository extends MongoRepository<Person, String> {

    @Query("{'lastname': ?#{[0]} }")
    List<Person> findByQueryWithExpression(String param0);
}
    public interface PersonRepository extends ReactiveMongoRepository<Person, String> {

    @Query("{'lastname': ?#{[0]} }")
    Flux<Person> findByQueryWithExpression(String param0);
}

    表达式可用于调用函数、求值条件语句以及构造值。 在 JSON 上下文中使用的 SpEL 表达式会揭示一种副作用，因为 SpEL 内部的类似 Map 的声明看起来就像 JSON，如下例所示：

    • Imperative

    • Reactive

    public interface PersonRepository extends MongoRepository<Person, String> {

    @Query("{'id': ?#{ [0] ? {$exists :true} : [1] }}")
    List<Person> findByQueryWithExpressionAndNestedObject(boolean param0, String param1);
}
    public interface PersonRepository extends ReactiveMongoRepository<Person, String> {

    @Query("{'id': ?#{ [0] ? {$exists :true} : [1] }}")
    Flux<Person> findByQueryWithExpressionAndNestedObject(boolean param0, String param1);
}
    在查询字符串中使用 SpEL 可以成为一种增强查询的强大方式。然而，它们也可能接受各种不需要的参数。请务必在将字符串传递给查询之前对其进行清理，以避免创建漏洞或对查询进行不需要的更改。

    表达式支持可通过查询 SPI 进行扩展：EvaluationContextExtension 和 ReactiveEvaluationContextExtension。 查询 SPI 可以贡献属性和函数，并自定义根对象。 扩展会在构建查询时执行 SpEL 评估的应用程序上下文中获取。 以下示例展示了如何使用评估上下文扩展：

    • Imperative

    • Reactive

    public class SampleEvaluationContextExtension extends EvaluationContextExtensionSupport {

    @Override
    public String getExtensionId() {
        return "security";
    }

    @Override
    public Map<String, Object> getProperties() {
        return Collections.singletonMap("principal", SecurityContextHolder.getCurrent().getPrincipal());
    }
}
    public class SampleEvaluationContextExtension implements ReactiveEvaluationContextExtension {

    @Override
    public String getExtensionId() {
        return "security";
    }

    @Override
    public Mono<? extends EvaluationContextExtension> getExtension() {
        return Mono.just(new EvaluationContextExtensionSupport() { ... });
    }
}
    自行引导 MongoRepositoryFactory 无法感知应用程序上下文，且需要额外配置以启用查询 SPI 扩展。
    响应式查询方法可以使用 org.springframework.data.spel.spi.ReactiveEvaluationContextExtension。

    全文搜索查询

    MongoDB 的全文搜索功能特定于存储，因此可以在 MongoRepository 中找到，而不是在更通用的 CrudRepository 中。 我们需要一个具有全文索引的文档（请参阅"文本索引"以了解如何创建全文索引）。

    MongoRepository 上的附加方法接受 TextCriteria 作为输入参数。除了这些显式方法外，还可以添加基于 TextCriteria 的存储库方法。这些条件会作为额外的 AND 条件被添加。一旦实体包含带有 @TextScore 注解的属性，就可以获取文档的全文本评分。此外，如以下示例所示，@TextScore 注解还使得能够根据文档的评分进行排序：

    @Document
class FullTextDocument {

  @Id String id;
  @TextIndexed String title;
  @TextIndexed String content;
  @TextScore Float score;
}

interface FullTextRepository extends Repository<FullTextDocument, String> {

  // Execute a full-text search and define sorting dynamically
  List<FullTextDocument> findAllBy(TextCriteria criteria, Sort sort);

  // Paginate over a full-text search result
  Page<FullTextDocument> findAllBy(TextCriteria criteria, Pageable pageable);

  // Combine a derived query with a full-text search
  List<FullTextDocument> findByTitleOrderByScoreDesc(String title, TextCriteria criteria);
}


Sort sort = Sort.by("score");
TextCriteria criteria = TextCriteria.forDefaultLanguage().matchingAny("spring", "data");
List<FullTextDocument> result = repository.findAllBy(criteria, sort);

criteria = TextCriteria.forDefaultLanguage().matching("film");
Page<FullTextDocument> page = repository.findAllBy(criteria, PageRequest.of(1, 1, sort));
List<FullTextDocument> result = repository.findByTitleOrderByScoreDesc("mongodb", criteria);

    聚合方法

    存储库层提供了通过注释的存储库查询方法与聚合框架交互的手段。与基于JSON 的查询类似，您可以使用org.springframework.data.mongodb.repository.Aggregation注解定义管道。该定义可以包含简单的占位符（如?0）以及SpEL 表达式?#{ … }。

    示例 2：聚合仓库方法
    public interface PersonRepository extends CrudRepository<Person, String> {

  @Aggregation("{ $group: { _id : $lastname, names : { $addToSet : $firstname } } }")
  List<PersonAggregate> groupByLastnameAndFirstnames();                            (1)

  @Aggregation("{ $group: { _id : $lastname, names : { $addToSet : $firstname } } }")
  List<PersonAggregate> groupByLastnameAndFirstnames(Sort sort);                   (2)

  @Aggregation("{ $group: { _id : $lastname, names : { $addToSet : ?0 } } }")
  List<PersonAggregate> groupByLastnameAnd(String property);                       (3)

  @Aggregation("{ $group: { _id : $lastname, names : { $addToSet : ?0 } } }")
  Slice<PersonAggregate> groupByLastnameAnd(String property, Pageable page);       (4)

  @Aggregation("{ $group: { _id : $lastname, names : { $addToSet : $firstname } } }")
  Stream<PersonAggregate> groupByLastnameAndFirstnamesAsStream();                  (5)

  @Aggregation(pipeline = {
      "{ '$match' :  { 'lastname' :  '?0'} }",
      "{ '$project': { _id : 0, firstname : 1, lastname : 1 } }"
  })
  Stream<PersonAggregate> groupByLastnameAndFirstnamesAsStream();                  (6)

  @Aggregation("{ $group : { _id : null, total : { $sum : $age } } }")
  SumValue sumAgeUsingValueWrapper();                                              (7)

  @Aggregation("{ $group : { _id : null, total : { $sum : $age } } }")
  Long sumAge();                                                                   (8)

    示例查询

    Introduction

    本章介绍示例查询（Query by Example）并解释如何使用它。

    示例查询（QBE）是一种用户友好的查询技术，具有简洁的界面。它支持动态创建查询，无需编写包含字段名称的查询语句。事实上，使用示例查询完全不需要您通过特定于存储的查询语言来编写查询。

    本章介绍查询示例（Query by Example）的核心概念。 相关信息源自 Spring Data Commons 模块。 根据您的数据库不同，字符串匹配支持可能受到限制。

    Usage

    Query by Example API 由四个部分组成：

    • 探针：一个具有已填充字段的领域对象的实际示例。

    • ExampleMatcher：该 ExampleMatcher 包含匹配特定字段的详细信息。它可以在多个示例中重复使用。

    • 示例：一个示例由探针和示例匹配器组成。它用于创建查询。

    • FetchableFluentQuery：一个 FetchableFluentQuery 提供流式 API，允许对源自 Example 的查询进行进一步定制。使用流式 API 可指定查询的排序、投影及结果处理方式。

    示例查询适用于多种使用场景：

    • 使用一组静态或动态约束查询您的数据存储。

    • 无需担心破坏现有查询，即可频繁重构领域对象。

    • 独立于底层数据存储 API 工作。

    基于示例的方法也存在一些局限性：

    • 不支持嵌套或分组属性约束，例如firstname = ?0 or (firstname = ?1 and lastname = ?2)。

    • 针对字符串匹配的存储特定支持。 根据您的数据库，字符串匹配可支持字符串的起始、包含、结尾或正则表达式匹配。

    • 其他属性类型的精确匹配。

    在开始使用示例查询之前，您需要拥有一个领域对象。 要开始操作，请按照以下示例为您的仓库创建一个接口：

    示例人员对象
    public class Person {

  @Id
  private String id;
  private String firstname;
  private String lastname;
  private Address address;

  // … getters and setters omitted
}

    前面的示例展示了一个简单的领域对象。 您可以使用它来创建一个 `Example`。 默认情况下，值为 `null` 的字段会被忽略，而字符串则使用存储特定的默认值进行匹配。

    将属性纳入 Query by Example 标准是基于属性的可空性。使用基本类型（int、double 等）的属性始终会被包含，除非 ExampleMatcher 忽略该属性路径。

    示例可以通过使用 `of` 工厂方法或使用 ExampleMatcher 来构建。Example 是不可变的。 以下示例展示了一个简单的 Example：

    示例 3：简单示例
    Person person = new Person();                         (1)
person.setFirstname("Dave");                          (2)

Example<Person> example = Example.of(person);         (3)
    1 创建域对象的新实例。
    2 设置要查询的属性。
    3 创建 Example 对象。

    您可以使用仓库运行示例查询。为此，让您的仓库接口扩展QueryByExampleExecutor<T>。以下列表展示了QueryByExampleExecutor接口的摘录：

    The QueryByExampleExecutor

}

    4 构造一个新的 ExampleMatcher 以忽略 lastname 属性路径。

    流式 API

    QueryByExampleExecutor 定义了流式查询方法，用于基于 Example 实例灵活执行查询，其接口为 findBy(Example<S> example, Function<FluentQuery.FetchableFluentQuery<S>, R> queryFunction)。

    与其他方法一样，它执行一个由 `Example` 派生的查询。 然而，查询函数允许您控制其他动态方式无法控制的查询执行方面。 您可以通过调用 `FetchableFluentQuery` 的各种中间和终端方法来实现这一点。

    中级方法

    • sortBy：对结果应用排序。重复调用该方法会追加每个Sort（请注意，使用已排序的Pageable的page(Pageable)会覆盖任何之前的排序顺序）。

    • limit：限制结果数量。

    • as：指定要读取或投影的类型。

    • project：限制查询属性。

    终端方法

    • first 和 firstValue：返回第一个值。如果查询未产生任何结果，first 将返回一个 Optional<T> 或 Optional.empty()。firstValue 是其无需使用 Optional 的可为 null 变体。

    • one、oneValue：返回单个值。若查询未产生任何结果，one 将返回 Optional<T> 或 Optional.empty()。oneValue 是其可空变体，无需使用 Optional。如果找到多个匹配项，则抛出 IncorrectResultSizeDataAccessException。

    • all：返回所有结果作为 List<T>。

    • page(Pageable)：返回所有结果作为 Page<T>。

    • slice(Pageable)：返回所有结果作为 Slice<T>。

    • scroll(ScrollPosition)：使用滚动（偏移量、键集）以 Window<T> 的形式检索结果。

    • stream()：返回一个用于惰性处理结果的 Stream<T>。 该流是有状态的，使用后必须关闭。

    • count 和 exists：返回匹配实体的数量或是否存在任何匹配项。

    中间方法和终端方法必须在查询函数内调用。
    示例 5。使用流式 API 获取按 lastname 排序的投影 Page。
    Page<CustomerProjection> page = repository.findBy(example,
    q -> q.as(CustomerProjection.class)
          .page(PageRequest.of(0, 20, Sort.by("lastname")))
);
    示例 6：使用流式 API 获取按 lastname 排序的多个结果中的最后一个。
    Optional<Customer> match = repository.findBy(example,
    q -> q.sortBy(Sort.by("lastname").descending())
          .first()
);

    Scrolling

    滚动是一种更细粒度的方法，用于遍历大型结果集的各个数据块。 滚动包含稳定排序、滚动类型（基于偏移量或基于键集的滚动）以及结果限制。 您可以通过使用属性名称定义简单的排序表达式，并通过查询推导使用 Top 或 First 关键字 定义静态的结果限制。 您可以连接表达式以将多个条件收集到一个表达式中。

    滚动查询返回一个 `Window<T>`，允许获取元素的滚动位置以获取下一个 `Window<T>`，直到您的应用程序消耗完整个查询结果。 类似于通过获取下一批结果来消费 Java 的 `Iterator<List<…>>`，查询结果滚动让您可以通过 `ScrollPosition` 访问位置，方式如下所示：

    Window<User> users = repository.findFirst10ByLastnameOrderByFirstname("Doe", ScrollPosition.offset());
do {

  for (User u : users) {
    // consume the user
  }

  if (users.isLast() || users.isEmpty()) {
    break;
  }

  // obtain the next Scroll
  users = repository.findFirst10ByLastnameOrderByFirstname("Doe", users.positionAt(users.size() - 1));
} while (!users.isEmpty());

    `ScrollPosition` 标识了包含整个查询结果的元素的确切位置。 查询执行将位置参数视为排他性的，结果将从给定位置之后开始返回。 `ScrollPosition#offset()` 和 `ScrollPosition#keyset()` 是 `ScrollPosition` 的特殊形式，用于指示滚动操作的起始点。

    上述示例展示了静态排序和限制。 您可以定义替代的查询方法，接受一个 `Sort` 对象以定义更复杂的排序顺序，或按请求进行排序。 同样地，提供一个 `Limit` 对象允许您按请求动态设置限制，而不是应用静态限制。 有关动态排序和限制的更多信息，请参阅查询方法详情。

    遍历并消费Window实例需要大量的条件判断才能达到最优的数据库往返性能，这很容易变成一项重复性工作，而使用WindowIterator可以简化这一过程。

    `WindowIterator` 提供了一个实用工具，通过消除检查下一个 `Window` 是否存在并应用 `ScrollPosition` 的需求，从而简化了在多个 `Window` 之间滚动浏览的操作。

    WindowIterator<User> users = WindowIterator.of(position -> repository.findFirst10ByLastnameOrderByFirstname("Doe", position))
  .startingAt(ScrollPosition.offset());

while (users.hasNext()) {
  User u = users.next();
  // consume the user
}

    使用偏移量进行滚动

    偏移分页类似于传统分页，它使用一个偏移量（Offset）计数器来跳过指定数量的结果，并让数据源仅返回从给定偏移量开始的结果。 这种简单的机制可以避免向客户端应用程序发送大量数据。 然而，大多数数据库要求在服务器返回结果之前，必须先将完整的查询结果物化到内存中。

    示例 8：在仓储查询方法中使用OffsetScrollPosition
    interface UserRepository extends Repository<User, Long> {

  Window<User> findFirst10ByLastnameOrderByFirstname(String lastname, OffsetScrollPosition position);
}

WindowIterator<User> users = WindowIterator.of(position -> repository.findFirst10ByLastnameOrderByFirstname("Doe", position))
  .startingAt(OffsetScrollPosition.initial()); (1)
    1 从偏移量为 0 开始，以包含位置 0 处的元素。

    `ScrollPosition.offset()` 与 `ScrollPosition.offset(0L)` 之间存在区别。前者表示滚动操作的起始位置，指向一个未指定的偏移量；而后者则标识结果中的第一个元素（位于位置 `0`）。鉴于滚动的**独占性**，使用 `ScrollPosition.offset(0)` 会跳过第一个元素并将其转换为偏移量 `1`。

    使用键集过滤进行滚动

    基于偏移量的滚动要求大多数数据库在服务器返回结果之前，先将整个结果集物化。因此，虽然客户端仅能看到请求结果的一部分，但您的服务器仍需构建完整的结果集，从而导致额外的负载。

    键集过滤方法通过利用数据库的内置功能实现子集检索，旨在降低单个查询的计算和 I/O 需求。 该方法维护一组用于恢复滚动操作的键，通过将键传入查询来有效修改过滤条件。

    Keyset-Filtering 的核心思想是利用稳定的排序顺序开始检索结果。当你想要滚动到下一批数据时，会获取一个 ScrollPosition，该位置用于在已排序的结果中重建当前位置。ScrollPosition 捕获了当前 Window 内最后一个实体的键集（keyset）。执行查询时，重建过程会将条件子句重写为包含所有排序字段和主键，以便数据库能够利用潜在的索引来运行查询。数据库只需根据给定的键集位置构建一个较小的结果集，而无需完全生成一个大结果集再跳过部分结果直到达到特定的偏移量。

    键集过滤要求用于排序的键属性必须为非空值。此限制是由于存储特定比较操作符对null值的处理方式以及需要在索引源上运行查询所导致的。对可空属性进行键集过滤将导致意外结果。
    使用 KeysetScrollPosition 与仓储查询方法
    interface UserRepository extends Repository<User, Long> {

  Window<User> findFirst10ByLastnameOrderByFirstname(String lastname, KeysetScrollPosition position);
}

WindowIterator<User> users = WindowIterator.of(position -> repository.findFirst10ByLastnameOrderByFirstname("Doe", position))
  .startingAt(ScrollPosition.keyset()); (1)
    1 从头开始，不要应用额外的过滤。

    当数据库中存在与排序字段匹配的索引时，键集过滤效果最佳，因此静态排序非常适用。 应用键集过滤的滚动查询要求查询返回用于排序顺序的属性，并且这些属性必须在返回的实体中进行映射。

    您可以使用接口和 DTO 投影，但请确保包含所有已排序的属性，以避免键集提取失败。

    在指定 `Sort` 顺序时，只需包含与查询相关的排序属性即可；如果您不希望确保查询结果唯一，则无需为此操心。键集查询机制会通过添加主键（或复合主键的其余部分）来修正您的排序顺序，从而保证每个查询结果都是唯一的。

List<Person> findByFirstname(String firstname);
    1 使用名为lastname-idx的索引。
    2 @Query注解定义了与添加@Hint注解等效的hint别名。

    有关索引创建的更多信息，请参阅集合管理部分。

    排序规则支持

    在通用排序支持存储库旁边，允许为各种操作定义排序规则。

    public interface PersonRepository extends MongoRepository<Person, String> {

  @Query(collation = "en_US")  (1)
  List<Person> findByFirstname(String firstname);

  @Query(collation = "{ 'locale' : 'en_US' }") (2)
  List<Person> findPersonByFirstname(String firstname);

  @Query(collation = "?1") (3)
  List<Person> findByFirstname(String firstname, Object collation);

  @Query(collation = "{ 'locale' : '?1' }") (4)
  List<Person> findByFirstname(String firstname, String collation);

  List<Person> findByFirstname(String firstname, Collation collation); (5)

  @Query(collation = "{ 'locale' : 'en_US' }")
  List<Person> findByFirstname(String firstname, @Nullable Collation collation); (6)
}
    1 静态排序定义，结果为 { 'locale' : 'en_US' }。
    2 静态排序定义，结果为 { 'locale' : 'en_US' }。
    3 动态排序，取决于第二个方法参数。允许的类型包括 String（例如 'en_US'）、Locale（例如 Locale.US）和 Document（例如 new Document("locale", "en_US")）。
    4 动态排序，取决于第二个方法参数。
    5 将 Collation 方法参数应用于查询。
    6 如果非空，Collation 方法参数将覆盖 @Query 中的默认 collation。
    如果您为仓库查找方法启用了自动索引创建，则在创建索引时可能会包含一个潜在的静态排序定义，如 (1) 和 (2) 所示。
    最具体的 Collation 可能覆盖其他定义。这意味着方法参数注解优先于查询方法注解，而查询方法注解又优先于领域类型注解。

    为简化代码库中排序属性的使用，还可以使用@Collation 注解，该注解是上述注解的元注解。 相同的规则和适用位置同样有效，此外，直接使用@Collation 会覆盖在@Query 和其他注解上定义的排序值。 这意味着，如果通过@Query 和@Collation 都声明了排序属性，则优先采用@Collation 中定义的排序方式。

    示例 10。使用@Collation
    @Collation("en_US") (1)
class Game {
  // ...
}

interface GameRepository extends Repository<Game, String> {

  @Collation("en_GB")  (2)
  List<Game> findByTitle(String title);

  @Collation("de_AT")  (3)
  @Query(collation="en_GB")
  List<Game> findByDescriptionContaining(String keyword);
}
    1 不再使用 @Document(collation=…​)。
    2 不再使用 @Query(collation=…​)。
    3 优先采用 @Collation，而非元数据用法。

    读取偏好设置

    @ReadPreference 注解允许您配置 MongoDB 的读取偏好。

    示例 11。读偏好示例
    @ReadPreference("primaryPreferred") (1)
public interface PersonRepository extends CrudRepository<Person, String> {

    @ReadPreference("secondaryPreferred") (2)
    List<Person> findWithReadPreferenceAnnotationByLastname(String lastname);

    @Query(readPreference = "nearest") (3)
    List<Person> findWithReadPreferenceAtTagByFirstname(String firstname);

    List<Person> findWithReadPreferenceAtTagByFirstname(String firstname); (4)
    1 为所有未定义查询级别读取偏好的仓库操作（包括继承的和非自定义实现的操作）配置读取偏好。因此，在这种情况下，读取偏好模式将设置为primaryPreferred。
    2 使用注解ReadPreference中定义的读取偏好模式，在本例中为secondaryPreferred。
    3 @Query注解定义了read preference mode别名，其效果等同于添加@ReadPreference注解。
    4 此查询将使用仓库中定义的读取偏好模式。

    `MongoOperations` 和 `Query` API 为 `ReadPreference` 提供了更细粒度的控制。
