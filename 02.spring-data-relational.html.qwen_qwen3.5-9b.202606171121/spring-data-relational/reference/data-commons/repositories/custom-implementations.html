    自定义仓库实现

    Spring Data 提供了多种选项，只需少量代码即可创建查询方法。 但当这些选项无法满足您的需求时，您也可以为存储库方法提供自定义实现。 本节将介绍如何实现这一点。

    自定义单个仓库

    若要为存储库添加自定义功能，首先必须定义该自定义功能的片段接口及其实现方式，如下所示：

    自定义仓库功能的接口
    interface CustomizedUserRepository {
  void someCustomMethod(User user);
}
    自定义仓储功能的实现
    class CustomizedUserRepositoryImpl implements CustomizedUserRepository {

  @Override
  public void someCustomMethod(User user) {
    // Your custom implementation
  }
}

    类名中与片段接口相对应的最重要部分是 `Impl` 后缀。您可以通过设置 `@Enable<StoreModule>Repositories(repositoryImplementationPostfix = …)` 来自定义特定于存储的后缀。

    历史上，Spring Data 自定义存储库实现的发现遵循一种命名模式，该模式从存储库派生自定义实现类的名称，从而有效地支持单个自定义实现。

    与存储库接口位于同一包中、且名称匹配存储库接口名称后跟实现后缀的类型，被视为自定义实现，并将作为自定义实现进行处理。遵循该命名规则可能导致意外行为。

    我们已将单自定义实现命名标记为弃用，并建议不再使用此模式。 请改用基于片段的编程模型进行迁移。

    实现本身并不依赖于 Spring Data，可以是一个普通的 Spring Bean。因此，您可以使用标准的依赖注入行为来注入对其他 Bean 的引用（例如JdbcTemplate），参与切面等。

    然后，您可以让仓库接口扩展片段接口，如下所示：

    您的仓库接口已更新
    interface UserRepository extends CrudRepository<User, Long>, CustomizedUserRepository {

  // Declare query methods here
}

    通过用您的仓储接口扩展片段接口，可以将 CRUD 功能和自定义功能结合起来，并使其可供客户端使用。

    Spring Data 仓库通过片段实现，这些片段共同构成仓库组合。 片段包括基础仓库、功能方面（例如 Querydsl）以及自定义接口及其实现。 每次向您的仓库接口添加一个接口时，都会通过添加一个片段来增强该组合。 基础仓库和仓库方面实现由每个 Spring Data 模块提供。

    以下示例展示了自定义接口及其实现：

    带有其实现的片段
    interface HumanRepository {
  void someHumanMethod(User user);
}

class HumanRepositoryImpl implements HumanRepository {

  @Override
  public void someHumanMethod(User user) {
    // Your custom implementation
  }
}

interface ContactRepository {

  void someContactMethod(User user);

  User anotherContactMethod(User user);
}

class ContactRepositoryImpl implements ContactRepository {

  @Override
  public void someContactMethod(User user) {
    // Your custom implementation
  }

  @Override
  public User anotherContactMethod(User user) {
    // Your custom implementation
  }
}

    以下示例展示了扩展 CrudRepository 的自定义仓库接口：

    您的仓库接口已更新
    interface UserRepository extends CrudRepository<User, Long>, HumanRepository, ContactRepository {

  // Declare query methods here
}

    仓库可以由多个自定义实现组成，这些实现按照其声明的顺序进行导入。 自定义实现的优先级高于基础实现和仓库切面。 这种排序允许您覆盖基础仓库和切面方法，并在两个片段提供相同的方法签名时解决歧义。 仓库片段不仅限于在单个仓库接口中使用。 多个仓库可以使用同一个片段接口，从而让您在不同仓库之间复用自定义功能。

    以下示例展示了一个仓库片段及其实现：

    覆盖 `save(…)` 的片段
    interface CustomizedSave<T> {
  <S extends T> S save(S entity);
}

class CustomizedSaveImpl<T> implements CustomizedSave<T> {

  @Override
  public <S extends T> S save(S entity) {
    // Your custom implementation
  }
}

    以下示例展示了使用前述仓库片段的仓库：

    自定义存储库接口
    interface UserRepository extends CrudRepository<User, Long>, CustomizedSave<User> {
}

interface PersonRepository extends CrudRepository<Person, Long>, CustomizedSave<Person> {
}

    Configuration

    仓库基础设施会尝试通过扫描位于发现仓库所在包之下的类来自动检测自定义实现片段。这些类需要遵循命名约定，即在名称后追加后缀，默认后缀为Impl。

    以下示例展示了一个使用默认后缀的仓库，以及一个为后缀设置自定义值的仓库：

    示例 1。配置示例

    • Java

    • XML

    @EnableJpaRepositories(repositoryImplementationPostfix = "MyPostfix")
class Configuration { … }
    <repositories base-package="com.acme.repository" />

<repositories base-package="com.acme.repository" repository-impl-postfix="MyPostfix" />

    前一个示例尝试查找名为com.acme.repository.CustomizedUserRepositoryImpl的类，以作为自定义仓库实现。第二个示例则尝试查找com.acme.repository.CustomizedUserRepositoryMyPostfix。

    歧义解析

    如果在不同的包中发现了多个具有相同类名的实现，Spring Data 将使用 Bean 名称来确定使用哪一个。

    鉴于之前展示的CustomizedUserRepository的两个自定义实现，将使用第一个实现。其 Bean 名称为customizedUserRepositoryImpl，该名称由片段接口（CustomizedUserRepository）的名称加上后缀Impl组成。

    示例 2：歧义实现的解析
    class CustomizedUserRepositoryImpl implements CustomizedUserRepository {

  // Your custom implementation
}
    @Component("specialCustomImpl")
class CustomizedUserRepositoryImpl implements CustomizedUserRepository {

  // Your custom implementation
}

    如果将 `UserRepository` 接口注解为 `@Component("specialCustom")`，则生成的 Bean 名称加上 `Impl` 后缀后，将与 `com.acme.impl.two` 中定义的仓库实现类匹配，从而优先使用该实现而非第一个。

    手动接线

    如果您的自定义实现仅使用基于注解的配置和自动装配，则上述方法非常有效，因为它被视为任何其他 Spring Bean。 如果您的实现片段 Bean 需要特殊的装配方式，您可以声明该 Bean，并按照前文所述的约定对其进行命名。 此时，基础设施将不再自行创建 Bean 定义，而是通过名称引用您手动定义的 Bean 定义。 以下示例展示了如何手动装配自定义实现：

    示例 3：自定义实现的接线

    • Java

    • XML

    class MyClass {
  MyClass(@Qualifier("userRepositoryImpl") UserRepository userRepository) {
    …
  }
}
    <repositories base-package="com.acme.repository" />

<beans:bean id="userRepositoryImpl" class="…">
  <!-- further configuration -->
</beans:bean>

    使用 spring.factories 注册片段

    如配置部分所述，基础设施仅在仓库基础包内自动检测片段。因此，如果位于其他位置或由外部归档贡献的片段不具有共同的命名空间，则不会被发现。通过在spring.factories中注册片段，可以绕过此限制，具体说明如下。

    假设您希望为您的组织提供一套可跨多个仓库使用的自定义搜索功能，并利用文本搜索索引来实现。

    首先，你需要定义一个 Fragment 接口。 请注意泛型参数 `<T>`，它用于将 Fragment 与仓库的领域类型对齐。

    片段接口
    public interface SearchExtension<T> {

    List<T> search(String text, Limit limit);
}

    假设实际的全文搜索功能通过一个名为SearchService的服务提供，该服务已在上下文中注册为Bean，因此您可以在我们的SearchExtension实现中调用它。 执行搜索所需的全部信息仅为集合（或索引）名称以及一个对象映射器，该映射器可将搜索结果转换为实际的领域对象，具体方案如下所示。

    片段实现
    import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.data.domain.Limit;
import org.springframework.data.repository.core.RepositoryMethodContext;

class DefaultSearchExtension<T> implements SearchExtension<T> {

    private final SearchService service;

    DefaultSearchExtension(SearchService service) {
        this.service = service;
    }

    @Override
    public List<T> search(String text, Limit limit) {
        return search(RepositoryMethodContext.getContext(), text, limit);
    }

    List<T> search(RepositoryMethodContext metadata, String text, Limit limit) {

        Class<T> domainType = metadata.getRepository().getDomainType();

        String indexName = domainType.getSimpleName().toLowerCase();
        List<String> jsonResult = service.search(indexName, text, 0, limit.max());

        return jsonResult.stream().map(…).collect(toList());
    }
}

    在上面的示例中，使用 RepositoryMethodContext.getContext() 来获取实际方法调用的元数据。 RepositoryMethodContext 暴露了附加到存储库的信息，例如领域类型。 在这种情况下，我们使用存储库的领域类型来识别要搜索的索引名称。

    暴露调用元数据成本较高，因此默认情况下该功能被禁用。 若要访问 `RepositoryMethodContext.getContext()`，您需要建议负责创建实际仓库的工厂类以暴露方法元数据。

    暴露仓库元数据

    • 标记接口

    • Bean 后置处理器

    将 `RepositoryMetadataAccess` 标记接口添加到片段实现中，将触发基础设施并启用这些使用该片段的存储库的元数据暴露功能。

    import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.data.domain.Limit;
import org.springframework.data.repository.core.support.RepositoryMetadataAccess;
import org.springframework.data.repository.core.RepositoryMethodContext;

class DefaultSearchExtension<T> implements SearchExtension<T>, RepositoryMetadataAccess {

    // ...
}

    可以通过 `BeanPostProcessor` 直接在仓库工厂 Bean 上设置 `exposeMetadata` 标志。

    import org.springframework.beans.factory.config.BeanPostProcessor;
import org.springframework.context.annotation.Configuration;
import org.springframework.data.repository.core.support.RepositoryFactoryBeanSupport;

@Configuration
class MyConfiguration {

    @Bean
    static BeanPostProcessor exposeMethodMetadata() {

        return new BeanPostProcessor() {

            @Override
            public Object postProcessBeforeInitialization(Object bean, String beanName) {

                if(bean instanceof RepositoryFactoryBeanSupport<?,?,?> factoryBean) {
                    factoryBean.setExposeMetadata(true);
                }
                return bean;
            }
        };
    }
}

    请勿直接复制/粘贴上述内容，而应考虑您的实际使用场景，可能需要更精细的方法，因为上述方法将简单地启用所有仓库中的该标志。

    同时拥有片段声明和实现后，您可以在 `META-INF/spring.factories` 文件中注册扩展，并在需要时进行打包。

    在 `META-INF/spring.factories` 中注册该片段。
    com.acme.search.SearchExtension=com.acme.search.DefaultSearchExtension

    现在您已准备好使用您的扩展；只需将接口添加到您的代码库中即可。

    使用它
    import com.acme.search.SearchExtension;
import org.springframework.data.repository.CrudRepository;

interface MovieRepository extends CrudRepository<Movie, String>, SearchExtension<Movie> {

}

    自定义基础仓库

    前面一节中描述的方法要求，当需要自定义基础仓库行为以影响所有仓库时，必须对每个仓库接口进行定制。 若要改为统一更改所有仓库的行为，可以创建一个继承自特定持久化技术仓库基类的实现类。 该类随后将作为仓库代理的自定义基类，如下例所示：

    自定义仓库基类
    class MyRepositoryImpl<T, ID>
  extends SimpleJpaRepository<T, ID> {

  private final EntityManager entityManager;

  MyRepositoryImpl(JpaEntityInformation entityInformation,
                          EntityManager entityManager) {
    super(entityInformation, entityManager);

    // Keep the EntityManager around to used from the newly introduced methods.
    this.entityManager = entityManager;
  }

  @Override
  @Transactional
  public <S extends T> S save(S entity) {
    // implementation goes here
  }
}
    该类需要包含一个由特定存储仓库工厂实现所使用的超类构造函数。 如果仓库基类有多个构造函数，请重写接受 EntityInformation 以及特定存储基础设施对象（例如 EntityManager 或模板类）的那个构造函数。

    最后一步是让 Spring Data 基础设施识别自定义的仓库基类。在配置中，可以通过使用 `repositoryBaseClass` 来实现，如下例所示：

    示例 4：配置自定义仓库基类

    • Java

    • XML

    @Configuration
@EnableJpaRepositories(repositoryBaseClass = MyRepositoryImpl.class)
class ApplicationConfiguration { … }
    <repositories base-package="com.acme.repository"
     base-class="….MyRepositoryImpl" />

    自定义仓储工厂

    通过仓库工厂的RepositoryFactoryCustomizer进行自定义，可以直接访问参与仓库实例创建的组件。 当您需要调整代理创建的相关方面，而又不想引入完全自定义的仓库工厂 Bean 时，这种机制非常有用。 以下示例演示了如何注册额外的监听器和代理顾问：

    factoryBean.addRepositoryFactoryCustomizer(repositoryFactory -> {
	repositoryFactory.addInvocationListener(…);
	repositoryFactory.addQueryCreationListener(…);

	repositoryFactory.addRepositoryProxyPostProcessor((factory, repositoryInformation) -> factory.addAdvice(…));
});

    `RepositoryFactoryCustomizer` 与特定的仓库工厂 Bean 相关联，理想情况下通过 `BeanPostProcessor` 实现，以确保仅影响指定的仓库。请注意，自定义器 Bean 不会自动应用，以避免产生不必要的依赖注入问题，这在多仓库配置或使用多个 Spring Data 模块的场景中尤为关键。

    自定义仓库工厂 Bean

    定制仓库创建的最强大方法是提供一个自定义的仓库工厂 Bean，通常是 RepositoryFactorySupport、TransactionalRepositoryFactoryBeanSupport 或特定存储仓库工厂 Bean 的子类。

    自定义仓库工厂 Bean 可让您完全更改仓库的创建方式，并拥有对底层仓库工厂的完整访问权限。

    请注意，这种方法需要付出最多的努力，通常仅在您需要更改仓库创建的核心方面时才需要使用。此外，您还需要考虑用于识别查询方法、基础实现方法和自定义实现的仓库元数据推导。以下摘要概述了关键方面：

    • repositoryBaseClass：仓储基类定义了由基类实现的方法，以及需要通过切面或自定义实现进行额外处理的方法。

    • repositoryFragmentsContributor：一个 RepositoryFragmentsContributor 允许在收集完所有标准片段后对仓库组合进行扩展。存储模块使用此机制添加功能，例如 Querydsl 或按示例查询支持。它同时也作为第三方扩展的服务提供者接口（SPI）。

    • `exposeMetadata`：控制是否可通过 `RepositoryMethodContext.getContext()` 获取调用元数据。
